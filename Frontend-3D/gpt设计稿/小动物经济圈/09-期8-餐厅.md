# 期 8 · 餐厅

> 状态：**待施工** · 2026-08-24 · 前置：期 5（挂机经营的骨架）+ 走进过小镇

## 一句话

去过一趟小镇之后，你也想开一间自己的馆子：把做好的菜摆进去，
第二天回来变成钱和一份「昨晚谁来吃了什么」——还上了报。

**烹饪第一次有了出口。** 在这之前做菜只能自己吃，那个 45% 的"上乘"
火候窗口在经济上零表达。

## 为什么这一期比看起来小

**期 5 已经把骨架写完了**（`Systems/shopkeeping.ts` 的

## 三件事

### 8A · 解锁链：走进过小镇

**地理上这条门早就修好了**——东桥坐在锁定地块 `east_bridge` 上，
领地外走不了，而地块表特意把东边切成 7 + 8 两条，注释写着：

> 地块可以有大有小，但"扩两次才看得到桥"是玩法节奏，不能被形状改掉。

所以**不用另加任何解锁机制**，判据用期 0 的信号：

```ts
{
  id: "diner_unlocked",
  triggers: [{ signal: "map_entered", subject: "town" }],
  effects: [
    { kind: "start_dialogue", dialogueId: "thinking_about_a_diner" },
    { kind: "give_item", itemId: "blueprint_diner", quantity: 1 },
  ],
},
```

**判"去过小镇"而不是"开了桥那块地"**：到过镇上的人才见过餐厅长什么样，
条件和叙事对得上。期 0 补 `map_entered` 就是为它。

### 8B · 餐厅建筑

`Buildings/dinerOwn.ts`（新，**先问参考图**）。

**命名避开小镇那家 `restaurant`**——那是地图内容（六家店之一，
只有一级、不能建不能升、里面是空房间），和玩家自己盖的这栋完全是两回事。
两个 `buildingId` 撞名的话，`findBuilding` 会认错。

```ts
export const dinerOwn: BuildingDefinition = {
  buildingId: "diner_own",
  localizationKey: "building.diner_own",
  doorOffset: 0,
  maxInstances: 1,
  levels: [
    {
      levelId: "l1",
      footprint: { width: 5, height: 5 },
      // 同图走进去（领地建筑那条路），不是换图（那是小镇店铺的进法）
      interior: (style) => buildInterior({ width: 5, depth: 5, windows: true }, style),
      nextLevelIds: ["l2"],
      build: () => /* ... */,
    },
    // 升级换的是**菜位数**和客流上限
    { levelId: "l2", footprint: { width: 6, height: 6 }, /* ... */ },
  ],
};
```

### 8C · 品质进价格（这一期唯一的新设计）

`ItemQuality` 今天只影响两处：送礼档位（`giftRules`）、吃了回多少饱食
（`qualityFoodMultiplier`）。**卖价零表达**。

```ts
// Core/Data/needs/index.ts，现状
export const qualityFoodMultiplier: Record<ItemQuality, number> = {
  [ItemQuality.Poor]: 0.6,
  [ItemQuality.Normal]: 1,
  [ItemQuality.Good]: 1.15,
  [ItemQuality.Excellent]: 1.3,
};
```

餐厅要一份**卖价**倍率。**不复用上面那张表**：

```ts
// Core/Data/economy/index.ts 加
/**
 * 品质对**卖价**的加成。和 `qualityFoodMultiplier`（吃了回多少饱食）
 * 分成两张表，不是复用一张。
 *
 * 两者回答的是不同的问题：吃的那张管"这顿顶不顶饿"，收敛得很紧
 * （0.6 ~ 1.3，因为饱食是照顾自己不是数值竞赛）；卖的这张管"客人
 * 愿意多付多少"，**跨度要大得多**——不然火候那个小游戏在经济上仍然
 * 约等于零表达，玩家做焦了照样卖差不多的钱。
 *
 * 上乘 1.6 是让"看准火候起锅"值得为它守在灶台前；过火 0.5 是让它
 * 有代价但不至于血本无归（本作不做功亏一篑的判定，那个 45% 的宽容
 * 窗口就是为此）。
 */
export const qualitySellMultiplier: Record<ItemQuality, number> = {
  [ItemQuality.Poor]: 0.5,
  [ItemQuality.Normal]: 1,
  [ItemQuality.Good]: 1.25,
  [ItemQuality.Excellent]: 1.6,
};
```

于是整条链第一次接上：

```
火候（45% 窗口）→ 菜的品质 → 餐厅卖价 → 金币 → 开销
```

厨房、行动、经济三个系统从此在同一条链上。**而且没有新增任何数值系统**
——`ItemQuality` 早就有，只是多了一个消费方。

### 8D · 餐厅的 `ShopKind`

```ts
const DINER: ShopKind = {
  // 收"能吃的"。生食材也能摆——但卖价低，做成菜才划算
  accepts: (itemId) => Boolean(findItemDefinition(itemId)?.food),

  /*
   * 客源**先是居民**（用户 2026-08-24）。名单做成函数不是数组，
   * 以后加"小镇散客""节日客流"是往这里加来源，结算逻辑一行不动
   * ——期 5 立骨架时就是照这个留的口。
   */
  customers: () =>
    listResidents().map((r) => ({
      id: r.id,
      budget: shopkeepingTuning.budgetPerResidentPerDay,
    })),

  priceFor: (itemId, _customerId, quality) =>
    Math.round(
      (findItemDefinition(itemId)?.value ?? 0) *
        qualitySellMultiplier[quality ?? ItemQuality.Normal],
    ),

  report: (sold) => {
    recordGoldFact(sold.reduce((sum, s) => sum + s.price, 0));
    for (const s of sold) recordHeadlineFact("diner_served", s.itemId);
  },
};
```

> **`priceFor` 要多收一个 `quality` 参数**——期 5 立骨架时那个签名是
> `(itemId, customerId)`。这是骨架为第二个用户唯一需要放宽的地方，
> 期 5 写的时候最好就带上（可选参数），省得这里改一次接口。

**离线补算**同期 5：按实结算多天，**菜卖完就停**（货架即上限）。

## 最容易写错的四处

### 一 · `buildingId` 别和小镇那家 `restaurant` 撞名

小镇六家店是**地图内容**（不建不移不升、不进存档），玩家这栋是
**领地建筑**（进存档、能升级）。两者的数据归属完全不同，
`findBuilding` 撞名会把两条路搅在一起。

### 二 · 品质用两张表不是一张

`qualityFoodMultiplier`（0.6~1.3）收敛得紧，因为饱食是照顾自己；
卖价那张要拉开（0.5~1.6），否则火候小游戏在经济上还是约等于没有。
复用一张表 = 为了少写六行数字，把这一期唯一的新设计给废了。

### 三 · 生食材也能摆，但要让"做成菜更划算"自己成立

`accepts` 判的是"能吃"，所以番茄也摆得进去。这**不用禁**——
禁了要多写一条规则，而经济上它本来就不划算（一份番茄 6，
一道番茄炒蛋 12 起，上乘的近 20）。让数字说话比加一条禁令好。

### 四 · 离线补算不要加天数上限

同期 5：菜卖完自然停，货架就是上限。加天数上限 = 惩罚离线，
而"离线封顶 12 小时"那条规矩管的是**消耗**不是产出。

## 刻意不做的

- **实时操作的烹饪玩法**（用户想做成 Overcooked 那样——那是厨房重做那一版，
  连带把决策 7/27 的饱食系统一起重定，是独立的一条线）
- **小镇散客**（客源函数已留口，等小镇那条线做起来）
- **菜单 / 定价 / 翻台率**（经营模拟那一路）
- **客人进店的演出**
- **盘下小镇那家 `restaurant`**（用户选的是自己在领地上建）

## 九期收官后的样子

```
现实里做完一件事 → 开出一件家具 ─┐
                                ├→ 卖给水獭 / 摆进小店 → 金币 ─┐
每日任务打勾 ────────────────────┘                            │
                                                              ├→ 食材（经常性）
邻居陆续搬来 → 满三位 → 家具小店                               ├→ 图纸 / 开地（一次性）
            → 送打印机 → 每天一份报纸                          └→ 旅行商人的永久升级
去过小镇 → 自家餐厅 → 火候 → 品质 → 卖价 ──────────────────────┘
```

两条循环接上了，金币有了终点，扩地有了目的，厨房有了出口，
而进度条是**住进来的邻居和店里挂着的货**，不是任何一个数字。
