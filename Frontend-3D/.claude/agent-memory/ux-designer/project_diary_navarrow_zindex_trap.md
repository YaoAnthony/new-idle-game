`BookPlanner.tsx` 的 `NavArrow`（第二轮改的翻页控件，见 `NavArrow` 函数，
约第 489-522 行）做成了「两侧整条边 `w-[10%] h-full` 当热区」，热区是
`.relative flex ... z-10` 那层的**直接子元素**，和装书页的
`w-[96%] h-[95%] ... relative z-20` 那个 div 是**同级兄弟**。

问题：书页内部的可点元素（完成任务的圆形勾选按钮、右页的删除按钮）
自己写的是 `z-50`（比 `NavArrow` 的 `z-40` 更高），但这不管用——`z-20`
的书页容器因为自带 `position:relative` + `z-index` 建立了**自己的
stacking context**，内部所有 z-index（哪怕 9999）都只在这个 context
内部比较，出了这个 context 只按外层那个 `z-20` 参与比较。所以只要
`NavArrow`（外层 `z-40`）和书页内任何元素在屏幕上重叠，**不管书页内部
元素自己标了多高的 z-index，视觉和点击命中都是 `NavArrow` 赢**。

**算过重叠范围（1040×760 设计坐标）：** 左页勾选框在全局 x≈64-92，
落在左侧热区 x=0-104 之内；右页删除按钮在全局 x≈940-976，落在右侧
热区 x=936-1040 之内。当前测试存档每天只有 1-3 条，行没有堆到热区
纵向中点（约 y=374）附近，所以三张评审截图（`13/14/15-panel-diary*.png`）
里恰好看不出来——**天数据填满（`actionLogTuning.maxPerDay` 那么多行）
时会真的触发**：某一行的勾选框/删除按钮一旦落在热区里，那次点击会被
翻页按钮吃掉。

**这个尺寸下没有"两全"的热区宽度**：要不撞到内容（热区宽度得 <64
设计px≈27 CSS px）要不够无障碍下限（≥104 设计px≈44 CSS px）——27 和 44
之间没有交集，说明这个 bug 是 [[project-diary-bookplanner-scale]] 那个
缩放地板问题的下游症状之一，不是这次热区实现本身没做好。

**可行修法（方向，不是我来实现）：** 把 `<NavArrow/>` 挪到
`w-[96%] h-[95%] ... z-20` 那个书本容器**内部**（和 `HTMLFlipBook` 同级），
让它和书页里那些 `z-50` 按钮在同一个 stacking context 里直接比较——
这样箭头（`z-40`）会在空白区域盖住普通内容，但真正的按钮（`z-50`）
会按预期赢过箭头，两边都不用改数值。

**Why:** 2026-08-28 第二轮评审时读代码 + 手推坐标发现的，三张截图因为
测试数据太稀疏都没暴露出来，容易被当成"截图看着没事就是没事"放过去。
**How to apply:** 以后评审这个热区（或任何"整条边当点击区"的翻页/滑动
控件），除了看截图，要检查热区元素和真正内容元素是不是在同一个
stacking context——嵌套 z-index 逃不出父级 context 这条规则很容易被
忽略，截图测试数据少的时候尤其看不出来。

**已解决（2026-08-28 第三轮评审）：** 作者没有采纳"把 NavArrow 挪进
`z-20` 书本容器内部"这条建议，走了更彻底的路——把箭头整个挪出书本，
渲染在 `Modal.tsx` 新增的 `overlay` 属性里（`.modal-overlay`，
`position:absolute;inset:0;z-index:5`，和 `.modal-card`/`.modal-paper`
是 `.modal-stage` 下的**同级兄弟**，不嵌在书页的 stacking context 里）。
`DiaryPanel.tsx` 的 `NavArrow` 贴屏幕边（`left-3`/`right-3`），
`BookPlanner.tsx` 只对外暴露 `navApi`/`onNavChange`，自己不再画箭头。
用 `Modal.tsx` 的 `fit()` 公式独立重算过一遍几何，在 667×375 基准机上
`.modal-card` 左边缘 x=96、宽 475，左箭头 x=12 宽 44（右边缘 56），
两者隔 40 设计px，不可能重叠——这个数字和作者自己截图量出来的完全一致。

**这是比"调 z-index 顺序"更好的修法**：热区和内容根本不共享同一块
屏幕区域，不是"谁的 z 更高"赢了，而是压根没有谁能吃到谁的点击——不会
因为测试数据变多、行数变高而在某个临界点突然复发。副作用还带一个
无障碍红利：箭头是屏幕真实 44px，不跟着书那套 ~0.42 的缩放走，天然满足
WCAG 2.5.5 触控热区下限，不用像书页内部的勾选框/删除键那样受缩放拖累
（那个问题看 [[project-diary-bookplanner-scale]]，还没解决）。
**How to apply（追加）：** 以后再遇到"控件热区会盖住内容"这类冲突，
先问"这俩东西是不是必须同屏共存在同一块地方"——如果控件本来就该在
内容之外（翻页箭头、面板级操作按钮），直接把它挪到内容的父级容器
甚至更外层，比在同一层里抠 z-index 优先级更稳。
