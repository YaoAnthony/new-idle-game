## 实跑结果（2026-08-22）

### 五组寻路边界测试

用户定的验收标准：**必须验证真的到达了正确坐标**。

| # | 测试 | 结果 |
|---|---|---|
| ① | **从院子走进房子内景** | ✅ 到达，误差 0.05，镜头切成 `house:<实例>` 那间的盒子 |
| ② | **从院子走进小屋内景** | ✅ 到达，误差 0.04，镜头切成 `land_cabin:<实例>` |
| ③ | **绕开实心的金币罐** | ✅ 4 个路点绕过去，误差 0.06；罐上 `isWalkable` 为假 |
| ④ | **升级换占地** | ✅ 房子 l1→l2 占地从 `x −10..−2` 长到 `−11..−1`，`(−10.5, 6)` 从能走变成挡住 |
| ⑤ | **同一处建了再拆** | ✅ 空地能走 → 建后挡住 → 拆后又能走 |

### 一个只有实跑才会发现的坑：门槛那一圈的双重拦截

楼的脚印同时进了**院子的占用图**（挡放置、挡从外面穿墙）和**"只能走门"
那条规则**。两处都拦的话，**门槛那一圈正好死在中间**——门那条规则放行了，
脚印又挡了一次。

表现是屋里和门口在导航网格上是**两个不连通的岛**：洪水填充显示门格连通、
屋内不连通，中间整整一行全黑，`findRoute` 一律返回 null。而两边单独看
`isWalkable` 都是"走"，因为那条断线只有 0.5 格宽，随手采样采不到。

改成"人已经在某栋楼的占地里就别再问院子那张图"：**进出楼由门那条规则管，
院子的占用图只管院子**。

### 金币罐（B2 / B10 / B12）实跑

```
/gold show          → 0 / 0（罐 0 只）
/gold add 30        → 进账 0，溢出 30      ← 没建罐就攒不下钱
/build gold_jar …   → 容量 50
/gold add 30        → 进账 30（30 / 50）
/gold add 40        → 进账 20，溢出 20（50 / 50）
两只罐存 60         → 先把第一只灌满再灌第二只（50 / 50）
花 30               → 从第二只扣（50 / 20）
升第一只到 l2       → stored 50 保留，总容量 200
```

液面真的在动（y 1.36 → 1.56 → 0.96）。修了两个坑：状态变了**只更新那一栋**
不整组重建；**升级改的是容量不是余额**，fill 是两者之比，不重算的话升完级
液面还贴在罐口上——而且挂载时要先算一次，读档发生在 GameView 挂载之前。

### 农田四阶段实跑

`empty → planted → thirsty →(浇水) growing → ripe →(收获) empty`，
每一步模型都切到对应那组苗，收获拿到 3 个番茄，种子从背包扣掉 1 个。

### 选址 UI（B17）实跑

落在锁定格 → 红 + 「这块地还没开」；挪到自己地里 → 绿；点一下 → 确认条出现；
**把人传送到十几米外走一圈，虚影仍钉在 (−2.5, 10.5) 一动不动**；回来按确认，
建筑落在那个位置。

升级选址：虚影默认在原位、目标等级已是 l2、按 R 从 north 转到 east，
确认后 `l1→l2`、占地 2×2 变 3×3、**instanceId 不变、罐里 20 金币还在**。

### buildingAudit 当场抓到一个真漏

金币罐第一版漏了 `l1` 的 `nextLevelIds`，`l2`/`l3` 直接成了**孤岛**——
而型号文件看起来完全正常（三级都写齐了）。这正是"图的校验比链多两条"
那句话的现场证据。

## 刻意留着没做的（不是漏了）

| 没做 | 为什么 |
|---|---|
| **房子从 base 的 `generateRooms` 迁成建筑实例** | 文档 2B-4 说 base 不再返回 `living`。**没做**：那一步要动存档形状（老档里的 `living` 家具往哪儿归）、要给 `stowed` 机制安排退场，而期 1 的 T10 之后并没有第二次"随便删档"的豁免。今天两条路并存：`living` 是地图定义里那间（默认收起），`house` 是建筑实例。合并是下一期的事，`interiorRoomId` 已经按"实例决定 roomId"写好了口 |
| 小屋的「喜好居住」牌子走近显示文字 | 牌子建模了，交互提示没接。那要给建筑加一套 `interactHint`，和家具那套并存——是另一件事 |
| 工人 / 施工耗时 | B8：本期瞬时。`buildDuration` 和 `construction` 字段已留，接的时候不用做存档迁移 |
| 真实的升级材料 | B6：`upgradeCost` 全空，恒可升。**校验路径是通的**（有用例证明填了就拦、置空就放） |
| 拆除返还材料 | `removeBuilding` 只删不还；经济规则等金币经济落地 |
| 建筑的联机同步 | `buildings` 进 `WorldSave` 天然跟着房主走；op 化是 M2 |

## 这一轮拍板的决策（2026-08-21）

| # | 决策 | 影响 |
|---|---|---|
| B1 | **升级 = 同一建筑的多个等级**，不是换型号 | 实例存**当前等级 id**，**实例 id 不变**（里面存的东西、位置全保留） |
| B7 | **房子升级是分叉的**：1 → 2 → 3a 或 3b | `levels` 数组表达不了树。等级改成**有向图**：每级列出 `nextLevelIds`。房子只做居住，3a/3b 就是用来验分叉的 |
| B2 | **金币罐就是钱包**：罐里有多少就是你有多少 | 没有"收进兜里"这一步；花钱从罐里扣；**容量 = 你能持有的上限**（CoC 储存资源模式）。期 0 定的单一货币「金币」不变，只是它现在**装在罐里、有上限** |
| B3 | 金币罐只升**容量**，在外面操作；**可以多建，容量相加** | 领地多大决定摆得下几只罐——开地和建罐互相喂 |
| B4 | 农田在外面种，暂时只有 1 级 | 无升级路径，但走同一套基类 |
| B5 | **陆地小屋可以进去**，暂时只有 1 级 | **同图走进去**，和房子一样：小屋有自己的 `RoomSave` 内景，门在 base 图上，镜头切屋内。**不换图** |
| B6 | 材料要求先留空数组 | `upgradeCost: []` 恒可升，等金币/材料系统落地再填 |
| B8 | **升级瞬时完成**，工人+工期 3 期之后再说 | 本期是测试用；但数据结构预留 `buildDuration` 和"施工中"状态，接工人时不重构 |
| B9 | **升级前置条件结构先留、内容以后填** | `requires` 字段和校验函数本期就写，值恒空 |
| B11 | **房子必须先搬空才能升级** | 屋里有家具就拒绝升级。这条同时解掉"升级时家具会不会丢"那个最大的数据风险 |
| B10 | **罐满了，再进账的金币溢出丢失**（照 CoC） | 逼玩家升容量或多建罐。损失只发生在**你主动做任务/交易**的那一刻 |
| B12 | **还没建罐时容量为 0**；新手期指引建第一只罐 | 第一只罐的代价必须为 0（否则死锁）。指引是剧情那期的事，本期只保证"没罐就溢出"这条规则成立且有提示 |
| B13 | **指令用院子格号**，(0,0) 固定在领地西北角、盖整个 60×45；**位置 = 占地左上角** | 格号不随开地变（网格从第一天就是最大）；左上角和家具的 `gridPosition` 一套规矩，整数格天然对齐 |
| B14 | **农田新增种子物品**，一种对一作物；本期只做番茄 | `tomato_seed` → 长出 `tomato`。种子本期靠调试指令给，以后商店卖 |
| B15 | **小屋只声明喜好、本期不住人** | 型号写 `preferredPetIds`，走近看得到牌子；真让宠物住进去是宠物那一期 |
| B16 | **HUD 上金币画条**（图标 + 数字 + 容量条） | **推翻期 0 的 U2**（当时说不画条，理由是金币无上限）——现在罐给了上限，条才有意义。条满 = 该升罐或多建罐 |
| B17 | **升级要重新选址 + 二次确认**，本期就做虚影 UI | 升级会变占地，压到东西就得挪。选完不立即动工，让玩家绕两圈确认 |
| B18 | **非空不给拆**（和升级同一条规矩） | 屋里有家具 / 罐里有钱 → 拒绝拆除，提示先清空。不静默吞东西 |

## 参考：部落冲突怎么做的（2026-08-21 查证）

用户要求对照 CoC。查下来**四处一致、三处不同**：

只是还没接上升级系统——B8 预留的接口是为这一天准备的。

# 2A-0 · 一图多栋运行时（前提，3 天）

房子和小屋都是**同图走进去**的（B5）。今天 Frontend 运行时只认**一个** `room`、一个 `occupancy`、
一个地板面、一套门——期 0 底层调查列过 21 个文件从 `getWorld().room` 拿。两栋可进的房子同时站在领地上，
这套就得按房间各一份。**Core 的规则函数本来就按房间算，不用改；改的是运行时。**

期 1 已经做了一部分（`occupancyOf(roomId)`、`buildGroundMap` 收全部房间、放置链 8 处按房间取锚点）。
本段把剩下的收完：

| 子系统 | 今天 | 改成 |
|---|---|---|
| 镜头 | 0a-2：`standingHouses()` 列表——**期 0 的那项，这里必须做** | 列表来源从 `this.houses`（构造时 push 一条）改成**按领地上的建筑实例生成**：每栋有内景的建筑一条 |
| 门 `doorsRuntime` | `initDoors()` 读 `getWorld().room` 一间的门 | 遍历所有有内景的房间，每间的外门/内门各自登记；`outdoorPass` 的"穿墙只能走门"按**人正在穿哪栋**判（用 `roomIdAt` 找脚下的地板面） |
| 走路 `walkable` | 室内判定按主房间的矩形 | 先 `roomIdAt(x,z)` 定房间，再用**那间**的占用图和锚点。`isIndoors` 本来就按地板面答，不用改 |
| 家具视图/音景/烹饪槽位 | 期 1 已改 8 处 | 清剩下的：`petAgent` / `petsRuntime` / `resting` / `dailyTasks` / `obstacles` 里的 `getWorld().room`——**宠物只在主屋活动**这条本期保留，所以 pet 相关两处可以仍取主房间，但要写明 |
| `getWorld().room` 这个单数入口 | 到处用 | 保留，语义改成"**玩家此刻所在的房间**（没在任何屋里 = 院子）"，由 `roomIdAt(玩家位置)` 驱动。不删——删了 21 处要同时改，风险太大；改语义让大多数调用方自动正确 |

**`getWorld().room` 改成"所在房间"是本段的关键一步**：屋里的东西（占用图、锚点、门）本来就该问"我在哪间"，
原来它恒等于主房间只是因为从前只有一间。语义改对之后，大部分消费方不用动。

### 验收

- [ ] headless（Core）：不动——规则层本来按房间算
- [ ] vitest：两间有墙的房间（主屋 + 一间 6×5 的小屋）放在院子里，`occupancyOf` 各一张；在小屋里放家具只进小屋那张

- [ ] 浏览器：`getWorld().room.roomId` 在院子里 = `yard`，在主屋 = 主屋，在小屋 = 小屋（控制台探针）
- [ ] 两包 typecheck 绿；Core 全量 + vitest 全量绿

# 2A · 建筑基类与三条指令

## 现状：一半已经有了

期 0/1 之前就存在的两个类型正好是"型号 + 实例"的对子：

| 已有 | 是什么 | 差什么 |
|---|---|---|
| `Buildings/types.ts` · `BuildingDefinition` | **型号**：占地、门偏移、`interiorMapId`（六家店换图用）、`build()` 建模型。住在 Frontend（模型是 three.js 代码，进不了 Core） | 没有等级、没有名字介绍、没有升级材料；**没有"同图内景"的概念**——店是换图进的，领地上的房子和小屋是走进去的 |
| `Core/types/building.ts` · `BuildingPlacement` | **实例**：instanceId、buildingId、x/z/elevation/facing、`state?` | 注释写着"今天没有任何玩法会改它，所以它不进存档"——本期要让它**进存档** |

六家店今天用的就是这套（`TOWN_BUILDINGS` 是一组 `BuildingPlacement`），只是**从不变化**：不建、不移、不升。
2A 就是把"会变化"这件事加上。

## 2A-1 型号加等级（Frontend）

```ts
// Frontend-3D/src/Buildings/types.ts
export type BuildingLevelId = string;             // "l1" / "l2" / "l3a" / "l3b"

/** 一个等级的样子。等级之间可以换模型、换占地、换数值 */
export type BuildingLevel = {
  levelId: BuildingLevelId;
  localizationKey: string;          // 这一级的名字（"木屋 · 加建"）
  descriptionKey: string;           // 介绍，UI 和指令都读它
  footprint: GridFootprint;         // 升级可以变大——所以放这儿不放型号上
  build: () => Object3D;
  /**
   * 同图内景（B5）：这一级走进去是什么样的房间。给一个**户型生成器**，
   * 建筑实例创建/升级时用它生成 `RoomSave`（带锚点 = 建筑的位置）。
   * 没有 = 进不去（金币罐、农田）。3a/3b 的户型可以不同。
   * **不是换图**——房间就在 base 图上，人从门走进去，镜头切屋内（0a-2）。
   */
  interior?: (style: RoomStyleDefinition) => Omit<RoomSave, "roomId" | "anchor">;
  /**
   * 能升到哪几级。**这是一张有向图不是一条链**（B7）：
   * 房子 l2 的 nextLevelIds = ["l3a", "l3b"]，玩家挑一条。
   * 空数组 / 不填 = 已满级。
   */
  nextLevelIds?: BuildingLevelId[];
  /**
   * 升到**每个**下一级各要什么。键是目标 levelId——分叉的两条路代价可以不同。
   * 空数组 = 无条件可升（B6：材料系统落地前恒空）。
   */
  upgradeCost?: Record<BuildingLevelId, Array<{ itemId: ItemId; quantity: number }>>;
  /**
   * 升到某一级的**前置条件**（B9，照 CoC 的"先铺满再升主厅"）。
   * 今天恒空 = 无条件；以后填 `[{ buildingId: "gold_jar", minLevelId: "l2" }]`
   * 这类。**结构本期就留**，校验函数和报错理由一起写好，加内容时是填数据不是改代码。
   */
  requires?: Record<BuildingLevelId, Array<{ buildingId: string; minLevelId: BuildingLevelId }>>;
  /**
   * 升到某一级要多久（秒）。**本期恒 0 = 瞬时**（B8）。
   * 留着是因为工人系统那一期要接："占一个工人 + 等这么久"，
   * 那是 CoC 的核心约束（建筑工小时），迟早要有。
   */
  buildDuration?: Record<BuildingLevelId, number>;
};

export type BuildingDefinition = {
  buildingId: string;
  localizationKey: string;          // 型号名（不带等级）
  descriptionKey: string;
  doorOffset: number;
  /** 至少一级。第一个是**初始等级**（新建出来就是它） */
  levels: BuildingLevel[];
};
```

**为什么是图不是数组**（B7）：房子要 `1 → 2 → 3a 或 3b`。数组下标天然是一条链，
表达不了分叉；硬用数组就得在外面另写一张"谁能升到谁"的表，两份数据迟早走散。
改成每级自己声明 `nextLevelIds`，**链是图的特例**（每级只有一个后继），
金币罐 l1→l2→l3 照样写得出来。

**实例存 `levelId` 不存 `level` 数字**：分叉之后"第几级"不再唯一（3a 和 3b 都是第三级），
数字没有意义。存 id 还顺带解决了"以后在中间插一级"——数组下标会全部移位，id 不会。

**为什么等级带 footprint / build / interior 而不是型号带**：升级要能变大变样子
（金币罐 L1 一只小罐、L3 一组三罐；房子 3a 和 3b 内景不同）。放型号上表达不了。

**六家店怎么迁**：每家的 `footprint` / `build` 包成 `levels: [{ levelId: "l1", … }]`（无 `nextLevelIds` = 满级）；
`interiorMapId`（换图进店）**留在型号上不动**——那是小镇店铺的进法，和领地建筑的同图内景是两回事，
两个字段并存，各管各的。一次机械改动，行为不变。

**型号加 `maxInstances?: number`**（B3 的"可以多建"）：不填 = 不限。本期罐和田不限，房子 1。

```ts

/** 这栋楼在世界里的占地矩形。footprint 取当前等级的，facing 旋转后宽深互换 */
export function buildingRectWorld(placement: BuildingPlacement, footprint: GridFootprint): DeckRect;

export type BuildCheck =
  | { ok: true }
  | { ok: false; reason: "outside_territory" | "overlaps_building" | "overlaps_house" | "cell_occupied" | "uneven_ground" };

/**
 * 这栋楼能不能放在这。**复用期 1 的两条**：领地用 rectInsideTerritory，
 * 地面平整度和压不压到东西用 housePlacementCheck 那套判据——房子和建筑
 * 是同一件事的两个尺寸，判据不该有两份。
 */
export function checkBuildingPlacement(…): BuildCheck;

export type RemoveCheck =
  | { ok: true }
  | { ok: false; reason: "not_empty"; detail: { furniture?: number; gold?: number } };

/** 能不能拆（B18）：屋里有家具 / 罐里有钱 → 不给拆，和升级同一条规矩 */
export function checkRemove(placement, contents): RemoveCheck;

export type UpgradeCheck =
  | { ok: true }
  | { ok: false; reason: "max_level" | "unknown_target" | "not_a_successor" | "missing_materials" | "requires_unmet"; unmet?: Array<{ buildingId: string; minLevelId: string }> };

/**
 * 能不能升到 targetLevelId。
 *
 * **必须指定目标**（B7）：分叉之后"升级"不再是一个动作而是一个选择。
 * 不指定就默认第一个后继的话，房子会在玩家没选的情况下悄悄变成 3a。
 * materials 传玩家背包的计数；upgradeCost 为空 = 恒 ok（B6）。
 * others 传领地上其他建筑的当前等级，用来判 requires（B9）；requires 为空 = 恒 ok。
 * **两个空值让本期恒可升**，但校验路径是通的——以后填数据即生效。
 */
export function checkUpgrade(level: BuildingLevel-like, targetLevelId, materials, others): UpgradeCheck;

/** 这一级能升到哪几级（给指令和以后的 UI 列选项） */
export function successorsOf(level: BuildingLevel-like): BuildingLevelId[];
```

> `checkBuildingPlacement` 收的是"型号的占地"而不是整个 `BuildingDefinition`——
> 定义住在 Frontend（带 three.js 的 `build()`），Core 不能 import 它。签名只收 `GridFootprint`。

`Core/src/logic/buildingAudit.ts`（新）——**图的校验比链多几条**：

- 每个型号至少一级；`levelId` 在型号内唯一
- 每个 `nextLevelIds` 指向的 id 都存在
- `upgradeCost` / `requires` / `buildDuration` 的键都在 `nextLevelIds` 里（写了却不是后继 = 死数据）
- `requires` 指向的 `buildingId` 和 `minLevelId` 都存在（防止指向打错的型号）
- **无环**（沿 `nextLevelIds` 走不能回到自己）——环会让"升级"变成死循环
- 从初始等级出发**每一级都可达**（孤岛等级 = 永远升不到的死内容）
- 型号的 `interiorMapId`（若有）指向的图存在；等级的 `interior`（若有）生成的 RoomSave 过 `roomAudit`（有墙必有门）

## 2A-5 三条指令

**坐标约定（B13）**：`<gx> <gy>` 是**院子格号**——`(0,0)` 是领地西北角，`(59,44)` 是东南角，
**格号固定盖整个 60×45，不随开地变**（网格从第一天就是最大，期 1 已定）。
给的位置是**占地的左上角**（西北格），和家具的 `gridPosition` 一套规矩。
`/buildings` 和报错信息里也一律用格号，不混世界坐标。

> 和 `/tp` 的世界坐标是两套。`/buildings` 的输出同时打两种（`C3 · 格 (28,37) · 世界 (-2,10)`），
> 调试时不用心算。

| 指令 | 行为 |
|---|---|
| `/build <buildingId> <gx> <gy> [facing]` | 校验 → 建。失败打原因（不在领地/压到东西/地不平/超出该型号上限） |
| `/movebuilding <instanceId\|name> <gx> <gy> [facing]` | 同校验；**校验时排除自己**（不然原地微调会判成"压到自己"） |
| `/upgradebuilding <instanceId\|name> [levelId]` | 不给 `levelId`：**列出可选的后继**并停下（分叉时必须让玩家选，B7）。只有一个后继时直接升。给了就升到那一级。打出新等级的名字和介绍 |
| `/removebuilding <instanceId\|name>` | 拆。**屋里有家具 / 罐里有钱就拒绝**（B18），提示先清空 |
| `/buildings` | 列出：instanceId、型号、当前等级、位置（格号 + 世界坐标）、可升到哪几级 |

`name` 是模糊匹配型号名（`/movebuilding 金币罐 5 12`），只有一栋时最省事；多栋时提示用 instanceId。

# 2A-6 · 选址 UI（3 天）

> B17：建造、移动、升级**都要先选址、再二次确认**。用户原话：
> "选定了之后，需要再次确认开始动工，这样方便用户绕两圈确认做的不错。"

## 为什么升级也要选址

升级会变占地（房子 8×6 → 10×8 → 12×10）。新增的那一圈可能压到旁边的罐子或田。
与其"挡着就拒绝"，不如**让玩家重新摆一次**——顺便他还能借升级的机会把房子挪个方向。

## 交互

复用家具布置模式那套（`PlacementController`），三处不同：

| | 家具布置 | 建筑选址 |
|---|---|---|
| 吸附 | 整格 | 整格（同） |
| 虚影 | 家具模型半透明 | **目标等级的建筑模型**半透明 + 地面一圈占地框 |
| 落点判据 | `checkPlacement`（占用图） | `checkBuildingPlacement`（领地 + 占用图 + 地形平整 + 排除自己） |
| 确认 | 点一下就落地 | **点一下先"选定"，再按确认键才动工**（B17） |
| 旋转 | R | R（同） |

**两步确认的形状**：

1. 进入选址：虚影跟着鼠标，绿/红实时提示；红时**说明原因**（"这块地还没开" / "金币罐挡住了" / "地不平"）
2. 在合法位置点一下 → **选定**：虚影停在那儿不再跟鼠标，出现一行确认条
   （"在这里建造木屋？ [确认] [重选] [取消]"）
3. 玩家可以走开绕两圈看——虚影一直在那儿
4. 按确认 → 动工

> 第 3 步是这条设计的**灵魂**：选定之后虚影不消失，玩家能绕着它转一圈再决定。
> 这也是为什么不做成"点一下直接建"。

**升级的选址预填**：进入升级选址时，虚影**默认摆在当前位置**（同朝向）。原地合法就直接确认，
不合法（新占地压到东西）才需要挪——大多数时候玩家只要按两下。

## 2B-1 金币罐（Gold Jar）

> 装金币的罐子。**罐就是钱包**（B2）：罐里有多少就是你有多少，容量就是你能持有的上限。
> 期 0 定的单一货币「金币」不变——变的是它从"一个无上限的数字"变成"装在罐里、会满"。

### 玩法

| | 说明 |
|---|---|
| 入账 | 完成每日任务、卖东西结算时，金币**直接进罐** |
| 花钱 | 买东西、升级建筑、开地——**直接从罐里扣**。没有"收进兜里"这一步 |
| 上限 | 所有罐的容量之和（B3：可以多建、容量相加）。**满了之后再入账的部分溢出丢失**（B10） |
| 升级 | 只升容量。三级：l1 / l2 / l3 |
| 多建 | 领地上摆得下几只就有几只——**开地和建罐互相喂**，这是领地扩展的第一个真实用途 |

**为什么是钱包不是收集器**：如果罐只是中转站、收进一个无上限的余额，那容量限制的只是"你多久没来收"，
而罐**不自增**，每次做完任务顺手一收就永不溢出——容量就不成其为关卡。做成钱包之后，
"我攒不下钱"是真实压力，升罐/多建罐才有意义。这也正是 CoC 的储存资源模式。

**没建罐时容量为 0**（B12）：开局领地是空地，第一笔金币会全额溢出。
所以**第一只罐的建造代价必须为 0**（本期 `upgradeCost` 全空，天然满足），
新手期指引玩家建第一只罐——指引本身是剧情那期的事，本期只保证规则成立且**溢出时有明确提示**
（"没有金币罐，金币流失了"）。

**金币属于谁**：属于**世界**（`WorldSave` 的建筑实例 state）。罐子是领地上的设施，
和"出货箱内容属 PlayerSave"不同——那个是你托运的货，这个是你家里的钱柜。
联机时进别人的领地，花的是自己家的钱：**余额查询按"我的领地"而不是"当前所在领地"**。

### 规则（Core）

**液面要看得见**：罐口内一片圆面，`y` 按 `stored / capacity` 插值——玩家一眼看出还能装多少。
这是这个建筑的灵魂，不做就只是个装饰。满罐时液面到顶 + 罐口一点微光，提示该升级或多建。

### HUD（B16：推翻期 0 的 U2）

期 0 定过"金币在左边跟精力条一起、**不画条**"，理由是金币无上限、画条得编一个假上限。
**罐给了上限之后这条理由不成立了**——现在画条是对的：

```
 🍙  72   ▇▇▇▇▇▇▇░░░
 🌿  55   ▇▇▇▇▇░░░░░
 🪙 340   ▇▇▇▇▇▇░░░░   ← 340 / 600（两只罐容量之和）
```

和上面两行完全同形（图标 + 数字 + 条），因为它现在**就是同一类东西**：一个有上限的量。
条满 = 该升罐或多建罐，一眼看得出。没有罐时条为空、数字 0、`tabular-nums` 对齐。

## 2B-2 农田（Farm Plot）

> 播种、浇水，暂时只有 1 级。

### 玩法

| | 说明 |
|---|---|
| 状态 | 空地 → 已播种 → 需浇水 → 成熟 → 收获（回到空地） |
| 操作 | 走过去按 F。手上拿着**种子**就播种；已播种且干燥就浇水；成熟就收获 |
| 生长 | 按真实时间：`plantedUtc` 到现在算到哪个阶段。关游戏也照长（存的是时间戳不是进度条） |
| 浇水 | 播种后某个时点进入"需浇水"，浇了才继续长；**不浇会停在那一阶段**（不枯死——陪伴类游戏不惩罚忘记） |
| 等级 | 只有 1 级（B4），但走同一套基类——以后加 l2（更大的地）不用改架构 |

**种子是新物品**（B14）：本期只做一对——`tomato_seed` 种下去长出 `tomato`。

```ts
// Core/src/types/items.ts — ItemDefinition 追加
/** 是一包种子：种下去长出什么、多久熟。有这块的物品能在农田上播种 */
seed?: { cropItemId: ItemId; growMinutes: number; waterAtMinutes: number; yield: number };
```

> 和"家具是带 `placement` 块的物品"同一个路数：**能力块而不是新类型**。
> 种子今天靠 `/give tomato_seed 5` 拿；以后市场卖（决策 E7 的货架里本来就有"种子"一项）。

**为什么不直接种食材**：番茄种出番茄就是无限循环，平衡没法做。种子是单独物品，
产出比才有得调。

**数据挂哪**：`BuildingPlacement.state` = `{ seedItemId, plantedUtc, wateredUtc? }`，
当前阶段是**算出来的**不是存的（纯函数 `farmStageAt(state, seedDef, nowUtc)`）——
存阶段就得有人定时推进它，存时间戳则永远自洽。

木框围出的一块土地，四角木桩。土面按状态换样子：

| 阶段 | 样子 |

## 2B-4 房子（House）· 分叉升级

> 房子目前只做 `1 → 2 → 3a 或 3b`。房子就是居住用的，**3a/3b 主要是验证分叉升级功能**（B7）。

### 和期 1 那栋"主屋"的关系

**这是同一栋房子，换了个身份。** 期 1 里房子是地图定义直接生成的一个 `RoomSave`（默认收起，T9）；
本期它变成**一栋建筑实例**（`BuildingPlacement`）+ 它的内景（由等级的 `interior` 生成的 `RoomSave`）。

| | 期 1 | 期 2 |
|---|---|---|
| 从哪来 | `generateRooms` 里写死一间 `living` | `/build house` 建出来，房间随实例生成 |
| 外面看 | `buildHouse` 从 RoomSave 建的几何 | 建筑型号 `house` 的 `levels[].build()` |
| 里面 | 同一个 RoomSave | 等级的 `interior` 生成的 RoomSave，**锚点 = 建筑位置** |
| 怎么进 | 走进去（同图） | **走进去（同图）**——没变 |
| 能不能移动 | `/house stow` / `place`（只能原位放回） | `/movebuilding house x z`（真的能挪，内景锚点跟着走） |
| 升级 | 没有 | `/upgradebuilding house l3a` |

**迁移路径**（本期做）：`base` 图的 `generateRooms` 不再返回 `living`——院子（`yard`）成为地图定义里
唯一的房间。房子的内景改成**跟着建筑实例走**：建造时生成、移动时改锚点、升级时换几何。

> 这一步把期 1 的 T9（房子默认收起）**兑现成正式形态**：领地上一开始就没有房子，
> 玩家用 `/build house` 建一栋——"从一块空地开始"这条线终于闭合了。
> 旧的 `stowed` 机制随之退役（房子不在 = 没有这个建筑实例，不需要"收起"这个状态）。

**内景房间的 roomId**：`house`（固定，不带等级）。升级换的是几何不是身份——
这样家具的 `roomId` 在升级前后一致，配合 B11（升级必须先搬空）是双保险。

### 四个等级

| levelId | 名字 | 占地 | 样子 | 内景（同图，roomId 恒为 `house`） | 后继 |
|---|---|---|---|---|---|
| `l1` | 木屋 | 8×6 | 单坡顶小木屋，一扇门一扇窗 | 一间房，6×4 | `l2` |
| `l2` | 木屋 · 加建 | 10×8 | 加一间偏厦、烟囱、门前一步台阶 | 两间房（一道内墙 + 门洞），8×6 | **`l3a`, `l3b`** |
| `l3a` | 石造宅 | 12×10 | 石墙 + 木构，双坡瓦顶，正面门廊 | 三间 + 门厅，10×8 | 无（满级） |
| `l3b` | 塔屋 | 8×8 | 占地不变但**长高**：三层塔身 + 观景平台 | 6×6 一间，**墙高 8**（挑高，镜头上限跟着走） | 无（满级） |

> `l3b` 的"三层"本期用**挑高一间**表达（墙高 8 而不是 4）——真正的多层楼板是 `RoomSave.floor` 那条线，
> 今天"只构建和渲染一层"。挑高已经能让 3b 一眼看出和 3a 不同，多层留给以后。

**3a 和 3b 刻意往两个方向走**：3a 摊开（占地大、气派），3b 长高（占地小、挑高）。
这样"选哪条"才是真选择，而不是换个皮。3b 占地小的实际意义：**领地紧张时它是省地的那条路**——
和领地系统咬合上了。也顺带验了分叉后**占地可以不同**、**内景可以不同**。

`upgradeCost` 本期全空（B6）：`{ l2: [], }` / `{ l3a: [], l3b: [] }`。

### 升级必须先搬空（B11）

**屋里还有家具就不给升级。** 玩家先把东西收进背包，房子空了才能升。

这条一加，"升级时家具会不会丢"那个最大的数据风险直接消失——**没有家具，就没有归属问题**。
原来的对策（四级内景共用一个 roomId）仍然照做，但它从"救命稻草"降级成"顺手做对"：

| | 原方案 | 加了 B11 之后 |
|---|---|---|
| 升级时屋里有家具 | 靠 roomId 保持一致来保命，验收专门盯 | **升不了**，直接拒绝 |
| 风险等级 | 本期最大的数据风险 | 不存在 |

```ts
// checkUpgrade 的又一个理由
| { ok: false; reason: "not_empty"; itemCount: number }
```

判据：`placedFurniture` 里 `roomId` 是这栋房子内景的那些，数量 > 0 就拒绝。
报错文案要说清怎么办："屋里还有 7 件家具，先收进背包再升级。"

> **为什么不自动搬空**：自动把玩家精心摆的一屋子东西塞回背包，是替玩家做决定；
> 而且背包放不下时还要处理溢出。让玩家自己动手，顺带也是一次"确认你真的要升级"。
> 以后要做"一键收纳"是 UI 的便利功能，不是升级流程的一部分。

## 建模标准（四个都要"精美"）

沿用仓库现有的低模路数（`Game3D/Visual/primitives` 的 `box` / `cylinder` / `blob`，
`palette.ts` 取色，`jitterShade` 抖色）。要"精美"靠的是这几条，不是堆面数：

| 条 | 说明 |
|---|---|
| **有层次** | 每个建筑至少三层：主体 + 结构件（木架/铁箍/石座）+ 一处记号。六家店的 `shell.ts` 就是这么做的——共用骨架 + 一处独门记号 |
| **色从 palette 取** | 不写字面色值。木 `woodMid/woodDark`、石 `baseStone`、铁 `ironMid`、水 `waterBlue` |
| **抖色** | 同材质的多个块用 `jitterShade(基色, i, j)`，避免"一整块纯色塑料" |
| **状态看得见** | 金币罐的液面、农田的四个阶段、小屋的窗光、房子各级的轮廓差异——**这是各建筑的灵魂**，不能省 |
| **等级看得出** | L1→L3 不只是变大：加结构件、加装饰、加记号。房子的 3a/3b 要**一眼分得出走了哪条路** |
| **不投影的小件不 castShadow** | 性能纪律，照现有做法 |

**一栋楼一个文件**（`Buildings/<id>.ts`），`index.ts` 登记一行——沿用现有约定。
