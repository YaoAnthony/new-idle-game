## 一句话

三位邻居来问能不能买你的家具，于是你开了间小店：把家具摆上货架，
关掉游戏，第二天回来变成钱和一句「谁买走了它」。

**从"等水獭来"变成"天天都能卖"——这才是小店真正的价值。**

## 这一期立的是**骨架**，餐厅（期 8）是第二个用户

小店和餐厅是同一件事的两个皮：

| | 家具小店（期 5） | 自家餐厅（期 8） |
|---|---|---|
| 上架什么 | 家具 | 做好的菜 |
| 谁来买 | 居民 | 居民（以后加小镇散客） |
| 什么时候结算 | `day_started` | `day_started` |
| 结果 | 金币 + "谁买走了什么" | 金币 + "昨晚谁来吃了什么" |
| 报纸版块 | 市场行情 | 餐厅 |

**所以这一期要把 `Systems/shopkeeping.ts` 写成通用的**：一个"货架 →
隔夜结算 → 报告"的机器，小店和餐厅各自喂它不同的货和不同的客源。
期 8 的工作量因此会小很多。

写的时候就按两个用户设计，不要等期 8 再来抽象——那时候第一个用户已经
长满了小店专属的假设，抽象会变成重写。

### 5B · 通用的「上架 → 隔夜结算 → 报告」骨架

`Systems/shopkeeping.ts`（新）。**这个文件从第一天就要为两个用户写。**

```ts
/**
 * 挂机式经营的通用骨架：**上架 → 隔夜结算 → 报告**。
 *
 * 两个用户：家具小店（期 5）和自家餐厅（期 8）。两者的差别只有三样——
 * 货是什么、客源是谁、报告怎么写——所以它们是这个机器的**参数**，
 * 不是两份代码。
 *
 * ## 为什么是挂机式而不是柜台式
 *
 * 用户 2026-08-24 定的。而它恰好是本作**唯一**和"绝对时间结算、关掉
 * 也在走"对得上的形态：你把货摆上，关游戏，明天回来钱到账。柜台式
 * （客人上门你现卖）要求玩家在场，和整个定位拧着。
 *
 * ## 货架就是天然的上限
 *
 * 离线十天回来不会凭空多出十天的钱——**货架上有多少就卖多少，卖完就停**。
 * 这正是动森那条"产出补但封顶"（跳一天化石 4→6，跳十天还是 6），
 * 而我们连封顶规则都不用写：货架自己就是上限。
 */

export type Shelf = {
  /** 哪栋楼的货架 */
  instanceId: string;
  /** 货位。null = 空位 */
  slots: Array<{ itemId: string; count: number } | null>;
};

export type ShopKind = {
  /** 这类店卖什么（判据函数，不是清单） */
  accepts: (itemId: string) => boolean;
  /** 今天有哪些客人，各有多少预算 */
  customers: () => Array<{ id: string; budget: number }>;
  /** 一件货对某位客人值多少（餐厅要按品质加价，小店就是 value） */
  priceFor: (itemId: string, customerId: string) => number;
  /** 结算报告怎么写进昨日事实 */
  report: (sold: SoldEntry[]) => void;
};

/**
 * 结算一天。**确定性**——同一天同一份货架同一批客人，算出来必须一样，
 * 否则玩家重开游戏就能重摇销量。
 *
 * 顺序：客人按 id 排序 → 每人按预算从贵到便宜挑（贵的先被买走，
 * 这样"摆好货"是有回报的）→ 卖完即停。
 */
export function settleDay(shelf: Shelf, kind: ShopKind, worldDayId: string): SoldEntry[];
```

**小店的 `ShopKind`**：

```ts
const FURNITURE_SHOP: ShopKind = {
  accepts: (itemId) => Boolean(findItemDefinition(itemId)?.placement),
  customers: () =>
    listResidents().map((r) => ({
      id: r.id,
      budget: shopkeepingTuning.budgetPerResidentPerDay,
    })),
  priceFor: (itemId) => findItemDefinition(itemId)?.value ?? 0,
  report: (sold) => {
    recordGoldFact(sold.reduce((sum, s) => sum + s.price, 0));
    for (const s of sold) recordHeadlineFact("shop_sold", s.itemId);
  },
};
```

**客源做成函数不是数组**（用户 2026-08-24 定："我们可以默认是居民先"）：
以后加"小镇散客""节日客流"是往名单里加来源，结算逻辑一行不动。

### 5C · 上架面板 + 离线补算

#### 面板

`PanelId` 加 `"shopShelf"`；组件照 `StoragePanel`（那也是"背包 ↔ 格子"
的双向搬运），加一列"这件值多少"。

#### 离线补算

```ts
// day_started 的监听里
const missed = daysBetween(lastSettledWorldDayId, currentWorldDayId);
for (let i = 0; i < missed; i += 1) {
  const sold = settleDay(shelf, kind, dayIdOf(i));
  if (sold.length === 0) break;   // 货卖完了，后面几天不用算
}
```

**按实结算多天**（总纲的"产出类：补，但封顶"），封顶靠货架存量。
`lastSettledWorldDayId` 存在建筑的 `state` 里。

> **不要给它加一个"最多补 N 天"的上限。** 货架就是上限，再加一层
> 是在惩罚离线——而离线补算封顶 12 小时那条规矩管的是**消耗**
> （饿、累），不是产出。产出没有理由罚。

## 最容易写错的四处

### 一 · 从第一天就按两个用户写

期 8 的餐厅要复用这套。第一个用户很容易长满专属假设（"客人就是居民"
"价格就是 value"），到期 8 再抽象等于重写。`ShopKind` 那四个函数
从一开始就要留着。

### 二 · 结算必须确定性

同一天同一份货架算出来必须一样。用 `hashSeed(instanceId|worldDayId)`，
不用 `Math.random()`——否则玩家发现"今天没卖出去"就重开游戏重摇。
和每日任务抽签、水獭想要清单同一条判据。

### 三 · 离线补算的封顶靠货架，不靠天数上限

加天数上限 = 惩罚离线。货架空了自然停，这是动森的"产出补但封顶"，
而且我们连规则都不用写。

### 四 · 摆出去的家具不能直接卖

上架的是**背包里的**。屋里摆着的要先收回背包才能上架——否则玩家会
误把正在用的桌子卖掉，而且 `ownedCountFn`（开箱的"已经有了"判据）
会跟着乱。

### 两处偏离原计划的设计（都是看过现成代码之后改的）

**一 · 货架不另立存档形状，直接复用储物库存。**
文档原本写了一个 `Shelf` 类型。看过 `State/storage.ts` 之后放弃：那套
已经是"一个实例 id ↔ 一格一格的东西"，而且**已经在 `WorldSave.inventories`
里**——存档、迁移、联机 op 通道、孤儿清理、面板范本五样全是现成的，
每一样都有过踩坑记录。另立一份等于把五个坑重踩一遍。

代价只有一处：`pruneOrphanStorages` 的活名单原来只喂**家具**实例 id。
不补的话每次 `world_changed`（摆一件家具就发）整架货当场蒸发，下一次
自动存盘永久落盘。两个调用点（`RoomScene` 和 `serialize`）各加了一句，
注释写明**活名单的语义是"还拥有库存的东西"**，不是"家具"。

**二 · 结算算法放 Core，不放前端。**
照 `logic/goldJar.ts` 的先例。于是"离线十天只够卖三天的货""贵的先被
买走""同一份货架算两次结果逐字一样"这些判据全是纯函数用例——不起浏览器、
不碰存档。前端那一层只剩凑入参、扣货、进账、记账。

### 实测抓到的三件事

**① 金库满着的时候，卖出去的钱静默溢出。**
最严重的一条。第一次实测：三位居民各买走一张桌子，`/gold` 从 40/40 到
40/40，一分没涨——**家具真没了，钱一枚没进**。

金币罐是钱包、超出容量丢弃，这是 `goldJar.ts` 立下的规矩，玩家在场时
它是好的（`depositGoldTo` 当场弹"金库满了"）。**挂机结算没有那个当场**：
离线一夜回来，只有一屋子少掉的家具和一句没人听见的提示。

改成 **金库装不下就不成交，货留在架上**（Core 的 `settleDay` 多一个
可选的 `revenueCap`）。没有任何损失，玩家第二天看见满架的货和满格的
金库，自己就知道该加只罐子。这也没破坏"货架就是上限"，只是多了一个
同样看得见的上限。空位**逐天重算**——一次性算的话，十天的货会按第一天
的空位放行。

**② `/shop settle` 说不出为什么没卖出去。**
原来一律回"一件都没卖出去（货架空了？没有居民？）"，而真凶往往是满金库
——我自己就被这句话带着去翻了一圈货架。改成三个原因分开报。拒绝要给
理由是这套建筑系统一开始就立的规矩（`BuildingPanel` 的 `whyBuild`）。

**③ 一张 60 的唱片在架上挂了五天没动，我差点改错地方。**
第一反应是"它没有 value"，动手把 `canShelve` 收窄成 `value > 0`——
查了数据才发现它 **value 是 60**，卖不掉是因为**没人买得起**：居民一天
15，谁都够不着。那是行情不是错误，贵重物件本来就归水獭（他按全价收），
小店做的是细水长流的量。

判据改回去了，改的是**面板**：底部并排显示「架上这些值 105 · 今天客人
带了 45」。两个数摆在一起，玩家一眼就看得出哪件是"摆着好看的"。
这条实测记在这里，是因为**我差一点把一个正确的行情当成 bug 修掉**。

### 顺手删掉的重复品

中途加了个 `/skipdays <n>`，写完才发现 `/advance <小时数>` 已经在做同一件事
