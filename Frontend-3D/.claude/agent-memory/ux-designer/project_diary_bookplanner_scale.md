日记本面板（`Frontend-3D/src/Components/Diary/DiaryPanel.tsx` + `Frontend-3D/src/BookPlanner.tsx`）
把整块 1040×760 设计稿用 CSS `transform: scale()` 整体缩小塞进 Modal 封面里
（`DiaryPanel.tsx` 里 `DESIGN_W=1040, DESIGN_H=760`，配 `Modal` 的
`--modal-outer`/`--modal-frame-w`，见 `src/index.css` `.modal-stage` 那段）。

在基准机 667×375（横屏最小支持尺寸，见用户全局记忆
`landscape-only-iphone-se`）上，算出来的缩放比 **≈0.425**（高度吃紧，卡在
`--modal-outer:14px / --modal-frame-w:12px` 那档，book 内部又有
`max-h-[720px]` 硬顶，比 95% 高度还矮）。这个比例把设计稿里 28px 的
`h1` 标题压到约 **11.9 实际 CSS px**，17px 的正文压到约 **7.2px**，13px 的
`分`/`min` 单位字压到约 **5.5px**——全面跌破可读下限。更严重的是可点
元素：`w-[36px] h-[36px]` 的删除/播放按钮实际命中区只剩约 **15.3 CSS px**，
远低于 WCAG 2.5.5 / Apple HIG 建议的 44px。

**这不是某个 padding/margin 数值调一下能救的**——即使把 Modal 外壳的
`--modal-outer`/`--modal-frame-w` 砍到最小，缩放比也只会从 0.425 涨到
~0.46 左右，标题也就到 12.6px，仍然不合格。真正的修法是给小屏一套
独立的紧凑版式（更大的基础字号、更少的装饰层，或者一次只显示单页
而不是摊开两页——单页模式能让缩放比接近翻倍）。`DiaryPanel.tsx`
第 99-102 行的注释里作者自己已经承认这点，定性为"下一轮的设计决定"，
不是这次要蒙混过关的地方。

**Why:** 2026-08-28 做 667×375 截图评审（`13-panel-diary.png`）时算出来的，
是这次评审给 FAIL 结论的主要原因。
**How to apply:** 以后再被问「日记本这个尺寸下能不能用」，先确认这个
缺口有没有被真正解决（有没有做小屏专用版式/单页模式），而不是又去看
某个 padding 是不是调了——调 padding 解决不了这个量级的差距。

**订正（2026-08-28 第二轮评审）：** 上面说「单页模式缩放比接近翻倍」
是**算错的**，被用户当场指出并验证。正确算法：

内胆（`.modal-paper`）在 667×375、`--modal-outer:14px`/`--modal-frame-w:12px`
这一档下实测/推导为 **451×323**（`Modal.tsx` 里 `fit()` 那段：
`cardH = stageH - outer*2 = 347`，`cardW = cardH * COVER_ASPECT ≈ 474.8`，
两边各减一次 `frameW*2` 得 451×323）。两页摊开模式设计尺寸
`DESIGN_W=1040 / DESIGN_H=760`，`scale = min(451/1040, 323/760) = min(0.434, 0.425)
= 0.425`——**卡在高度**，宽度还有余量（0.434 > 0.425）。

单页模式如果只是把设计宽度从 1040 砍到单页的 500（`HTMLFlipBook` 的
`width={500} height={720}`），高度需求几乎不变（书内胆留白从 760 降到
720，只砍掉了封面/书脊那 40px 呼吸量），新缩放比 `= min(451/500, 323/720)
= min(0.902, 0.4486) = 0.4486`——**只从 0.425 涨到 0.449，+5.6%**，
不是「接近翻倍」。因为瓶颈从来不在宽度（两页摊开时宽度本来就没卡满），
单页与否根本碰不到宽度这个维度，自然救不了被高度卡住的缩放比。

**真正能撬动这个数字的，是页面内容自己要求的高度（720），不是外壳
chrome。** 把 `DESIGN_H` 从 760 砍到 720（去掉封面呼吸量，不用换单页
模式）就能拿到同样的 +5.6%，比换单页模式便宜得多——这说明"改单页"
本身没有专门的杠杆，真正值钱的是压缩 720 这个数字本身：`LeftPageContent`
/`RightPageContent` 内部的 `pt-12`（48px）、任务行 `h-[64px]`、装饰性网格
背景这些如果为小屏单独减重，把单页设计高度从 720 压到比如 450，缩放比
能到 `323/450 ≈ 0.72`——这才是量级对的改法，但代价是**这已经不是"调
参数"，是给小屏重新画一套更紧凑的页面内容**，即本文件原来说的"小屏
专用版式"，不是"单页 vs 摊开"这个选择本身。

**How to apply（订正后）：** 以后再评估"改单页/改摊开能不能救这个缩放比"，
先算清楚瓶颈是宽度还是高度（两页摊开时几乎总是高度，因为设计稿本身是
竖长条书页）——如果瓶颈是高度，单页/摊开的切换不影响结果，别再当成
候选方案提；该问的是"页面内容自己的设计高度能不能压缩"。

**订正之二（2026-08-28 第三轮评审）：** 上一条订正本身也漏了一步——
"压 720 这个数字"这句话默认了 `DESIGN_W`（两页摊开时=1040）按兵不动，
但只压高度、不压宽度，在两页摊开模式下**压不出订正之一算的那个
323/450≈0.72**。真实情况是 `scale = min(paperW/DESIGN_W, paperH/DESIGN_H)`
里的宽度项会先封顶：`451/1040 ≈ 0.434`——这是个跟 `DESIGN_H` 完全无关
的硬天花板，`DESIGN_H` 压到 744 以下之后，无论再怎么往下压，`min()`
拿到的都是这个 0.434（比今天的 0.425 只高 2%，16px 字从 6.8px 变
6.94px，等于没变）。0.72 那个数是**只有在单页模式**（`DESIGN_W` 也跟着
缩到单页自己的宽度，而不是两页+书脊的 1040）才拿得到的——订正之一算对
了"单页本身、高度不变时救不了"，但没算到"高度**也**大幅压缩之后，
单页和摊开就不再等价了"：高度压得越狠，宽度这个维度越可能反超变成
新瓶颈，而两页摊开的宽度需求（1040）比单页（~500）大一倍多，反超的
门槛也就低得多。

**真正不改变书的形状、只压信息密度的正确杠杆**：把 `DESIGN_W` 和
`DESIGN_H` **按同一个比例 k 一起收缩**（k<1），书的整体比例
`COVER_ASPECT = DESIGN_W/DESIGN_H` 和每页自己的比例都不变——书还是那本
书，只是画在了更小的画布上。这种收缩下 `scale = (1/k) × 当前 scale`
严格成立（两个分母同乘 k，`min()` 直接跟着变）。要把 0.425 拉到 0.68，
需要 `k = 0.425/0.68 ≈ 0.625`：`DESIGN_W` 1040→约650，`DESIGN_H`
760→约475，`HTMLFlipBook` 的单页 `width={500} height={720}` 也要跟着
收到约 325×450（这就是用户说的"内部尺寸压到设计高度约 450"里"450"这个
数字唯一站得住的算法路径——但前提是宽度必须同步收，光压高度不动宽度
拿不到这个数）。这意味着 `LeftPageContent`/`RightPageContent` 里**几乎
每一个数值**（padding、行高、图标尺寸、字号、gap）都要按约 62.5%
统一缩，不是挑三五个常量改一改，是重新画一版更紧凑的页面——跟订正
之一里"这已经不是调参数，是给小屏重新画一套版式"的结论一致，只是这次
把"能不能靠调参数救"的答案坐实到了具体数字上：**在两页摊开形式不变的
前提下，0.434 是硬顶，够不着 0.68**；0.68 只有换算法（整体等比例缩小
画布）才拿得到，且代价是要重画几乎全部内部数值。

**还有一个隐藏代价没人问过：这个改法不分屏幕大小。** `DESIGN_W`/
`DESIGN_H` 是模块级常量，不看断点。用户桌面窗口 1044×795 这一档现在
实测 `scale≈0.861`（接近但不到 1，读着正好）；如果为了小屏把画布整体
按 k≈0.625 收缩，大屏的 scale 会跟着从 0.861 涨到约 `0.861/0.625≈1.38`
——书会比现在**平白大出快 40%**，跟游戏里其他同级面板的视觉体量对不上，
而大屏根本没有这个问题、不需要被"顺便"改。要不出这个副作用，必须做成
按断点切换的两套画布常量（跟 `index.css` 里 `--modal-outer`/
`--modal-frame-w` 已经在用的 `@media (min-height: 460px)` 断点模式一样），
不能是一处全局改的常量——这比"调几个 padding"要大得多的一块工程量，
真正落地前应该先让用户/game-designer 拍板要不要做，而不是直接动手改。

**How to apply（订正之二）：** 以后被问"压高度能不能救缩放比"，先确认
问的是"只压高度"还是"高度宽度一起等比例压"——这两者结果天差地别
（前者卡在一个跟高度无关的宽度硬顶上，后者才是 `scale=(1/k)` 那条
线性关系）。给出目标 scale 时要顺手算一遍这套改法对**其他断点**的副作用
（多半是不分断点地全局生效，把"修小屏"变成"顺带改坏大屏"）。
