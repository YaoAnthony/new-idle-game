# 01 · 行动架构：动词表 + 技能注册表（零行为变化）

> 状态：**文档，待执行** · 2026-09-05 · 前置：00 改名完成
>
> 目标：把 `ResidentAgent`（原 `PetAgent`，1268 行）拆成三层——**身体 / 动词 / 技能**——
> 现有行为一个不改、一个不少。这是 02 的地基：02 只往 `skills/routine.ts` 里写新东西。
> 验收标准是"全量测试前后一致 + 浏览器里四种生物行为肉眼看不出区别"。

## 一句话

**一个基类 `Resident`，每种小动物一个子类**（用户定 2026-09-05）。基类提供身体：移动、说话、
需求、存档、动词执行、技能表。子类是一个文件，声明自己挂哪些**注册过的技能**、覆盖少数钩子
（登场、动画、专属动词参数）。水獭 = `class Otter extends Resident`，挂 `wander` + `trade`；
石傀儡 = `class Golem extends Resident`，挂 `build` + `wander`；三只 wisp 共用 `class Wisp`。
加一种新生物（会挖洞的鼹鼠）= 注册一个 `dig` 技能 + 一个 `class Mole extends Resident` 文件 + 注册表一行。

> 这条推翻了 `petAgent.ts` 文件头写的"实例化不继承"。那条规矩当年是为了防"每加一只就复制一份
> 状态机"——现在状态机在基类里、行为在注册技能里，子类只剩声明和钩子，那个风险不存在了。
> 执行 00/01 时把那段注释改掉，写上这次的理由。

子类**只允许**做三件事：声明技能表（`skills`）、覆盖钩子（`onSpawn` / `onDayStarted` / `animationFor(verb)`）、
给自己的技能传参数（比如石傀儡的 `build` 用 `ignoresObstacles`）。子类里出现 `startPathTo`、
`this.x =`、`if (hungry)` 就是把行为写回了子类，退回基类或技能。

## 三层

```
Resident（基类 · 身体）   位置 · 朝向 · 碰撞 · 寻路与走路 · 让路 · 需求衰减 · 心情 · 存档 · 技能表 · 动词执行
    ↑ extends
Slime / Fox / Spirit / Wisp / Shushu / Golem / Otter / FishTrader / Dragon（子类，各一文件）  声明技能 + 钩子
    ↑ perform(intent)
Actions（动词表）  walk_to · stand · sit · sleep · hide · show · gesture · work_at · speak
    ↑ Intent
Skills（技能）     needs · wander · approach · build · trade · （02）routine
```

三条硬规矩：

1. **技能只能说动词表里的词**。技能里出现 `this.x = ` / `startPathTo` / `registerObstacle` 就是违规。
2. **基类不认识任何具体身份或技能**。`Resident` 里不得出现 `if (role === Worker)`、`trySeekSite`、`Golem` 这类字样。它只知道"有一张技能表，闲下来问一圈"。子类和技能都由工厂按 `definitionId` 查表装配。
3. **动词是唯一的外部入口**。指令 `/npc <谁> do <动词>` 和技能算出来的 Intent 走同一个 `perform`。如果指令要另开一条路才能让他动，说明动词没封装好。

## 动词表（第一版，用户 2026-09-05 定）

| 动词 | 参数 | 到达 / 完成条件 | 现在对应的代码 | 动画钩子（以后换） |
|---|---|---|---|---|
| `walk_to` | `{x, z, speedScale?}` | 路径走完；走不到 → 失败回调 | `startPathTo` + `tickMove` | 走路摆动（现在是程序化） |
| `stand` | `{seconds?, facing?}` | 计时到 | `idle` 状态 + `idleTimer` | 待机呼吸 |
| `sit` | `{anchorRef}` | 坐下即完成；由下一个 Intent 打断 | **新**：复用玩家的 `restOn` 那套锚点（`Systems/resting.ts` 的 `findFreeAnchorNear`），Resident 不写第二套 | 坐姿 |
| `sleep` | `{seconds}` | 计时到，或被打断 | `fallAsleep` / `wakeUp` | 睡姿 + 代谢放缓 |
| `hide` / `show` | — | 立即 | `hidden` 状态 + `removeCreatureObstacle` / `registerObstacle` | 淡出 / 淡入 |
| `gesture` | `{gestureId}` | 立即（表现层自己播完） | `emit("resident_gesture")` | 现有通道 |
| `work_at` | `{instanceId}` | 工地完工，或被打断（打断 → `releaseSite`） | `beginWork` / `tickWork` | 敲打 |
| `speak` | `{localizationKey, seconds}` | 计时到 | **新**：头顶气泡（复用 `Components/Bubble`） | — |

**`walk_to` 要留"路好走"的口**（用户 2026-09-05）：以后铺了小路，居民要**更愿意走路上**。
现在 `findRoute` 是格子可走 / 不可走的二值 A*，没有代价层。这期不做小路，但动词的实现要走
`findRoute(from, to, { costOf?: (cell) => number })` 这个签名——代价从地面类型推
（`GroundMap` 的地表 kind：小路 1、草地 1.6、泥 2.2，数字住 Core 数据），不给就全 1，和今天完全一致。
A* 的 g 值乘 `costOf` 是 `Core/logic/pathfinding.ts` 里几行的事，01 顺手把参数打通、默认全 1，
铺路那期只需要往地表表里填数。玩家自己走路**不受**代价影响（玩家是手操的）。

后续任务只加两个动词：`knock`（07，敲门等开）、`invite`（06，请另一位换 Intent，对方可拒）。
**之后动词表封口**——活动、节日、剧情全用组合。完整表见 [引擎扩展清单](引擎扩展清单.md)。

吃和喝**不进动词表**：它们是 `walk_to` + 到达回调（扣掉地上的东西 / 回饱食）+ `stand(进食时长)`。今天的 `eat` / `drink` 状态拆成这三段，行为相同，表现层看的 `state` 字段用 `stand` 的一个 `flavor` 标签（`eating` / `drinking`）保住原动画。

## Intent 与打断

```ts
type Intent = {
  skillId: SkillId;           // 谁下的。/npc do 下的是 "command"
  priority: number;           // 抢占用。command = PRIORITY.command（1000，数据表里的常数，不用 Infinity——它进不了 JSON）
  steps: ActionStep[];        // 顺序执行的动词序列，例：[walk_to 椅子, sit]
  onArrive?: (agent) => void; // 到达最后一个 walk_to 时改世界的部分（认领工地、吃掉东西）
  onInterrupted?: (agent) => void;  // 被抢时的收尾（释放工地、站起来）
  interruptible: boolean;     // false = 只有指令能打断
};

/**
 * 能上网线的那一半：`steps` 里的目标必须是**已经解析好的**坐标 / 实例 id / 锚点 ref，
 * 不能是"最近的椅子"这种要在对端重新搜索的描述——两端搜出来的椅子可能不是同一把。
 * 回调不上网线（房客不改世界），所以 `WireIntent = Omit<Intent, "onArrive" | "onInterrupted">`。
 * 技能产出 Intent 时就按这个约束写，联机那节直接复用，不做第二种形状。
 */
type WireIntent = Omit<Intent, "onArrive" | "onInterrupted">;
```

**打断规则**（用户定：允许打断）：

- 每次 tick 结束时，身体问一圈技能 `decide`；有技能给出 Intent 且 `priority > 当前.priority` 且 `当前.interruptible` → 调 `onInterrupted`，换上新的。
- 指令下达的 Intent `priority = Infinity`、`skillId = "command"`，**立即生效**、无视 `interruptible`（用户定）。指令 Intent 完成后身体回到"问一圈"。
- 为了不让技能每帧抢来抢去，`decide` 的调用节流到每 0.5 秒一次；同一技能连续两次算出同一目标不算新 Intent。

优先级表（数据，`Core/src/Data/residents/skills.ts`）。下面只列 01 搬的几个，**全表在 [引擎扩展清单](引擎扩展清单.md)**，后续任务加技能往那张表登记：

| 技能 | 优先级 | 可被打断 |
|---|---|---|
| `command` | 1000 | 否 |
| `build` | 80 | 是（释放工地） |
| `needs` | 60 | 否（吃到一半不该被叫走） |
| `routine`（02） | 40 | 是 |
| `approach` | 20 | 是 |
| `wander` | 10 | 是 |

## 技能接口

```ts
type Skill = {
  id: SkillId;
  /** 闲下来 / 每 0.5s 被问一次。null = 现在不想干什么 */
  decide?(ctx: SkillContext): Intent | null;
  /** 玩家按 F 时开什么。不填 = 走定义里的 dialogues */
  interact?: (ctx: SkillContext) => { kind: "dialogue"; dialogueId: string } | { kind: "trade" } | null;
  /** 事件驱动的技能（03 的 reactions）：订阅 EventBus，命中就下并行槽动词。没有 decide 也行 */
  onEvent?: (ctx: SkillContext, event: { kind: string; payload: unknown }) => void;
};

type SkillContext = {
  agent: ResidentAgentView;       // 只读视图：位置、needs、mood、home、role、definition
  player: { x: number; z: number };
  clock: ClockReading;            // getClock()
  weather: WeatherDefinition;     // getWeather()
  world: WorldQueries;            // 只读：listSites / listDroppedItems / findFreeAnchorNear / isWalkable …
};
```

`SkillContext.world` 是**只读查询**。改世界的动作只在 `Intent.onArrive` / `onInterrupted` 里做，而且调的是既有系统函数（`claimSite`、`removeDroppedItem`），不是技能自己改数组。

注册：`Frontend-3D/src/Game/State/skills/index.ts` 导出 `skillRegistry: Map<SkillId, Skill>`。
**谁挂什么写在子类上**（`static skills: SkillId[]`），不写在 Core 定义里——Core 不知道技能的实现，
而子类本来就是"这只动物是什么"的唯一答案。工厂 `Frontend-3D/src/Game/State/residents/index.ts`
维护 `definitionId → 子类` 的表（`slime_neighbor → Slime`，三只 wisp → `Wisp`），`spawnResident` 走工厂 `new`。
表里没有的 definitionId 用基类兜底（挂 `[needs, approach, wander]`），加新动物忘了登记时它还能站着走路，
content 测试报"没有对应子类"。

## 联机：房主权威，房客是木偶

### 现状（这是一个已经存在的 bug）

`WorldRefreshSlices` 里**没有 `pets` 这一片**（协议 v7 的九片：家具、掉落物、库存、天气、时钟、唱片机、灯、建筑、进度）。
房客进场时 hydrate 拿到房主整份世界（含活物位置）一次，之后 `RoomScene.update` 里 `tickPets` **不看
`isRemoteWorldActive`**，两端各跑各的状态机、各掷各的骰子。结论：今天做客时，A 看见史莱姆在北边、
B 看见它在南边，是必然，不是偶然。任何"居民更活"的工作只会放大这条分叉。所以联机模型是 01 的一部分，不是以后的事。

### 三种做法对照

| 做法 | 谁在用 | 对我们 |
|---|---|---|
| **确定性锁步**：同一种子、同一时钟，两端各自算，指望结果一致 | RTS（星际、帝国） | 否。浮点、帧率、`Math.random`、玩家位置（`approach` 读它）任一处不同就永久分叉，而且分叉了无法收敛 |
| **全量状态流**：房主每帧 / 12.5Hz 推每只的位置朝向，房客只画 | 玩家自己的 `sync:transform` 就是这条 | 能用但浪费：9 只 × 12.5Hz 一直发，而且房客端不知道"他在坐着"，动画对不上 |
| **意图复制 + 关键帧纠偏**：房主把 Intent（动词序列 + 解析好的目标）发一次，房客用同一套动词自己走；低频关键帧兜底纠偏 | MMO 的"move to" 复制 + Source 引擎的快照插值；《动森》做客时村民行为由岛主机决定 | **选这个**。动词表恰好是这条路要求的"两端共享的执行语义"——01 把行为收成动词，联机就顺手成了 |

### 规则

1. **权威 = 不在做客**（`!isRemoteWorldActive()`）。房主端：技能照常 `decide`。房客端：`Resident` 进**木偶模式**——技能表为空、需求不衰减、不发任何剧情信号、不掷骰子；只执行网线送来的 Intent 和关键帧。
2. **Intent 复制**：房主端每次换上新 Intent（含 `command`）→ `sendWorldOp({ kind: "resident_intent", residentId, intent: WireIntent, atMs })`。房客 `perform` 它，优先级当 `command` 处理（木偶没有别的来源，不存在抢占）。
3. **关键帧纠偏**：新增 host→all 的流事件 `sync:residents`，**2 Hz、只发有变化的**：`{ atMs, residents: [{ id, x, z, heading, verb, flavor, hidden, expression?, speaking?, heldProp? }] }`（后三项分别由 03 / 06 / 12 用到，**一次定全**，免得协议号加三次）。房客：偏差 < 0.6 m 忽略；0.6~3 m 用 0.3 s 插过去；> 3 m 直接放；`verb` 不一致就切。这是走路分叉（两端寻路格子略有差异）的兜底。
4. **生灭与整体对账走刷新切片**：`WorldRefreshSlices` 加 `pets`（形状同 `WorldSave.pets`，名字跟存档字段一致），`WORLD_REFRESH_KEYS` 加一项（编译期断言会逼着加）。房客收到整片 → 对账：多出来的 id 造木偶、少了的移除、已有的只校位置。居民到来、去小镇、水獭来去全靠这一片，不另发 op。
5. **房客的交互**：按 F 对话照开（对话是本地演出，做客时剧情系统本来就闭嘴）；交易面板照旧被挡；**送礼被挡**（改的是房主家活物的好感，走 `guardWorldMutation` 那条提示）；`/npc <谁> do …` 在做客时拒绝："做客中不能指挥别人的邻居"。
6. **随机只在房主**。`hashSeed` 那套确定性抽签仍然只在房主端跑，房客不需要种子。
7. **回家**（退出做客）：hydrate 自己的存档 → 全部 `Resident` 退出木偶模式、技能表按子类装回。

### Backend 与契约

- `NET_PROTOCOL_VERSION` +1。
- 新 op kind `resident_intent`、新流事件 `sync:residents`（服务端只接受房主发的，房客发的丢弃——和 `world:refresh` 同一条规矩）。
- **顺手修一个同类隐患**：Backend `validate.ts` 里的 `OP_KINDS` 是一份手抄的字面量集合，和 `WorldOp` 类型各写各的——这正是 `WORLD_REFRESH_KEYS` 在 2026-08-23 走散过的那种 bug（加了 lamps 没加白名单，整条刷新被静默打回）。这次把 `WORLD_OP_KINDS` 搬进 `Core/src/types/net.ts`，用同一招编译期断言钉住，Backend 从 Core 读。否则 `resident_intent` 就是下一个被静默丢掉的 op。
- `contracts/` 里补一段"活物同步"的人读说明。

### 联机验收

- `tests/residentSync.test.ts`（照 `netSession.test` 的假 Api 模式，不碰真网络）：
  - 房主端史莱姆换上一个 `walk_to` Intent → 出站里有一条 `resident_intent`，`steps` 里的目标是坐标不是描述。
  - 房客端灌入同一条 → 木偶开始 `walk_to`；**`decide` 从未被调用**（spy 计数为 0）；需求值 60 秒后不变。
  - 灌入关键帧：偏 0.4 m 不动；偏 2 m 在 0.3 s 内到位；偏 5 m 立即到位；`verb: "sit"` 而本地在走 → 切到 `sit`。
  - 灌入 `pets` 切片：新 id → 出现木偶；缺 id → 被移除；这两者都不发 `resident_spawned` 剧情信号。
  - 做客时 `runCommand("/npc slime do sit")` 返回 ok=false 且文案含"做客"。
  - `exitRemoteWorld` 后 `decide` 恢复被调用。
- Backend `tests/multiplayer.test.ts` 加三条：`resident_intent` 在白名单内且双向转发；`sync:residents` 房主发的广播到房客、房客发的被丢；超 64 KB 的 op 被拒。
- **浏览器双端**（这是用户点名的那条："我可不想一个小动物 A 看在北边，B 看在南边"）：同一台机器开两个标签页，一个 `/host` 一个 `/join`，两边都 `window.__scene.debugTeleport` 到同一视角。
  1. 房主 `/npc slime do walk_to 20 20` → 5 秒后两边 `/npc slime where` 位置差 < 0.5 m，两边截图里史莱姆在同一格。
  2. 房主 `/npc slime do sit` → 房客那边史莱姆坐在**同一把**椅子上。
  3. 房主 `/npc slime do hide` → 房客那边消失、碰撞体摘掉（房客走过去不被挡）。
  4. 房客 `/npc slime do sit` → 被拒，房主那边无事发生。
  5. 房客离开再回来 → 史莱姆在房主当前位置，不是进场时的老位置。
  6. 两边各挂 60 秒不操作 → 位置差始终 < 0.5 m（关键帧在兜底）。

## 指令（挂在 `/npc` 下，`Systems/residents/commands.ts`）

| 指令 | 干什么 |
|---|---|
| `/npc <谁> do walk_to <格X> <格Y>` | 走到院子格。到不了报"走不到" |
| `/npc <谁> do sit` | 找最近的空座坐下；没有报"附近没座" |
| `/npc <谁> do sleep [秒]` / `stand [秒]` / `hide` / `show` / `gesture <id>` / `speak <文案键>` | 对应动词 |
| `/npc <谁> skill <id> on\|off` | 开关技能（运行时，不进存档）。关掉全部 = 只听指令，调动画时用 |
| `/npc <谁> skills` | 挂了哪些、哪个在决策、当前 Intent 的优先级 |
| `/npc <谁> where` | 位置、当前动词、剩余时长、Intent 来自哪个技能 |

`<谁>` 接受简称（`slime` / `golem` / `otter`）和运行时 id（`pet-slime`）。石傀儡和水獭也是 Resident，同样能点名。

## 最容易写错的四处

1. **搬的时候顺手"修"行为。** 这一步的价值就是零变化。看见奇怪的常量（`idleTimer = 3 + Math.random() * 5`）照抄，想改的记到 02 的"待定"里。
2. **技能里偷读身体私有字段。** `SkillContext.agent` 是只读视图类型，不是 `ResidentAgent` 本身。TS 的 `private` 只是编译期，用一个明确的 view 类型挡住。
3. **`needs` 不可打断但 `walk_to` 那一段可以。** 走向食物的路上被更高优先级抢走是合理的，吃到一半不行。`interruptible` 要按 step 判，不是按 Intent 一刀切——实现上 Intent 的 `interruptible` 在进入最后一个 step 时翻成 false。
4. **`hide` 要摘碰撞体。** 现在 `hidden` 状态是否摘了障碍要查；居民回家（02）会大量用它，隐身还挡路就是"撞到一团空气"那个老坑。
