# 期 2 · 行动开箱

> 状态：**已完成** · 2026-08-24 · 见文末收工记录 · 前置：期 1（要 `value` 和 `origin`）· 总纲见 `00-总纲.md`

## 一句话

行动的奖励从「四组写死的物品清单」换成**开箱抽一件家具**——投入越大，
开出的东西越好。这是玩家在这套改造里**第一次看到变化**的一期。

## 拍板过的

| # | 决策 | 出处 |
|---|---|---|
| 1 | 行动**只产出家具**，不产出材料和食材 | 用户 |
| 2 | 每日任务**只产出金币** | 用户 |
| — | 家具**是货不是收藏**，重复无所谓——不用先补内容 | 用户 2026-08-24 |
| 28 | 行动带回的标 `Real`、工作台造的标 `Otherworld` | 我提，用户点头（"工作台先不退场"） |
| 7 | **饱食系统整个不动** | 用户 2026-08-24 |
| 27 | 吃饱加成**缓到厨房重做那一版**（用户想做成 Overcooked 那样） | 用户 2026-08-24 |

## 这一期最大的运气：抽箱机器整套是现成的

系列任务（`actionChains`）那条线两个月前就把开箱做完了，而且**算法在 Core、
纯函数、随机数注入**。行动开箱要的东西一件都不用新写：

| 要的 | 现成的 | 在哪 |
|---|---|---|
| 投入分 → 稀有度 | `rollChestRarity(score, rand)` | `Core/logic/actionChains.ts` |
| 分档权重表 | `chestWeightTable`（四行，minScore 0/8/20/40） | `Core/Data/actionChains/index.ts` |
| 投入分公式 | `nodeChestScore(minutes) = minutes / 15` | 同上 |
| 稀有度 → 具体哪一件 | `pickChestFurniture(rarity, pool, owned, rand)`，**优先抽没有的**、该档空了**降一档** | `Core/logic/actionChains.ts` |
| 候选池 | `buildCandidatePool()`：所有带 `placement` 的、排除唱片和场景道具 | `Frontend/Systems/actionChains.ts`（已 export） |
| 拥有数 | `ownedCountFn()`：背包 + 摆放 + 储物三处 | 同上（已 export） |
| 开箱演出 | `emit("action_chest_ready", {...})` + `RewardPanel` | 同上 |

**所以这一期的本质是接线，不是造轮子。** 真正要想清楚的只有三件事：
重要级怎么进投入分、休息怎么办、每日任务那颗番茄怎么退场。

## 现状盘点

### 现在的行动奖励长什么样

`Core/Data/actions/index.ts`：

| 行动 | 现在给什么 | 时长上限 | 疲劳 |
|---|---|---|---|
| 写作业 | 2 木头 + 1 鸡蛋 | 480 分 | 18 |
| 运动 | 1 铁锭 + 1 番茄 | 240 分 | 25 |
| 创作 | 3 纸 + 1 石墨 | 300 分 | 15 |
| 休息 | 1 根茎 | 180 分 | **−30**（回疲劳） |

重要级（低/普通/重要）按 `rewardMultiplier`（1 / 2 / 3）放大数量，
`fatigueMultiplier`（0.6 / 1 / 1.6）放大消耗。

**注意一件反直觉的事**：现在的奖励**完全不看时长**。做 1 分钟和做 8 小时
拿到的一模一样。这是这一期顺带修掉的最大的一处失衡——开箱的投入分
`minutes / 15` 天然按时长走。

### 家具池的真实规模

| 稀有度 | 可摆放的家具件数 |
|---|---|
| 普通 | 32 |
| 优良 | 8 |
| 稀有 | 4 |
| 珍贵 / 传说 / 神话 | **0** |

`chestWeightTable` 只给了前三档权重（注释里明说高三档"候选池也还是空的"）。
一周做 30 次行动会把池子抽遍——**用户 2026-08-24 定：家具是货，重复无所谓**，
所以这一期不补内容。玩家开出重复的椅子就是拿去卖的货。

## 五件事

### 2-1 · 行动奖励换成开箱

#### Core：`ActionDefinition.rewards` 的语义变了

不删这个字段（`RewardDefinition[]` 还有 `gold` / `unlock` 两种形状要留着），
改成**空数组 = 走开箱**：

```ts
  /**
   * 完成后给什么。
   *
   * **空数组 = 走开箱**（2026-08-24）：按时长 × 重要级算投入分，
   * 抽一件家具。这是绝大多数行动的形态——"现实里做完一件事"换来的
   * 是那边世界的一件东西，而不是一把定量的木头。
   *
   * 写了内容就照写的发，不抽。留这条路是给**特殊行动**用的
   * （以后的剧情任务、教程步骤），也是给测试用的——用例要能钉住
   * "发的就是这一件"，而不是每次都掷点。
   *
   * 和 `ActionChainNode.rewards` 是同一套语义（那边是"完成那一刻
   * 抽出来写进去，之后不再变"），两处共用 `grantChest`。
   */
  rewards: RewardDefinition[];
```

四条行动定义改成：

```ts
  {
    id: "work_study",
    localizationKey: "action.work_study",
    category: ActionCategory.WorkStudy,
    requiredFurnitureCapabilities: [FurnitureCapability.Study],
    durationMinutes: { min: 1, max: 480 },
    fatigueCost: 18,
    // 空 = 开箱。原来写死的「2 木头 + 1 鸡蛋」不看时长，
    // 做 1 分钟和做 8 小时拿到的一模一样——那是这次一并修掉的失衡
    rewards: [],
    audioProfileId: "sfx_action_writing",
  },
```

运动、创作同理。**休息是例外，见 2-2。**

#### Frontend：结算处调 `grantChest`

`Systems/actionChains.ts` 的 `grantChest` 已经是通用的（收一个
`{ rewards: RewardDefinition[] }`，空就抽、非空就照发）。把它 export 出来，
`Systems/actions.ts` 的 `finishAction` 里：

```ts
  if (completed && definition) {
    // 重要级放大收益（代价已经在开始时按同一个重要级扣过精力了）
    const multiplier =
      findActionPriority(active.priority)?.rewardMultiplier ?? 1;

    for (const reward of definition.rewards) {
      if (reward.type !== "item") continue;
      const quantity = Math.max(1, Math.round(reward.quantity * multiplier));
      addItem(reward.itemId, quantity);
      rewards.push({ itemId: reward.itemId, quantity });
    }
  }
```

改成：

```ts
  if (completed && definition) {
    /*
     * **开箱不是"发东西 × 倍率"**，是"投入分 → 稀有度 → 抽一件"。
     *
     * 重要级因此不再乘在数量上（那会变成"标重要就开三个箱"），
     * 而是乘进**投入分**——标得越重要，同样的时长开出的东西越好。
     * 这保住了 actionPriorityDefinitions 那段注释的意图（代价和回报
     * 同向缩放、取舍是真的），只是"回报"从件数变成了品质。
     *
     * 写了 rewards 的行动照发不抽（特殊行动 / 测试用），
     * 那条路仍然吃 rewardMultiplier——它对定量奖励仍然是对的。
     */
    if (definition.rewards.length === 0) {
      const minutes = active.durationMs / 60000;
      const priorityMultiplier =
        findActionPriority(active.priority)?.rewardMultiplier ?? 1;
      const score = nodeChestScore(minutes) * priorityMultiplier;

      const box = { rewards: [] as RewardDefinition[] };
      const chest = grantChest(box, score);
      rewards.push(...chest.items);
      emit("action_chest_ready", {
        size: "node",
        title: active.customName,
        rarity: chest.rarity,
        items: chest.items,
      });
    } else {
      const multiplier =
        findActionPriority(active.priority)?.rewardMultiplier ?? 1;
      for (const reward of definition.rewards) {
        if (reward.type !== "item") continue;
        const quantity = Math.max(1, Math.round(reward.quantity * multiplier));
        addItem(reward.itemId, quantity);
        rewards.push({ itemId: reward.itemId, quantity });
      }
    }
  }
```

> `action_chest_ready` 的载荷现在有 `chainId` / `nodeId` / `iconId` /
> `colorId` 四个链专属字段。行动开箱没有链，要把它们改成可选——
> 动 `EventBus.ts` 那一行，`RewardPanel` 那边加缺省。

#### 投入分对照（`chestWeightTable` 的四档）

score = 分钟 / 15 × 重要级倍率（1 / 2 / 3）

| 时长 | 低 | 普通 | 重要 | 落在哪档 |
|---|---|---|---|---|
| 15 分 | 1.0 | 2.0 | 3.0 | 第一档（80/18/2） |
| 1 小时 | 4.0 | 8.0 | 12.0 | 普通起进第二档（60/32/8） |
| 2 小时 | 8.0 | 16.0 | 24.0 | 重要进第三档（40/42/18） |
| 4 小时 | 16.0 | 32.0 | 48.0 | 重要进第四档（22/48/30） |
| 8 小时 | 32.0 | 64.0 | 96.0 | 第四档封顶 |

这张表**不用改**——`SCORE_DIVISOR_MINUTES = 15` 那段注释写的判据
（"随手一个 25 分钟的小节点落在 1~2 分""两小时硬活到第二行"）对行动
同样成立，因为链节点本来就是拿去跑行动的。

### 2-2 · 休息不掉东西

```ts
  {
    // 休息是唯一**回**疲劳的行动（fatigueCost 为负），
    // 所以疲劳见底时它永远做得了——不会把玩家锁死
    id: "rest",
    localizationKey: "action.rest",
    category: ActionCategory.Rest,
    requiredFurnitureCapabilities: [FurnitureCapability.Rest],
    durationMinutes: { min: 1, max: 180 },
    fatigueCost: -30,
    /*
     * **休息不掉东西**（2026-08-24）。
     *
     * 别的行动开箱说得通——你在现实里做完一件事，那边世界回你一件东西。
     * 躺一会儿开出一张沙发说不通，而且它会立刻变成最优刷法：休息不耗
     * 精力（还回精力），时长上限 180 分，白开箱等于无限刷货。
     *
     * 它的回报本来就是**疲劳本身**——`fatigueCost: -30` 就是它的奖励。
     * 空数组在这里不能用（空 = 开箱），所以显式留一条注释说明它是
     * "既不抽也不发"的第三种：见下面 finishAction 里的 restNoReward 判据。
     */
    rewards: [],
    noChest: true,
  },
```

`ActionDefinition` 加字段：

```ts
  /**
   * **不开箱**。`rewards` 空数组的默认含义是"走开箱"，这个标志把它
   * 改回"什么都不给"。
   *
   * 今天只有休息用。做成标志而不是"用一个特殊的 rewards 值"表达，
   * 是因为那种约定（比如 `rewards: null`）读的人得先知道约定；
   * 一个叫 noChest 的布尔不用解释。
   */
  noChest?: boolean;
```

`finishAction` 的判据变成 `if (definition.rewards.length === 0 && !definition.noChest)`。

| origin | 哪些 | 判据 |

**说法**（他没货源）和**定价依据**（Real 贵）。开箱池仍是

## 最容易写错的四处

### 一 · 重要级不能乘在件数上

乘件数 = "标重要就开三个箱"，那是纯收益，重要级标签当场退化成一次
无意义的点击（`actionPriorityDefinitions` 的注释专门讲过这件事）。
乘进**投入分**才保住取舍：标得越重要越累、当天能做的件数越少、
但开出的东西越好。

### 二 · 休息必须显式关掉开箱

`rewards: []` 的默认含义变成了"开箱"，所以**什么都不改的话休息会开始
掉家具**——而且它是全游戏唯一不耗精力的行动，180 分钟上限，
立刻成为最优刷法。`noChest` 那个标志不是洁癖，是拦这个的。

### 三 · `action_chest_ready` 的链专属字段要变可选

现在的载荷带 `chainId` / `nodeId` / `iconId` / `colorId`。行动开箱没有链，
硬塞空串的话 `RewardPanel` 会去查一条不存在的链。改成可选 + 面板缺省，
比造一条假链干净。

### 四 · 别趁机"顺手"给高三档补内容

珍贵 / 传说 / 神话现在是**空池**，而 `pickChestFurniture` 遇到空池会
**降一档重抽**——所以即使 `chestWeightTable` 哪天加了高档权重，
今天也不会开出空箱。用户已经定了"家具是货，重复无所谓，期 2 不补内容"。
补内容是独立一笔，不挡这条链。

### 撞出来的三件事

1. **一个真 bug，用例抓的**：开箱事件里读 `active.customName`，而它在
   `setActive(null)` **之后**才发——运行时抛
   `Cannot read properties of null (reading 'customName')`。
   改成在清空前把标题抓走。**浏览器那条路测不到它**（休息不开箱，
   走不到那一行），是 Frontend 用例逼出来的。

2. **`typecheck:tests` 又抓到一处恒空检查**（和期 1 的 Quest 同一类）：
   四条行动的 rewards 全空之后，`satisfies` 保留的字面量类型把循环元素
   收成了 `never`，`content.test.ts` 里那条"奖励物品存在"的检查编不过。
   **保留了那条检查**（特殊行动那条路没废，剧情任务仍会写死奖励），
   显式标注 `as RewardDefinition[]` 并把"为什么它今天看起来是空转"写进注释。

3. **浏览器里摆家具比想象中绕**：`testroom` 一次只塞得下 10 件，塞不进
   书桌/哑铃/画架，于是 `/act` 的三条非休息行动在实机上起不来。
   开箱回路的决定性验证因此放进 Frontend 用例（`replayPlaceFurniture`
   直接摆，跳过占用校验——那条路本来就是给"对方已经校过"准备的）。
   **浏览器留给它擅长的**：分布统计和结算查看。

### 顺手加的三条指令

| 指令 | 用途 |
|---|---|
| `/act <分类> <秒> [重要级] [名字]` | 起一条**独立**行动（不走链）。秒数很短就能当场看开箱 |
| `/lastact` | 打印上一条行动的结算：开出什么、有没有陪伴 |
| `/chest <分钟> [重要级] [次数]` | **只掷点不入包**，抽 N 次看档位分布。不入包是刻意的——抽 200 次真发 200 件会把背包塞爆，而且污染 `ownedCount`（开箱优先抽没有的），分布就不真了 |

### ⚠️ 留给期 3 的一件事：五种材料现在断供了

还能拆成木头——那给"重复"第二个用途，而且和"家具是货"这条定位同向。
