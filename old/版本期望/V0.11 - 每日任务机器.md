# 每日任务机器

一件可放置的家具。玩家把自己现实里想做的事写进去，机器每天从中抽 4 条当"今日任务"；
做完打勾，屋里的进度条推进，凑满机器吐出奖励。

**联机时进度条是共享的**：两个人各打一个勾就是 2/4，人多凑得快。

---

## 一、已定的决策（2026-08-04）

| 决策 | 选择 | 后果 |
|---|---|---|
| 任务内容 | **自由文本，手动打勾** | 游戏不判定"你有没有真的写完作业"。这是自律工具不是成就系统 |
| 任务池归属 | **个人**（跟着玩家走） | 每人抽自己的 4 条，看到的清单各不相同 |
| 进度条归属 | **共享**（属于这个家） | 分母恒为 4，不随人数变；谁打的勾都算 |
| 奖励发放 | **吐到地上，每个在场的人各一份** | 复用现有掉落物系统，联机天然同步 |
| 奖励内容 | **注册表里的一张清单**，当前只有一颗番茄 | 调平衡时改数据不改代码 |
| 多台机器 | **全家共享一份进度** | 进度存 `WorldSave` 顶层，机器只是显示器和出口 |
| 重抽 | **每天一次**，换掉其中一条 | 下雨天抽到"跑三公里"有出路，又不至于换到全是最简单的 |
| 获得途径 | **剧情解锁**（本轮先留挂点），命令行可提前拿 | 本轮用 `/give` 测试，剧情内容以后写 |
| **惩罚** | **完全没有**（见 §2） | 不掉血、不掉级、不断连续记录、不记名 |

## 二、设计原则：不惩罚（有依据的选择）

这个玩法最容易被抄错的地方，是照搬 Habitica 的惩罚层。**明确不抄。**

Habitica 的做法是：漏做每日任务掉 HP，HP 归零掉级、掉金币、掉装备；组队时
**队友漏做你也跟着掉血**。看起来是最有效的问责机制，实际数据是：

| 现象 | 数据 |
|---|---|
| 惩罚反噬 | 丢掉 2–3 天连续记录的用户只有 **0.90%** 会回来重开；4–7 天的 1.42% |
| 新鲜感消退 | 游戏化 app 前两周参与度 +41%，**第四周 67% 流失**（Stanford Persuasive Tech Lab） |
| 反生产效应 | 学术研究结论：受访者普遍在**特别忙、特别有产出的日子**被惩罚——因为忙到没空打勾 |
| 社交压力变焦虑 | 队友因自己掉血，对本就自我苛责的人是**放大自责**，不是健康问责 |

来源：[Habitica 游戏化案例分析](https://trophy.so/blog/habitica-gamification-case-study)、
[Party 机制](https://habitica.fandom.com/wiki/Party)、
[Counterproductive effects of gamification（ScienceDirect）](https://www.sciencedirect.com/science/article/abs/pii/S1071581918305135)

推论（三条，直接约束下面的设计）：

1. **共享进度条只做正向贡献，绝不连坐。** 别人不打勾，你的进度不减；
   进度条**不记名**（不显示哪一格是谁打的）。记名等于把没打勾的人钉在墙上，
   正是"社交压力变焦虑"的来源。
2. **没有连续记录（streak）。** 一旦引入 streak，就引入了"断掉"，
   而那 0.90% 说明断掉之后人就不回来了。今天没做完，明天照常抽新的 4 条。
3. **真正的敌人是第四周，不是"玩家会偷懒"。** 见 §4.1 抽签那一节。

### 为什么"手动打勾"是自洽的

项目里已经有一套会自动判定的东西：**行动系统**（`PlayerActionEntry`）——写"专注 25 分钟"，
按开始，真实时间走完自动结算。那套管**在游戏里坐下来做的事**。

每日任务管的是另一半：**游戏管不到的事**。"喝八杯水""给妈妈打电话""跑三公里"——
没有任何信号能判定，也不该假装能。玩家自己按下那个勾就是这个玩法的全部仪式。

因此**没有防作弊，而且是刻意的**：能骗过它的唯一受害者是玩家自己
（Habitica、Forest 全是这个路子）。联机时同理——朋友帮你点满，你们俩心里都清楚
那颗番茄是怎么来的。

### 为什么分母恒为 4

"两个人各做一个任务，算完成两次"（原话）。分母若随人数涨（4×人数），
两个人各做一个只是 2/8，比单人还慢，和这句话正好相反。

副作用是**人越多越快**，这是想要的。Habitica 的 Boss 战也是这个数学：
"人多的队伍伤害叠加，Boss 战很少超过几天"。它奖励的是"一起过日子"，不是"多人多劳"。

## 三、数据模型

### 3.1 任务池与今日抽签 → `PlayerSave`（跟着玩家走）

```ts
/** 玩家写的一条待办。纯文本，游戏不理解它的含义 */
export type DailyTaskTemplate = {
  taskId: string;        // 本地生成，稳定不变（改文案不换 id）
  text: string;          // "喝八杯水"
  createdAtUtc: UtcTimestamp;
};

/** 今天抽中的一条 */
export type DailyTaskDraw = {
  taskId: string;        // 指回模板
  text: string;          // 抽签那一刻的文案快照（见下）
  done: boolean;
};

export type DailyTasksSave = {
  pool: DailyTaskTemplate[];
  /** 今日抽签结果。worldDayId 变了就作废重抽 */
  today?: {
    worldDayId: WorldDayId;
    draws: DailyTaskDraw[];
    /** 今天的那一次重抽用掉了没有（见 §4.2） */
    rerollUsed?: boolean;
  };
};
```

挂在 `PlayerSave.dailyTasks`。

**`text` 在抽签时快照一份**，不是每次回 pool 里查：玩家中途改了文案（或删了那条模板），
今天已经抽出来的任务不该跟着变或凭空消失——"今天要做的事"定了就是定了。

**不复用 `PlayerSave.missions.daily`**（`MissionInstance[]`）。那个类型是给
"系统派发的、有 missionId 的任务"设计的，`status: active|completed|claimed` 是三态领奖流程。
这里是玩家自写的自由文本、两态、不单独领奖。硬套会得到一个两边都不像的类型。
那个空壳留给将来真正的系统任务。

### 3.2 进度与领奖 → `WorldSave` 顶层（属于这个家）

```ts
// WorldSave 新增
dailyBoard?: {
  worldDayId: WorldDayId;   // 这份进度属于哪一天
  progress: number;         // 0..taskCount，谁打勾都加
  claimed: boolean;         // 今天吐过奖励没有
};
```

**放世界顶层而不是家具实例上**，是为了让"多台机器"这件事自己解释自己：
进度属于**这个家的今天**，机器只是它的显示器和出口。摆第二台不会多一份奖励，
因为它显示的是同一份进度——不需要一条"禁止摆两台"的规则，玩家摆了自然就明白。

代价是它和 `slotContents` 那类"家具自己的状态"不同构：机器被收走时进度不跟着走。
这是对的——**今天做了几件事是这个家的事实，不是那台机器的**。全部收走再摆回来，
进度照旧（当天）。

`worldDayId` 存在这里是为了**惰性重置**：不需要后台定时器，也不怕玩家离线跨天——
任何人读这块状态时发现日期对不上，当场归零。跨了三天没上线也只是一次归零。

### 3.3 玩法参数 → Core 注册表（不是代码里的常量）

```ts
// Core/src/Data/dailyTasks/index.ts
export const dailyBoardDefinition = {
  /** 每天抽几条。分母也是它 */
  taskCount: 4,
  /** 池子上限，防止无限写 */
  poolLimit: 20,
  /** 每天能重抽几次（见 §4.2）。0 = 不许重抽 */
  rerollPerDay: 1,
  /**
   * 满格奖励。**每个在场的人各得一整份**，不是分掉——
   * Habitica 的 party quest 就是这样：所有参与者拿到完全相同的奖励。
   * 现在只有一颗番茄，是为了先把流程跑通；调平衡时改这里，不动代码。
   */
  rewards: [
    { type: "item", itemId: "tomato", quantity: 1 },
  ] satisfies RewardDefinition[],
};
```

`RewardDefinition` 是现成的（`ActionDefinition.rewards` 在用），已经支持
`{type:"item"}` 和 `{type:"unlock"}` 两种。以后要接战利品表（`findLootTable`）
或者按人数/天数变化，都在这一处扩展。

### 3.4 归属为什么这么切

联机时房客带着自己的 `PlayerSave` 进房主的世界：
- **池子和抽签**跟着房客走 → 他在别人家看到的还是自己的 4 条待办 ✓
- **进度**在房主世界的顶层 → 两个人的勾加在同一个数上 ✓
- 房客回家后自家机器有自己的进度，互不干扰 ✓

存档合成器（`setSaveComposer`，联机那一轮做的）天然处理好了：房客的 `dailyTasks`
在玩家侧、实时入档；房主家的 `dailyBoard` 在世界侧、绝不进房客的档。
**不需要新增任何存档纪律。**

## 四、玩法流程

### 4.1 抽签（惰性，无定时器）

打开机器面板 / 读取进度条时，检查 `today.worldDayId`：

```
不存在 或 != 当前世界日
  → 从 pool 随机抽 min(taskCount, pool.length) 条，写入 today
```

抽签用**每日确定性种子**（`hash(playerId + worldDayId)`），不用 `Math.random()`：
同一天里反复开关面板不能抽出不同结果，否则玩家会一直重开直到抽到简单的那几条。

**抽签是对抗第四周流失的主要机制，不只是"控制每天的量"。**
Habitica 的 Dailies 是固定清单，天天面对同一张脸，67% 的第四周流失里有它一份；
我们每天抽出的组合不同，池子越厚变化越多——这本身就在鼓励玩家把池子写厚，
而写池子这个动作又是在梳理自己的生活。这层价值要在 UI 上明说
（"池子里有 12 条，今天抽到这 4 条"）。

**池子不足 taskCount**：抽出几条算几条，但分母仍是 taskCount。
UI 明说"再写几条才凑得满"——引导补池子，不是惩罚。
（联机时朋友的勾照样能帮你凑满。）

### 4.2 重抽（每天一次）

下雨天抽到"跑三公里"、出差抽到"给阳台浇水"——抽签是随机的，
总有做不了的时候。**每天一次机会换掉其中一条**（`rerollPerDay`）。

```
玩家点某条的"换一个" → 从 pool 里剔除今天已抽中的，随机取一条替换
                     → rerollUsed = true
```

- **已打勾的不能换**：那等于撤销进度，而进度是共享的（见下）。
- **池子里没有备选时**（池子条数 ≤ taskCount，全抽出来了）灰掉按钮，
  提示"池子里没有别的了，再写几条吧"——又一次把玩家推向补池子。
- 替换用的随机种子是 `hash(playerId + worldDayId + taskId)`，
  结果写进 `today.draws` 就固定了，读档不会变。

为什么是一次而不是无限：无限重抽等于让玩家直接筛出四条最容易的，
抽签这个机制当场失效（也就失去了 §4.1 里对抗新鲜感消退的作用）。
一次的额度让玩家把它花在真正做不了的那条上，这个取舍本身就是玩法。

### 4.3 打勾

```
玩家点某条 → draw.done = true（PlayerSave）
           → 全家 progress += 1，封顶 taskCount（WorldSave 顶层）
           → 广播 op（§5）
```

**打勾不可撤销**（当天）。可撤销的话进度条会倒退，而进度是共享的——
A 撤销自己的勾把 B 已经看到的进度拽回去，是最容易吵起来的交互。

进度已满时仍可继续打勾（个人清单要能划完），但 progress 不再涨。

### 4.4 满格与奖励

`progress === taskCount && !claimed` 那一刻：
1. `claimed = true` 先置位再吐——避免两个客户端同时满格吐两份
2. 机器演一段动画（抖 → 出口张开）
3. 按 `dailyBoardDefinition.rewards` 逐项吐到地上，**在场每人各一整份**
4. 走 `throwItem()`：现成的抛物线物理 + 现成的 `item_thrown` op，联机各端自动重放同一条弧线

"在场每人各一份"的实现：房里有 N 个人就吐 N 份，散开落地，谁捡到算谁的
（不做定向绑定——那要给掉落物加归属字段，而治愈游戏里没人会去抢朋友的番茄）。

**从哪台机器吐**：触发满格的那次打勾所在的那台。玩家刚在这台机器上点完最后一勾，
奖励从眼前这台吐出来才对得上因果；屋里另外几台只是同一份进度的其它显示器。
一台都没有的极端情况（打完勾的瞬间被别人收走了）落到玩家脚下。

### 4.5 跨天

`world_day_changed`（凌晨 4 点）到来时：
- 个人：`today` 作废（连同 `rerollUsed`），下次打开面板重抽
- 世界：`dailyBoard` 归零（`progress=0, claimed=false`）

离线跨天不需要特殊处理——两边都是"发现日期不对就重置"的惰性逻辑。
**没做完的任务不留下任何痕迹**（无 streak、无欠债，见 §2 推论 2）。

## 五、联机同步

新增两种 `WorldOp`：

```ts
| {
    /** 有人打了一个勾。进度是全家一份，所以不带 instanceId */
    kind: "daily_board_ticked";
    worldDayId: WorldDayId;
    /** 打勾后的进度。发结果不发增量 */
    progress: number;
  }
| {
    /** 今日奖励已发放（吐东西本身走 item_thrown，这条只负责置位） */
    kind: "daily_board_claimed";
    worldDayId: WorldDayId;
  }
```

**发绝对值不发 `+1`**：op 通道是尽力而为的转发（不保证不重复、不保证有序），
增量在这种通道上必然算歪。带 `worldDayId` 是为了丢弃跨天边界上的迟到包——
凌晨 4 点前发出、4 点后才到的那条，不该把新一天的进度顶成 1。

奖励的"吐"不需要新 op：它就是若干次 `throwItem`，联机那一轮已经打通。
`claimed` 单独发一条，是为了让**后加入的人**也知道今天领过了。

服务端只做白名单和体积校验（和现有 7 种 op 一样），不判定"该不该满 4"——
自由文本手动打勾的系统本来就没有服务端可校验的真相。

## 六、UI

### 6.1 进度条（屏幕顶部）

只要屋里放着至少一台机器，**屏幕正上方**常驻一条进度条：

```
        ╭─────────────────────────╮
        │ 今日任务  ●●○○   2 / 4  │
        ╰─────────────────────────╯
```

- 奶油马卡龙皮肤（和时钟、快捷栏同一套 `--cream` / `--peach`）
- 有人打勾时那一格**弹一下**（`cubic-bezier(0.34,1.56,0.64,1)`，和选中格同一条曲线）
- 满格时整条变暖黄 + 轻微呼吸，直到奖励吐出

**什么时候显示**，三个条件任一成立就显示（否则整条不渲染）：

```
屋里有机器  且 (  我今天有抽中的任务
                或 进度 > 0            ← 关键：别人正在推进
                或 今天已经领过奖励 )
```

第二条是"藏起来"和"全家共享"的交叉情况：**我自己池子空，但房主已经打了两个勾**。
这时候藏起来等于看不见房间里正在发生的事——只要进度动了，那就是这个家的事，
该显示。反过来，我池子空且没人推进（`0/4`），整条藏起来。

藏起来而不是显示 `0/4`，理由是 §2 那条"反生产效应"：Habitica 最普遍的抱怨是
**忙的时候被系统追着骂**。一条常驻屏幕正上方、整天显示 `0/4` 的进度条就是消极凝视。
它该**奖励推进，而不是提醒欠债**。

代价是新玩家摆下机器后进度条不出现，得自己按 F 才知道要写任务——
但"摆下机器"本来就是主动动作，玩家会去按一下看看。机器本体的造型
（一块空白的板子）也在暗示"这里该写点什么"。

### 6.2 机器面板（按 F）

两栏：左边"我的任务池"（增删改自由文本，上限 `poolLimit`），
右边"今日抽中的 N 条"（打勾）。池子那栏顶部显示"池子里有 12 条"——见 §4.1。

复用现有 `station_open_requested` 通道和面板外壳（`ui-action-panel` + 牌匾），
新增 `FurnitureCapability.DailyBoard`。

### 6.3 吐奖励的动画

1. 机器整体 squash & stretch 抖两下（0.4s）
2. 出口翻板打开
3. 奖励逐颗以 `throwItem` 抛出（朝机器正面，略微上抛，彼此错开角度）
4. 一声轻响 + 顶部进度条滑出

## 七、怎么拿到这台机器

**剧情解锁**（以后写）+ **命令行提前获得**（本轮就有）。

本轮实现的部分：
- 物品/家具注册表条目（`furniture_daily_board`），带 `FurnitureCapability.DailyBoard`
- `/give furniture_daily_board` 能拿到，摆下即可用

剧情那一侧只留挂点，不写内容：`StoryEffect` 已有 `{kind:"give_item"}`，
以后在 `storyRules` 里挂一条规则就行，**这个玩法本身不需要为剧情改任何代码**。

为什么不走工作台制作：每日任务是驱动日常回流的核心玩法，
藏在"先攒材料"后面等于让新玩家前几天完全体验不到它。剧情赠予既保住了叙事，
又能放在很早的位置。

## 九、已知取舍

- **没有防作弊**：自由文本手动打勾，服务端无从校验。刻意为之（见 §2）。
- **跨家重复打勾**：在朋友家打完勾回自己家还能再打一次（两台机器两份进度）。
  同一件现实事项算了两次——但既然全靠自觉，这不比"直接连点四下"更严重。
- **进度条不记名**：不显示哪一格是谁打的。见 §2 推论 1。
- **奖励按人数翻倍**：五个人在场就吐五份。番茄不值钱时无所谓，
  接稀有奖励时要重新评估（可能要改成"总量固定、人人有份"）。
- **进度不跟着机器走**：全部机器收走再摆回来，当天进度还在（它属于这个家，
  不属于那台机器）。想"重置今天"只能等跨天。
- **空池子时 HUD 完全不出现**：新玩家摆下机器后没有任何视觉反馈，
  必须自己按 F。用机器本体的造型来补这个引导（见 §6.1）。
