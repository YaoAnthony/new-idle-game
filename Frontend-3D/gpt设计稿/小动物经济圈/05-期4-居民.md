## 架构：一位居民 = 一条 storyRule

用户那三条要求（走 event 管线 / 现在纯随机 / 以后要能加门槛）合起来，
答案只有一个形状：

```ts
{
  id: "resident_slime_arrives",
  triggers: [{ signal: "day_started", poolId: "resident_arrival" }],
  //                                   ↑ 期 0 补的抽签池
  effects: [ spawn_pet, start_dialogue, give_item(blueprint) ],
}
```

- **现在纯随机** = trigger 上只有 `day_started` + `poolId`，没有任何门槛
- **以后加门槛** = 那条 trigger 上多一个 `requiresFeature: "plot.north_grove"`，
  代码一行不动
- **加第四位邻居** = 加一条规则，写同一个 `poolId`
- **保底 + 同一天最多来一位** = 期 0 的池机制天然保证（共享一次掷点、
  共享错过计数）

**这就是期 0 存在的全部理由。** 如果这一期发现自己在写"随机选一位居民"的
代码，说明切错了地方——那个随机在 `drawFromPool` 里，已经写完了。

## 分三步

### 4A · 三位居民的模型与定义

**先问参考图**（三个生物 + 三栋房子，六张）。

```ts
// types/pets.ts
export enum CreatureRole {
  Pet = "pet",
  Worker = "worker",
  Merchant = "merchant",
  /**
   * 住在这块地上的邻居。
   *
   * 和 Pet 的区别：他**有自己的房子**，驻地是那栋房子而不是出生点，
   * 晚上会回屋。和 Merchant 的区别：他常驻，不会走。
   *
   * 会不会吃喝亲近：**照 Pet 走**（他们是邻居不是工具），
   * 所以 chooseNextActivity 那三支保留。
   */
  Resident = "resident",
}
```

```ts
// Data/pets/index.ts
  { id: "slime_neighbor",  /* ... */ role: CreatureRole.Resident },
  { id: "fox_neighbor",    /* ... */ role: CreatureRole.Resident },
  { id: "spirit_neighbor", /* ... */ role: CreatureRole.Resident },
```

**精灵的设定要先立**：用户明确说了它**不是 wisp 那一支**（wisp 是
"环境自己长出来的元素凝聚体"），而且是尖耳朵人形。这意味着世界观里
要多一支"有文明的小人"——写对话前先把这条定下来，否则三位邻居的
说话方式会互相打架。

**建模上的两条既有教训**（都写在 `golem.ts` 的注释里，精灵直接适用）：

1. 人形的辨识度**几乎全在剪影上**：肩要比腰宽出去一截、头和肩之间要留
   脖子、手臂要挂在轮廓**外面**。石傀儡第一版三块石板越堆越窄，
   远看是一根柱子。
2. `animate` 里**不要写 `root.position.y = 0`**——那会覆盖 `PetView`
   每帧设的地面高度，角色会浮空（石傀儡浮了 0.45 就是这么来的）。
   要动就动 rig 中间节点。

### 4B · 三栋房子 + 图纸

一栋一个文件（用户定），照 `landCabin.ts` 的结构：

```
Buildings/slimeHouse.ts   → blueprint_slime_house
Buildings/foxHouse.ts     → blueprint_fox_house
Buildings/spiritHouse.ts  → blueprint_spirit_house
```

各自在 `Buildings/index.ts` 登记一行。要点：

- `interior: (style) => buildInterior({...}, style)` —— **同图走进去**，
  和 `landCabin` 同一条路（不换图）
- `maxInstances: 1` —— 一位邻居一栋
- `buildCost` —— 走 `economy` 表；**不要在这里写字面量**
- `icon` 走 `<名字>/lv1.png` 目录约定；图纸的图标由 `blueprintIconUrl()`
  自动借成品的，不用另画
- **不打 `instantBuild`**：那个标志的判据是"玩家会一口气摆十个吗"
  （见 `BuildingDefinition.instantBuild` 的注释）。邻居的房子一辈子建一次，
  施工演出正是要让玩家看见"有人在替我盖"——这是它该有的仪式

### 4C · 到来链 + 搬入机制

#### 到来（纯数据）

```ts
// Data/story/index.ts，三条同构的规则
{
  id: "resident_slime_arrives",
  triggers: [{ signal: "day_started", poolId: "resident_arrival" }],
  effects: [
    { kind: "spawn_pet", petId: "pet-slime", definitionId: "slime_neighbor", delayMs: 3000, jitterMs: 2000 },
    { kind: "start_dialogue", dialogueId: "slime_asks_to_stay", petId: "pet-slime", delayMs: 5000 },
    { kind: "give_item", itemId: "blueprint_slime_house", quantity: 1 },
  ],
},
```

> **图纸在对话之前发还是之后发？** 上面写的是效果数组里一起发。
> 更好的做法是让对话节点的 `emitEventId` 接一条规则再 `give_item`——
> "他把图纸递给你"应该发生在他说完那句话的时候。两种都对，
> 后者的演出更连贯，代价是多一条规则和一个事件 id。

#### 搬入（本期唯一的新机制）

```ts
// Systems/residents.ts（新）
/**
 * 房子建好 → 他搬进去。
 *
 * "搬进去"落到运行时是两件事：
 * 1. **驻地重定向**：`PetBehavior.wanderRadius` 的圆心从出生点挪到他家门口。
 *    驻地**进存档**（石傀儡那期定的：不能读档时拿当时站的位置顶上，
 *    否则每存读一次驻地就朝他溜达到的地方挪一次，挪几回就漂没了）。
 * 2. **发 `resident_moved_in` 信号**，subject = 物种 definitionId。
 *
 * 房子和人的对应关系从**哪张图纸盖出哪栋楼**推，不另存一张表——
 * `slime_house` 建成 → 史莱姆搬进去，一一对应写在这个映射里。
 */
const HOUSE_OF: Record<string, string> = {
  slime_house: "slime_neighbor",
  fox_house: "fox_neighbor",
  spirit_house: "spirit_neighbor",
};

export function startResidents(): () => void {
  return on("building_completed", ({ buildingId, instanceId }) => {
    const species = HOUSE_OF[buildingId];
    if (!species) return;
    moveResidentIn(species, instanceId);   // 驻地重定向 + 存档
    signal("resident_moved_in", species);  // 期 0 加的枚举，这里第一次发
  });
}
```

#### 满三位 → 家具小店的图纸

```ts
{
  id: "residents_want_furniture",
  triggers: [{ signal: "resident_moved_in", signalCount: 3 }],
  effects: [
    { kind: "start_dialogue", dialogueId: "residents_ask_for_shop" },
    { kind: "give_item", itemId: "blueprint_furniture_shop", quantity: 1 },
  ],
},
```

`signalCount: 3` 查的是**不带 subject 的那个键**（`resident_moved_in`），
也就是"搬进来过三位"。这正是期 0 那条"不复用 `pet_spawned` 数人数"
的注释在讲的事——`pet_spawned` 会把水獭和石傀儡一起算进去。

> 家具小店的**建筑本体在期 5**。这一期只发图纸——玩家拿着一张暂时
> 盖不了的图纸不好，所以**两期要么一起上，要么把这条规则挪到期 5**。
> 推荐后者：期 4 只到"三位住齐"，期 5 开头接上求购对话。

## 最容易写错的四处

### 一 · 别在这一期写"随机选一位居民"的代码

那个随机是期 0 的 `drawFromPool`。这一期只写三条 storyRule，
共享 `poolId: "resident_arrival"`。写代码就是切错了地方。

### 二 · 驻地必须进存档，不能读档时拿当前位置顶上

石傀儡那期踩过：每存读一次驻地就朝他溜达到的地方挪一次，挪几回就漂没了。
搬入时把 `wanderCenter` 写进 `PetSave`。

### 三 · 三位居民的对话不能互相打架

精灵是"尖耳朵人形、有文明"，史莱姆和小狐狸是小动物。**写对话前先把
精灵这一支的设定立起来**——三位的说话方式如果没有分工，玩家只会觉得
"来了三个 NPC"，而不是"来了三位邻居"。

### 四 · `maxInstances: 1` 别忘了

不设的话玩家能盖三栋史莱姆的房子，而 `HOUSE_OF` 是按 buildingId 映射的
——第二栋建成会再发一次 `resident_moved_in`，三位居民的计数就废了。

### 实机抓到的：building_completed 只有一半路径在发

`building_completed` 原来**只在 `finishSite` 发**。于是绕过工地那条路
落地的楼一律不报完工，而挂在完工上的剧情就**静默不触发**。

**这个洞有多大，我第一遍说过头了，这里更正。** 当时看到 `/build` 摆的
房子人不搬进去，就写成了"居民永远搬不进来"。实际上：

| 路径 | 落地成什么 | 原来发不发 |
|---|---|---|
| 选址面板确认（`asSite: true`，真游戏走这条） | 工地 → 石傀儡建 → `finishSite` | **发**，居民搬得进去 |
| `/build` 调试指令 | 当场成品 | 不发 ← 我踩到的是这条 |
| `instantBuild` 的木墙（无视 `asSite`） | 当场成品 | 不发 |

所以真游戏里的居民搬入**一直是好的**，我踩的是调试路径。木墙那一支
是实打实的产品路径，只是今天还没有任何剧情挂上去。

修还是要修，因为判据本来就该是"**这一刻它是不是成品**"（没有
`construction` 就是），不是"走了哪个函数"。两条路径各发一次，
`finishSite` 只在真的从工地转成品时发，同一栋不会报两遍。

回归用例放在 `tests/construction.test.ts`（工地生命周期归它管），
三条分支各钉一条：打了 asSite 的落地不报 → finishSite 才报 →
没打 asSite 的当场报；外加木墙即使点了 asSite 也当场报。
第一版我把用例写在 residents.test.ts 里、断言"居民房的 buildDuration
是空的所以瞬时"——那个前提也是错的：空的 `buildDuration` 走的是
`DEFAULT_BUILD_SECONDS = 20`，不是 0。已删掉重写。

   守卫的真意是"图纸不该顶着一张**别的**脸"，不是"每张都必须有脸"——
   没图时 `slots.tsx` 退化成画名字，是诚实降级。这和它自己那条
   "房子、小镇店铺不上架所以不查"的豁免是同一条线。
2. **`storySystem` 挑 once 规则的启发式** → 排除 `poolId`。进抽签池的
   规则不是"发了信号就触发"而是"同池掷点、命中的才触发"，挑中居民规则
   之后发一次 `day_started` 命中的往往是别人——那条用例本来验的是
   firedRules 去重，不是抽签。

### 一个调试上的坑（不是 bug）

`/day` 反复发时，抽签的种子是 `hashSeed(poolId|worldDayId)`——**同一个
现实日里 worldDayId 不变，所以每次掷点结果相同**。表现是连按 `/day`
会连续命中（三位在三次内全到齐），看起来像"保底失效"。这是确定性设计
的正确后果（防重开刷），实机隔天玩不会遇到。要看保底爬坡得用
`/time` 拨天或者清掉 `poolMisses`。
