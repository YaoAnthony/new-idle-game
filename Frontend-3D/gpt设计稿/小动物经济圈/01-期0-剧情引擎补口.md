# 期 0 · 剧情引擎补口

> 状态：**待施工** · 2026-08-24 · 前置：无（全蓝图第一期）· 总纲见 `00-总纲.md`
>
> 标准：任何人不看聊天记录也能照着做完并验收——每处改动给前后代码，每条验收给命令和期望输出。

## 一句话

把「小动物经济圈」整条链需要的**剧情引擎能力**一次补齐：四个信号、一个触发条件、
一个抽签池机制、一个效果，加上一份"昨日事实"记录。做完之后偷窃、居民、报纸、
餐厅解锁**全部是注册表数据，代码里零 if**。

## 为什么它必须是第一期

后面八期里有五期都在等这一期的口子。不先补，那五期就得在 gameplay 代码里写剧情
分支——而"剧情内容零硬编码"是 `Data/story/index.ts` 开头第一句写着的铁律。

| 后面哪一期要用 | 要用什么 |
|---|---|
| 期 3 偷窃 | `building_completed`（金库建成才盯上）、`day_started`（第二天才偷）、`adjust_gold`（扣钱和还钱） |
| 期 4 居民 | `day_started` + 抽签池（随机来一位）、`resident_moved_in`（满三位） |
| 期 7 报纸 | `day_started`（每天一版）、昨日事实记录（版面内容） |
| 期 8 餐厅 | `map_entered`（去过小镇才解锁） |
| 期 5/6 结算 | `day_started`（隔夜结账、商人排期） |

**玩家在这一期看不到任何新东西。** 这是全蓝图唯一的纯地基期，验收全靠测试和调试指令。

### 0-3 · 抽签池 + 保底

这是这一期唯一需要**设计**而不只是接线的一块。

#### 要解决的问题

用户定的居民机制（决策 14）：「不需要先后顺序，这种就进随机池子，新的一天随机到了，就进行」。
拆开来是四条要求：

1. 每天有机会来一位，来谁是随机的
2. 一位居民 = 一条规则（走 event 管线，以后加门槛就是往那条规则加字段）
3. **要保底**——播报员一直不来，报纸就一直出不来
4. **同一天最多来一位**——保底会把概率推高，三条规则各自掷点的话后期会三位同一天全来

`chance` 一条都满足不了：它的注释明写「每次信号独立掷点，**不做保底**」，
而且三条规则各掷各的，第 4 条守不住。

#### 形状：`poolId` 在规则上，参数在 Data 里

`Core/src/types/story.ts` 的 `StoryTrigger`：

```ts
  /**
   * **把这条规则放进一个抽签池。**
   *
   * 和 `chance` 是两种东西，**不要混用**：
   *
   * - `chance` 是**撞见的**——每次信号独立掷点，错过就错过（"某天暴雨时
   *   门口有敲门声"）。
   * - 池是**迟早会来的**——同一个 poolId 的规则共享一次掷点和一份"错过了
   *   几次"的计数，每错过一次命中率往上抬，命中后归零。
   *
   * 共享 poolId **就是共享节奏**：三位邻居写同一个池，于是（a）一次派发
   * 只掷一次点，同一天最多来一位；（b）有人来了，三条的命中率一起回到底；
   * （c）加第四位邻居 = 加一条规则、写同一个 poolId，参数一个字不用改。
   *
   * 池的参数（起始概率、每次抬多少、封顶）在 `Data/story` 的 `storyPools`
   * ——写在规则上会让同池的三条各抄一遍同样的数，那三份数迟早走散。
   *
   * 一条 trigger 不要同时写 `chance` 和 `poolId`（`auditStoryContent` 会拦）。
   */
  poolId?: string;
```

`Core/src/Data/story/index.ts` 新增：

```ts
/**
 * 抽签池的调平衡表。**改节奏只动这张表。**
 *
 * 命中率 = min(max, base + step × 错过次数)，命中后错过次数归零。
 * 期望等待天数在 base=0.12 / step=0.08 下大约是 4 天——够玩家感觉到
 * "过几天会有人来"，又不会某天早上一开门站着三位。
 *
 * 数字是初值。`max: 1` 表示抬到头是**必中**：邻居是卡进度的，不能真的
 * 无限等下去（这正是 `chance` 那条"不做保底"的注释所不适用的场合）。
 */
export type StoryPoolDefinition = {
  poolId: string;
  /** 起始命中率 */
  base: number;
  /** 每错过一次加多少 */
  step: number;
  /** 封顶。不填 = 1（迟早必中） */
  max?: number;
};

export const storyPools: StoryPoolDefinition[] = [
  { poolId: "resident_arrival", base: 0.12, step: 0.08, max: 1 },
];

export function findStoryPool(poolId: string): StoryPoolDefinition | undefined {
  return storyPools.find((pool) => pool.poolId === poolId);
}
```

#### 纯函数部分放 Core

`Core/src/logic/storyTriggers.ts` 加两个纯函数：

```ts
/**
 * 池当前的命中率。`misses` 是"连续错过了几次"。
 *
 * 单独一个函数是为了让用例能直接钉住这条曲线——它是平衡的一部分，
 * 埋在派发循环里就没法单独验。
 */
export function poolChance(
  pool: { base: number; step: number; max?: number },
  misses: number,
): number {
  return Math.min(pool.max ?? 1, pool.base + pool.step * Math.max(0, misses));
}

/**
 * 这次抽签中不中。**掷点必须是确定性的**——种子里带 worldDayId。
 *
 * 用 Math.random 的话玩家一发现"今天没人来"就会重开游戏直到有人来，
 * 抽签这个机制当场失效。这和每日任务抽签是同一条判据
 * （见 `Data/dailyTasks` 里那段注释），所以直接复用它的 hashSeed。
 */
export function poolHits(
  pool: { base: number; step: number; max?: number },
  misses: number,
  seed: number,
): boolean {
  return seededRandom(seed)() < poolChance(pool, misses);
}
```

```ts
/**
 * 各抽签池"连续错过了几次"。进存档——不然读一次档保底就归零，
 * 玩家重开游戏就能把等待重置。
 */
let poolMisses: Record<string, number> = {};

function fire(rule: StoryRule): void {
  firedRules.add(rule.id);
  for (const effect of rule.effects) runEffect(effect);
}

function handleSignal(signal: StorySignal): void {
  /**
   * **先计数再派发**。顺序反了的话 `signalCount: 1` 要等到第二次才成立——
   * "做完一个任务"这种最常见的写法会整体差一拍。
   */
  for (const key of signalCountKeysFor(signal)) {
    signalCounts[key] = (signalCounts[key] ?? 0) + 1;
  }

  const context = currentContext();
  const available = storyRules.filter(
    (rule) => !((rule.once ?? true) && firedRules.has(rule.id)),
  );

  /*
   * 分两段：不进池的照旧一条条判；进池的按 poolId 分组，一组一次掷点。
   *
   * 一条规则算不算"进池"，看的是**这次匹配上的那个 trigger** 有没有
   * poolId——同一条规则可以有两个 trigger，一个走池一个不走。
   */
  const pooled = new Map<string, StoryRule[]>();

  for (const rule of available) {
    const hit = rule.triggers.find((trigger) =>
      triggerMatches(trigger, signal, context),
    );
    if (!hit) continue;

    if (hit.poolId) {
      const group = pooled.get(hit.poolId) ?? [];
      group.push(rule);
      pooled.set(hit.poolId, group);
    } else {
      fire(rule);
    }
  }

  for (const [poolId, candidates] of pooled) {
    const pool = findStoryPool(poolId);
    if (!pool) {
      // 池没登记 = 数据写错了。开机自检会报，运行时不静默丢弃规则
      if (import.meta.env.DEV) {
        console.warn(`[story] 池 "${poolId}" 没有登记，${candidates.length} 条规则不会触发`);
      }
      continue;
    }

    /*
     * 候选为空**已经在上面被过滤掉了**（进不了 pooled）——所以到这里
     * 一定有至少一条候选，"错过"才是真的错过。
     *
     * 这条区别很重要：门槛还没满足的时候不该累积保底，否则玩家开局第一天
     * 就在给一个还不可能发生的事攒运气，等条件满足那天保底已经满了，
     * 邻居当场就来——"过几天会有人来"的节奏被吃掉了。
     */
    const seed = hashSeed(`${poolId}|${context.worldDayId}`);
    if (!poolHits(pool, poolMisses[poolId] ?? 0, seed)) {
      poolMisses[poolId] = (poolMisses[poolId] ?? 0) + 1;
      continue;
    }

    /*
     * 中了。从候选里确定性地挑**一条**——同一天重开必须挑到同一位，
     * 否则"重开换人"就成了刷法。种子和掷点分开（后缀不同），
     * 不然"中不中"和"是谁"会被同一个数字绑在一起。
     */
    const [picked] = drawDeterministic(
      candidates,
      1,
      hashSeed(`${poolId}|${context.worldDayId}|pick`),
    );
    if (picked) fire(picked);
    poolMisses[poolId] = 0;
  }
}
```

## 最容易写错的四处

### 一 · 开机补发翻页要排除空串

`save.lastObservedWorldDayId` 在**第一次开档**时是空串。不排除的话开局第一帧
就报一次翻页，于是"新的一天"在开局当场发生一次——挂在它上面的每日流程全跑一遍。
判据是 `rememberedDay && rememberedDay !== cached.worldDayId`，两个条件都要。

### 二 · 池的"错过"只在候选非空时才算

门槛还没满足的规则**不能算进错过**。要是算了，玩家从开局第一天就在给一件还不
可能发生的事攒保底，等条件真满足那天保底已经满了，邻居当场就来——"过几天会有人来"
的节奏被吃掉。实现上这条是**自动成立的**：候选为空的池根本进不了 `pooled` 这个 Map，
所以下面那段结算跑不到它。写的时候别"顺手"给所有已登记的池都结算一遍。

### 三 · 掷点和挑人要用两个种子

`hashSeed(poolId|day)` 决定中不中，`hashSeed(poolId|day|pick)` 决定是谁。
共用一个的话，"今天中了"和"今天来的是史莱姆"被同一个数字绑死——候选名单一变
（比如第四位邻居入池），已经中了的那天可能变成没中，读档就不一致了。

### 四 · 四件套别只做前两件

`poolMisses` 和 `dayFacts` 都进 `WorldSave`。仓库里已经有一笔漏账的先例：
`Backend/tests/sessions.test.ts:341` 那条 todo——`validate.ts` 的 `REFRESH_KEYS`
放了 `gramophones`，`applyRefresh` 却没有对应那一行，于是联机刷新会把它丢掉。
**加字段的四处**：迁移（这次可选字段+安全缺省，确认不需要即可）、
`Core/src/types/net.ts`、`Backend/.../validate.ts` 的 `REFRESH_KEYS`、
`Backend/.../sessions.ts` 的 `applyRefresh`。

**撞出来的坑**：

1. **开机补发的翻页必须晚一拍**。`startClock` 是启动链里最先起的（"时钟必须
   最先起"），剧情、食物过期、每日刷新的监听全挂在它**后面**——同步 emit
   的话一个听众都不在场，事件发进真空。挂到 `setTimeout(0)`，stop 时拆掉
   没响的那一拍。文档正文没预料到这一条，验收用例（离线七天恰好一次）
   反而是靠它才写得出来。
2. **"可选字段不用抬版本"这个先例过期了**。文档正文写的是照 signalCounts
   的先例不迁移——但那个先例在 `saveShape.test.ts`（2026-08-23 的指纹守卫）
   之前。守卫的注释写得对：不抬版本的后果是两个客户端自称同版而形状不同，
   旧端读新档丢字段再存回去，**静默丢档**。所以照它的三问走了全套：
   **SAVE_SCHEMA_VERSION 29 → 30**、迁移 v30（显式补空缺省）、联机明确
   不跟（story 不在做客端跑，报纸给不给访客看是期 7 的决定）。
3. `EventDefinition` 没有 `descriptionKey`（写文档时按习惯猜的），
   audit 只查事件名 + 各阶段两类键——正文已同步改。

**顺手修掉的 bug**（本来就在，只是没人踩到）：开机静默采纳新世界日、
不发 `world_day_changed`——离线回来"过期食物降品质"那条监听从来没在
开机时跑过。补发之后它自动开始工作（食物过期判定本身按时间戳，幂等）。

**给期 3 留的口**：偷窃链写数据时用 `/day` 验证第二天偷、第三天还；
`/rule` 已经能具名点火任何规则（用户要的"命令行指定居民加入"）。
