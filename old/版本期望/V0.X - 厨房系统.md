# 厨房系统

在基础架构完善之后，开始制作厨房系统。

初期我们可以先通过背包里直接选择给予食物以解锁后续剧情，但厨房系统之后，
我们便需要自己制作食物。

烹饪逻辑基本采用 Overcooked 的方式（调研见 `OVERCOOK调研.md`）。

> **本文是把 `OVERCOOK调研.md` 套进本作的落地稿。**
> 调研里的机制不是照抄——本作没有订单、没有限时、也不该制造焦虑，
> 所以下面每一处删改都写了理由。

---

## 一、从 Overcooked 里拿什么、不拿什么

调研的结论是三句话：**台面是共享存储空间，锅是带状态的加工容器，盘子是提交载体。**
前两条完全适用，第三条要换掉"提交给谁"。

| Overcooked 的机制 | 本作 | 为什么 |
|---|---|---|
| 台面槽位（一格一件） | ✅ 照搬 | Core 的 `FurnitureSlot` / `slotContents` 就是这个，早就定义好了 |
| 锅是可移动的带状态容器 | ✅ 照搬 | 第一天流程明写"把锅拿出来放到灶台上" |
| 食材状态机（生/切/煮…） | ✅ 照搬 | 但去掉"烧毁"，见第四节 |
| 放置规则表驱动交互 | ✅ 照搬 | 和"注册表而不是硬编码"的既定方针一致 |
| 盘子是最终装配单位 | ✅ 照搬 | `整体架构.md`：「盘子——拿来盛成品」 |
| **订单 / 出餐口 / 计分 / 小费** | ❌ **整个删掉** | 本作没有顾客。做好的菜去向是**自己吃**或**给小动物**，见第五节 |
| **限时压力** | ❌ 删掉 | 本作是专注陪伴工具，`V0.2` 明写「不制造焦虑」 |
| **烧焦销毁** | ⚠️ **改成降品质** | `整体架构.md`：「火候只影响品质，不会烧毁稀有材料,进度条有不同颜色，白色，绿色，黄色，红色，烧到黄色才是上乘，红色会显示很焦，绿色表示没熟，如果多个菜放入，只有最后一步需要纠结这个进度条」 |
| **脏盘 / 洗碗池 / 餐具回收循环** | ⏸️ 延后，可能不做 | 它的作用是制造资源压力（限制盘子数量逼你洗碗）。本作要的是"待着舒服"，洗碗是纯家务负担。**默认不做** |
| **食材箱（无限产出）** | ❌ 不适用 | 本作食材来自行动奖励、宠物带回、种植。厨房不凭空生食材 |
| 垃圾桶 | ✅ 保留 | 需要一个"倒掉锅里配错的东西"的出口，否则玩家会卡死 |

**一句话**：借它的**物品流转模型**，不借它的**压力来源**。

## 二、空间与交互

厨房完全建立在既有的 16×12 网格上，不另起一套。

- 每件厨具占一格或多格（沿用 `GridFootprint`）
- 玩家**站在相邻格并朝向厨具**时可交互（`RoomScene.refreshInteractTarget` 的现有判据）
- 交互提示气泡浮在厨具上方（`interactHint` + world-to-screen，已有）

### 两个按键

沿用调研的分法，也和现有操作一致：

| 键 | 用途 | 例子 |
|---|---|---|
| **F（交互键）** | 瞬时行为 | 拿起、放下、投料、装盘、端锅 |
| **长按 F（操作键）** | 需要持续时间的行为 | 切菜、揉面、搅拌 |

### 判断优先级

玩家面对一件厨具按 F 时，按这个顺序解析，**不写 if-else 长链**：

1. 手里有东西，且目标能接收它 → 投入
2. 手里有东西，且目标表面为空 → 放下
3. 空手，且目标表面有东西 → 拿起
4. 空手，且目标可以产出 → 取出（如锅里的成品）
5. 无可用操作 → 提示

这条顺序能避免"我想拿盘子却误触灶台"。

### 设施清单

`整体架构.md` 已经点名了灶台 / 面包机 / 展板（切菜）/ 煮饭锅，补齐后：

| 设施 | 功能 | 能放什么 |
|---|---|---|
| 普通台面 | 暂存、传递 | 1 个槽位 |
| 展板（砧板） | 切菜切肉 | 1 个食材槽 |
| 灶台 | 加热锅具 | 只接受锅具（已有 `burner_left` / `burner_right` 两个槽） |
| 煮饭锅 | 煮米饭 | 专用容器 |
| 面包机 | 面粉 → 面包 | 专用容器 |
| 盘架 | 提供干净盘子 | 可叠放 |
| 垃圾桶 | 倒掉配错的内容 | 放入即销毁 |

**普通台面默认只有一个槽位**——这不是限制，是让画面保持清晰。要放多份东西请装进锅或盘子里。

## 三、食物在哪里：四选一

这是整个系统最重要的一条约束。

**每一份食材，任何时刻只能存在于以下四处之一：**

1. 玩家手中
2. 设施表面槽位
3. 容器内部（锅 / 碗 / 盘）
4. 已销毁或已被吃掉

**绝不允许同一份东西既记在锅里、又留在台面数据里。**否则端起锅的时候，
食材会留在原地——这是调研里点名的经典 Bug。

数据上表现为**归属指针**而不是坐标：

```ts
// 对：食材只记录自己属于谁
{ itemId: "tomato", state: "chopped", holder: { kind: "cookware", id: "pot-01" } }

// 错：分别记"番茄坐标"和"锅坐标"
```

### 与 Core 现状的对接

- 设施表面 → 已有 `PlacedFurnitureState.slotContents: Record<SlotId, InventoryStack>`
- 容器内部 → **需要新增**：锅本身是个物品实例，得能带内容物。
  现在 `InventoryStack` 只有 id + 数量，装不下"这口锅里有 2 份切好的番茄、煮到 60%"
- 玩家手中 → **需要新增**：现在只有背包，没有"手持"这个位置

> ⚠️ 这是厨房系统最大的一处 Core 改动：**物品要从"可堆叠的计数"升级成"可以有个体状态的实例"**。
> 只对容器和带状态的食材开这个口子，普通材料继续走计数，避免整个背包重构。

## 四、食材状态机（去掉"毁掉"那一档）

```
生 raw
  ↓ 切（展板，长按）
切好 chopped
  ↓ 投入锅具
烹饪中 cooking
  ↓ 进度满
完成 cooked
  ↓ 继续留在火上
过火 overcooked   ← 本作止步于此
```

Overcooked 的最后一档是 `burnt`（作废重来），**本作改成 `overcooked`：能吃，但品质下降**。

理由有两条，都是既有设定：

- `整体架构.md`：「火候只影响品质，不会烧毁稀有材料」
- `V0.2- 3d 分支尝试.md`：本作是专注陪伴工具，**不做"功亏一篑"的判定，不制造焦虑**

所以"过火"的后果是：卖相差一点、恢复量低一点、**小动物可能不爱吃**——
但你辛苦攒的稀有食材永远不会凭空消失。

### 端锅离火 = 暂停

锅从灶台移到普通台面，**烹饪进度和过火进度都暂停**。
这条要保留——它不是压力，是给玩家的**控制权**：同时炖两锅东西时可以主动调度。

### 配错了怎么办

锅里放了不匹配任何配方的组合时：

- 锅**停止加热**，显示"这个搭配好像不太对"
- 玩家可以端到垃圾桶倒掉，或者补上缺的那一样
- **不自动删除、不生成黑暗料理**（第一版）

### 错误放置绝不吞东西

拿着生肉去点盘子这类操作：

- 盘子轻轻晃一下就行了

调研里这条说得很对：自动吞掉玩家的东西会让人觉得系统坏了。

## 五、做好之后给谁——替换掉订单系统

Overcooked 的终点是出餐口。本作没有顾客，**盘子仍然是最终装配单位，但提交对象变成两个**：

```
完整的一盘菜
  ├─→ 自己吃         → 恢复饥饿 / 疲劳
  └─→ 递给小动物     → 好感度 + 宠物记忆
```

所以**没有出餐口这件家具**，也没有验证、计分、小费、倒计时。
一盘菜做好后就是个普通的、带状态的物品，你想什么时候处理都行。

### 装盘是双向的

两个方向都要支持，操作才自然：

- 拿着**空盘**面对**完成的锅** → 盛出来
- 拿着**完成的锅**面对**空盘** → 倒进去

盛出后锅恢复为空锅。

## 六、配方与厨具都是注册表

配方和厨具**都必须是注册表数据**，加一道菜、加一种锅，都不该动任何系统代码。

### 厨具注册表

⚠️ 别写成 `cookwareType: "pot" | "pan"` 这种**硬编码联合类型**——
加一种锅就要改类型定义、改所有 switch。厨具是内容，走注册表：

锅本身就是背包里的一件物品，所以**不另开一张表**——沿用 `ItemDefinition`
已有的「可选能力块」写法（现在的 `food?` / `tool?` / `ingredient?` 就是这个模式）：

```ts
// ItemDefinition 新增一块
cookware?: CookwareBlock;

type CookwareBlock = {
  /** 能做哪些加工方式，配方靠这个匹配。值是注册表键，不是字面量联合 */
  methods: CookMethodId[];
  capacity: number;                  // 固定容量，不做体积计算
  /** 要架在带哪种能力的家具上；不填 = 不需要火，放哪张台面都能用（搅拌碗） */
  heatSource?: FurnitureCapability;  // Cooking
};

/** 「这是一口锅」= 这个 ItemId 带 cookware 块。不需要独立的 CookwareId */
type CookwareId = ItemId;
```

这样锅在背包里、在灶台槽位里、在配方表里都是**同一个 id**，
不会出现"物品表登记一次、厨具表再登记一次"的双份真相。

第一版两种（定案）：

| id | 名称 | 加工方式 | 容量 |
|---|---|---|---|
| `wok` | 炒锅 | 炒 / 煎 | 3 |
| `tall_pot` | 高锅 | 煮 / 熬 | 3 |

正好对上灶台已有的 `burner_left` / `burner_right` 两个槽位。
以后加蒸笼、砂锅、搅拌碗，只是注册表多一条。

### 加工方式也是注册表（定案）

一开始我以为「怎么加热」是**有限的物理动作集合**，可以写成枚举。
但只要问一句「交互气泡上那个字从哪来」就否掉了：

- 长按提示要显示「炒」「煮」「蒸」——**需要 `localizationKey`**
- 火焰 / 水汽 / 油烟的特效按方式区分——**需要 `visualId`**

**凡是需要挂一条数据的东西就是内容，内容走注册表。**所以：

```ts
type CookMethodDefinition = {
  id: CookMethodId;                  // fry / boil / steam / mix，以后加"炸""烤"只是多一条数据
  localizationKey: LocalizationKey;  // 「炒」——交互提示要显示这个字
  /** 加热时的表现：火焰、水汽、油烟。渲染层自己查，逻辑层不认识 */
  visualId?: VisualId;
};
```

关键是**系统代码永远不 switch 加工方式**，它只做一件事：
判断 `cookware.methods` 是否包含 `recipe.method`。加一种方式 = 注册表加一条 +
写一句译文，一行系统代码都不动。

> 如果以后真出现「炸需要先倒油」这类特殊规则，也是往 `CookMethodDefinition`
> 里加字段（例如 `requiresItemId`），仍然不是加分支。
>
> ⚠️ 顺带记一笔：Core 现在的 `ToolType`（`"camera" | "hoe" | …`）
> 犯的正是这个错——加一把工具就要改类型。不是本节要修的东西，但迟早要一起搬。

### 配方表保持扁平——因为半成品留在锅里

**这是个很省事的结论。**既然煎鸡蛋做好后就留在锅里、直接加番茄继续，
那"番茄炒蛋 = 煎鸡蛋 + 番茄"**仍然是一条普通配方**，只不过其中一样材料
恰好是另一道菜的产物。

锅只要记住"我现在装着什么"，投料时拿 **锅内现有内容 + 新投入的** 去匹配配方表即可。
**合成树是数据自己长出来的，系统不需要感知"这是第几步"。**

```ts
type CookingRecipe = {
  id: RecipeId;
  localizationKey: LocalizationKey;
  cookwareId: CookwareId;            // 引注册表，不是写死的字符串
  method: CookMethodId;              // 同上，注册表键
  /** 锅内需要的东西。可以包含其他配方的产出（煎鸡蛋） */
  inputs: RecipeInput[];
  output: ItemId;
  durationSeconds: number;
  /** 进度条会不会烧到红色。省略 = true，半成品（煎鸡蛋）才写 false。见六之二 */
  overcookable?: boolean;
};
```

### 投料顺序天然重要（定案）

先放番茄再放鸡蛋**做不出**番茄炒蛋——因为没有任何配方匹配
"锅里有生番茄 + 生鸡蛋"。这是上面那个设计的**自然结果，不用额外写规则**。

### 已定的五条配方

```
鸡蛋 → 炒锅（煎）            → 煎鸡蛋
煎鸡蛋 + 番茄 → 炒锅（炒）    → 番茄炒蛋
米 → 高锅（煮）               → 白米饭
青椒 + 肉 → 炒锅（炒）        → 青椒炒肉
皮蛋 + 娃娃菜 → 炒锅（炒）    → 上汤娃娃菜
```

> 原稿写的是「白米饭 + 高锅 → 米饭」，输入输出写反了（已确认）。
> 正确的是「米 → 白米饭」：`rice`（生米，食材）煮出 `cooked_rice`（白米饭，成品）。

### 第一版不做切菜（定案）

展板、`chopped` 状态、长按切菜**全部延后**。五条配方都是直接下锅，
现在做等于建一套没人用的机制。以后真出现要切的菜再开。

### 碗分两类，各挂一块能力（定案）

| 类型 | 例子 | 挂哪块 |
|---|---|---|
| **加工容器** | 搅拌碗、面糊碗 | `cookware?`——它和锅同类，只是 `methods: ["mix"]` 且不填 `heatSource` |
| **盛装容器** | 盘子、汤碗、饭碗 | `servingWare?`——最终装配单位 |

⚠️ 和厨具同一个道理：**别写成 `servingWare: "plate" | "soup_bowl" | "rice_bowl"`**。
盘子、汤碗、饭碗是内容，加一种碗不该动类型定义。它和 `cookware?` 完全同构：

```ts
// ItemDefinition 再新增一块
servingWare?: ServingWareBlock;

type ServingWareBlock = {
  capacity: number;                  // 一盘能装几样，和 CookwareBlock 同名同义
  /** 只收某几类菜？留空 = 什么都能盛。第一版全部留空 */
  acceptsTags?: string[];            // 对 ItemDefinition.ingredient.tags
};

type ServingWareId = ItemId;
```

于是"视觉上不同"这件事**自动就解决了**：盘子和饭碗是两个不同的 `ItemId`，
各带自己的 `visualId` 和译名，数据上共享的只是 `servingWare` 这块行为。
不需要"统一成一个类型"，需要的是"统一成一块能力"。

> 一件东西同时带 `cookware` 和 `servingWare` 也是合法的（比如端上桌的砂锅），
> 规则表按能力查，不按品类查。

## 六之二、火候与起锅

这是整个厨房**唯一需要手感**的地方，其余全是搬运。

### 进度条四色

白 → 绿（没熟）→ **黄（上乘）** → 红（焦了）

### 按 F 起锅，当场定品质（定案）

锅还在灶上，玩家**看准颜色按 F**，菜的品质就定在那一刻。
不用端锅、不用提前拿盘子站旁边——一个键解决。

### 中间段不会过火（定案）

煎鸡蛋这种还能继续加工的阶段，**进度走完就停住，不会变红**。
只有"最终成菜"那一步才需要盯着颜色。对应你说的
「多个菜放入，只有最后一步需要纠结这个进度条」。

**怎么判断"最终"？配方自己声明，不靠推导（定案）。**

```ts
// CookingRecipe 新增
/** 这道菜的进度条会不会烧到红色。省略 = true */
overcookable?: boolean;
```

- 番茄炒蛋 / 白米饭 / 青椒炒肉 / 上汤娃娃菜 → `true`（默认，要看准颜色按 F）
- 煎鸡蛋 → `false`（走完就停在那儿等你加番茄，或者直接盛出来吃）

> 曾经考虑过纯数据推导：「存在一条配方拿它当材料 → 它是中间体 → 不过火」。
> 现在的五条配方下这个推导完全正确，但它有个隐患：以后加一道
> 「番茄炒蛋盖饭 = 番茄炒蛋 + 白米饭」，番茄炒蛋就**自动变成中间体、从此不再需要盯火**——
> 只是加了一道新菜，却悄悄改掉了一道老菜的手感，而且没有任何地方会提示你。
>
> 「这道菜要不要盯火」是**手感决定**，不该由「以后有没有别的配方用到它」这种
> 不相关的内容改动来决定。所以宁可多填一个字段。

### 煎鸡蛋既是菜也是材料（定案）

饿了就盛出来吃，不饿就继续加番茄。**玩家自己决定停在哪一步。**
所以"最终成菜"某种意义上是**玩家的起锅动作定义的**，不是数据写死的。

## 六之三、食材来自两个世界

**这是全作的题眼落到数据上的地方，不只是分类标签。**

`整体架构.md`：「吱吱从来没见过奶酪，所以这不是单纯的送礼加好感，
而是在告诉玩家：**现实行动获得的奖励，可能是这个世界没有的东西**。」

所以食材有两个来源，**注册表必须能表达它属于哪个世界**：

| 来源 | 产出 | 例子 |
|---|---|---|
| **现实任务**（行动系统） | 现实世界的物品 | 奶酪、铁块 |
| **宠物派遣** | 那边（奇幻世界）的食材 | 青椒、肉、皮蛋、娃娃菜、米 |

```ts
// ItemDefinition 新增
origin: "real" | "otherworld";
```

这个字段不是摆设，它驱动：

- **小动物的反应**——递过去一样 `origin: "real"` 的东西，它没见过，
  反应和普通食材完全不同（第一天的奶酪就是这么来的）
- **宠物记忆**——记下的不是"喜欢奶酪"，是"原来你来自另一个世界"
- **以后的配方**——用异世界食材做的菜 vs 用现实食材做的菜，可以有区别

> 也就是说：**你在现实里写完作业换来的东西，在这个世界里是稀罕物。**
> 这条设定同时给了行动系统和厨房系统存在的理由。

### 现实物品能下锅（定案）

奶酪这类 `origin: "real"` 的东西**可以当食材**，而且**做出来的菜很特别**——
两个世界的东西凑成一盘，小动物的反应最强烈。

这给了玩家一个创造的理由：不只是"把奶酪递过去"，而是"用你那边的东西
和我这边的东西，做一道谁都没吃过的菜"。

## 六之四、食材不能吃，只有成品能吃

**（定案）食材只是素材。**生番茄、生鸡蛋、米、肉——**一律不能直接吃**。
想恢复饥饿就得真的做一顿饭。

> ⚠️ **现状与此冲突**：`tomato` 有 `food: { hungerRestore: 6 }`、
> `egg` 有 `hungerRestore: 5`，现在**生啃番茄和鸡蛋是能回饥饿的**。
> 实现时要把食材的 `food` 字段摘掉，只留成品（如 `fried_tomato_egg`）。

这条规则让厨房**成为必经之路**而不是可选玩法——否则玩家会发现啃生食材更省事。

### 每样食物有两个属性

```ts
// ItemDefinition.food 扩展
food?: {
  hungerRestore: number;
  fatigueRestore?: number;
  shelfLifeSeconds?: number;

  /** 吃下去的反应：buff / debuff。先留空，以后填 */
  effects?: FoodEffect[];

  /** 吃下去之后的表现 */
  onEat?: {
    /** 描述文案，我们自己写 */
    localizationKey: LocalizationKey;
    /** 角色行为状态：开心 / 难受 / …（后面做） */
    behavior?: EatBehavior;
  };
};
```

两者的分工：

| 属性 | 是什么 | 现在做吗 |
|---|---|---|
| `effects` | 数值层面的 buff / debuff | ❌ 先留空，字段先占位 |
| `onEat.localizationKey` | 吃完的一句描述（我们写的文案） | ✅ 可以现在写 |
| `onEat.behavior` | 角色的表现状态（开心 / 难受） | ❌ 后面做 |

> 「开心 / 难受」是角色的**姿势与表情状态**，和现有的专注姿势（`focusPose`）
> 同一类东西——`CharacterView` 的一组部件 transform，不是数值。

### 实现时补的决定

1. **起锅不是"产出到背包"**，是锅里的内容整体换成成品（带品质）留在锅里。
   所以"继续加料"和"装盘"用的是同一份数据。
2. **白 / 绿 时按 F 什么都不消耗**，只提示"还没熟"。不做功亏一篑的判定。
3. **内容一变，加热秒数归零**——锅里现在是另一样东西了，沿用上一道菜的火候没有意义。
   代价是配错料会丢掉已经烧的时间（但材料一样不丢）。
4. **暂时没有垃圾桶这件家具**，改成对着锅按 **G 倒掉**。这是防止一口锅被
   错误组合卡死的保底出口，垃圾桶做出来之后可以并存。
5. **带内容的容器不能进背包**：背包按 itemId 合堆，两口锅合成一堆会丢掉其中一口
   锅里的菜。所以锅碗的 `stackLimit` 全是 1，非空时拒绝放回背包。
6. 于是**装盘后的菜必须有出路**，手持栏上补了两个：**吃掉** / **收起来**（进背包）。
   为此背包槽位加了 `quality` 字段，**品质不同的同名菜不合堆**——
   不然"过火降一档"在送礼时就无从判断了。
7. **灶眼选哪个由站位决定**，不弹面板选。灶台左右两个灶眼，走近哪个就操作哪个。
8. 交互气泡的文案**每帧问一次规则表**，随手上端着什么实时变
   （空手→"端起来"，端着蛋→"投进锅里"，熟了→"起锅"，端着空盘→"盛出来"）。

### 还没做

- **展板 / 切菜**：按第六节的定案延后。
- **面包机、煮饭锅、盘架**：只有灶台有槽位；这三件还没有 FurnitureDefinition。
- **搅拌碗**（不需要热源的 `cookware`）：类型支持了（`heatSource` 可选），还没有数据。

- **食材没有各自的 3D 模型**：锅里的内容先用色块占位
  （`cookware.ts` 的 `ingredientColor`，以后换成查 VisualRegistry）。

## NPC 喜好与送礼系统

每个 NPC 应该有特别喜欢的食物，大幅度添加好感度和记忆。

这一节和厨房是**同一个循环的两端**——做饭的意义有一半在这里，所以要一起设计。

> 参考星露谷物语与动物森友会。
> ⚠️ 以下参考内容是凭记忆整理的，**具体数值未经核对**，机制骨架可信、数字仅供参考。

### 两个参考作怎么做的

**星露谷**：分五档（爱 / 喜欢 / 无感 / 不喜欢 / 讨厌），送错**真的扣好感**。
数据是**通用规则打底 + 个体覆盖例外**（一个 `NPCGiftTastes` 数据文件），
所以不必写 N 个 NPC × M 个物品。交互极简：手持物品直接点 NPC，
**你完全可以把垃圾递过去然后挨骂**。节流是每人每周 2 次。

**动森**：好感度**不显示数字**（和本作既定设定一致）。反应重于数值——
送的衣服它会真的穿上、家具会真的摆进它家。回报是"它把你送的东西用起来了"。
节流是每天一次。

### 抽出来的三条骨架

1. **分档而不是二元**，每档有独立反应
2. **让玩家能送错**——送错本身是了解对方的一部分
3. **反应**（而不是数字）才是回报

> ⚠️ 现状三条全违反：`acceptedItemIds` 写死在对话节点里，
> UI 只列出它**接受**的东西，玩家根本没机会递一个它不喜欢的。这块要重做。

### 本作的方案

**四档**，沿用 `整体架构.md` 已有的措辞：**爱吃 / 能吃 / 不喜欢 / 不能吃**。

**送错不扣好感**（定案）。理由是本作「不做功亏一篑的判定，不制造焦虑」——
试错是了解它的过程，不该被惩罚。四档的差别全部体现在**反应**上：

| 档位 | 表现 |
|---|---|
| 爱吃 | 眼睛发亮、卷芽整个舒展，留下记忆条目，推进剧情 |
| 能吃 | 收下、道谢，反应平淡 |
| 不喜欢 | 闻一闻就放下，委婉拒绝——**东西还在你手上** |
| 不能吃 | 明确摇头，可能顺带解释为什么（这本身也是了解它的信息） |

**每天一次**（动森式，定案）。防止一次性塞一背包刷满，也符合"每天回来看看"的节奏。
⚠️ 依赖时钟系统——目前还没接，接之前先用 `WorldDayId` 推导或占位。

**菜的品质参与判定**：过火的菜降一档（爱吃 → 能吃）。和厨房那边接上。

### UI：头像 + 放入框

不做星露谷的"手持点击"（本作是第三人称 + 背包制，没有手持系统）。
用动森那种直给式，**越简单越好**：

```
走近小动物按 F → 对话里出现「递东西」
┌──────────────────────────┐
│  [头像]   苔苔            │
│                           │
│        ┌────────┐         │
│        │  放入  │  ← 从背包拖进来
│        └────────┘         │
└──────────────────────────┘
→ 判定档位 → 它的反应 → 触发对应剧情分支
```

关键是**背包里的东西全都能拖进去，不做任何过滤**。

### 分支不硬编码

判定只负责算出档位，**后果交给剧情系统**——和现有的
「对话只发事件、不写效果」是同一条路子：

```
送出物品 → 查喜好表得到档位 → 发信号
             gift_loved / gift_liked / gift_disliked / gift_inedible
           → storyRules 声明各档接什么后果
```

所以"没那么喜欢的怎么办"就是**加一条 StoryRule 的事，不动代码**。

### 喜好数据

**每只宠物写完整喜好表**（定案）。

```ts
type PetTaste = {
  loved: ItemId[];        // 爱吃
  liked: ItemId[];        // 能吃
  disliked: ItemId[];     // 不喜欢
  inedible: ItemId[];     // 不能吃
  /** 表里没列到的物品落哪一档。防止漏填导致判定失败 */
  fallback: "liked" | "disliked";
};
```

> ⚠️ 代价：**每加一样新食物，都要回头补所有宠物的表**。现在 3 只还好，
> 物种多了会累。`fallback` 是安全网——漏填不会崩，只是落到默认档。
> 以后如果表维护不动了，可以换成星露谷那套「按 tag 通用打底 + 个体只写例外」，
> 数据结构不用大改。

`整体架构.md` 还提到**与天气相关的偏好**，那是后话，先不做。

### 宠物记忆

送礼的真正产出（`整体架构.md`：「如果它对这个东西感兴趣，就会留下最初的信息记录」）。

- 「爱吃」档送出后写一条记忆：**你给了它什么、它说了什么**
- 记忆是玩家"一点点理解它"的载体，不是数值面板
- 属于宠物，进 `WorldSave`

第一天流程的题眼就在这里：你递过去的奶酪是**现实行动换来的**，
而它从没见过——记忆条目记下的不只是"喜欢奶酪"，是"原来你来自另一个世界"。

## 送礼系统实现状态（2026-07-30）

已实现：四档判定、每日节流、放入框 UI、日常寒暄的可重复送礼入口。
**未实现：宠物记忆**（本次只发信号、留空壳，见下）。

### 实现时补的决定

**非食物一律「不能吃」，不进喜好表。**
`fallback` 按设计只覆盖「表里没列到的**食物**」；木板、锤子、家具这类
结构上就不能吃的东西由 `resolveGiftTier` 直接判 inedible。
否则每只宠物都要把四十件家具抄一遍。

**过火降一档最低只到「不喜欢」。**
设计只举了「爱吃 → 能吃」一个例子。统一按降一档实现（能吃 → 不喜欢），
但不会降到「不能吃」——焦的菜还是菜，不是结构上没法吃的东西。

**主线推进挂 `gift_given`（不分档），不挂 `gift_loved`。**
第一天的题眼是「你递上了它连见都没见过的东西」，和好不好吃无关。
挂档位的话玩家第一次递生鸡蛋（判定为不能吃）就永久卡住，
违反「不制造焦虑」。四档信号留给 storyRules 声明各自的反应后果。

**节流按「递出去过」算，不按「收下了」算。**
否则拿一样它不吃的东西可以无限试（不消耗物品），
四档反应会退化成免费的喜好查询器，送礼就从「每天回来看看」变成一次性摸表。

**日常寒暄必须带送礼入口。**
原实现只有初见对话能送礼——那样节流永远碰不到，整套系统等于一次性过场。

**`DialogueItemRequest` 用 `Record<GiftTier, DialogueNodeId>`。**
四档回应节点一个都不能少，用 Record 逼出穷尽性——
「四档的差别全部体现在反应上」，少写一档就等于那一档没反应。

对话节点的 `emitEventId` 原本发的是 `gift_accepted` 信号，
而 `pet_gift_accepted` 规则不过滤 subject——妈妈对话的 m4 节点
也会触发好感晋级和解锁宠物派遣。改成语义正确的 `dialogue_event`。
副作用：`mom_promised_machine` 现在没有任何规则监听（它本来就没有，
之前只是错误地蹭了送礼规则）。要不要给它补规则待定。
