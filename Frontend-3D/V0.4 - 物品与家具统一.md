# V0.4 · 物品与家具统一

> 2026-07-31。起因是「切换快捷栏时手上要显示对应的模型」，
> 一路查下去发现问题比显示更深：**同一件东西在数据里存在两次**
> （物品一条、家具一条），"长什么样"又散在三张表里。
>
> 这份文档是**定案的数据结构 + 迁移方案 + 分阶段计划**，供实现照做。

---

## 一、现状的三个问题

### 1. 落地灯是两件东西

```
Core/Data/items     : { id: "furniture_floor_lamp", placeableFurnitureId: "floor_lamp" }
Core/Data/furniture : { id: "floor_lamp", visualId: "floor_lamp", ... }
i18n                : "item.furniture_floor_lamp": "落地灯"
                      "furniture.floor_lamp":      "落地灯"      ← 同一个名字写两遍
```

两个 id、两条定义、两个本地化键，靠 `placeableFurnitureId` 和
`findItemByFurnitureId` 两个函数来回换算。加一件能摆的东西要在两张表各写一条，
还得记得让它们对上。

### 2. 「长什么样」散在三张表

| 表 | 键 | 谁在用 |
|---|---|---|
| `VisualRegistry` | `visualId` | 家具；厨具靠**拿 itemId 当 visualId 蒙** |
| `INGREDIENT_SHAPE` | `itemId` | 锅里那一份 |
| `INGREDIENT_COLOR` | `itemId` | 上一张查不到时的兜底色 |

后两张是做「锅里要看得见鸡蛋」时图省事加的，当时就该并进注册表。

### 3. 覆盖率（实测，53 件物品）

| | 数量 | 情况 |
|---|---|---|
| A | 4 | 自己有同名视觉配方：`bedroll` `wok` `tall_pot` `plate` |
| B | 25 | **家具物品——模型早就有了**，顺着 `placeableFurnitureId` 一跳就到 |
| C | 24 | 真没有模型：材料 11 + 食物 13 |

B 那 25 件不缺模型，缺的是**一跳**。真正要补的只有 C 的 24 件，
其中 13 个食物是要紧的（要下锅、要拿在手上），11 个材料排后面。

而且现在查不到就**静默不画**——分不清是还没做还是坏了。

## 二、数据结构（定案）

### 用「能力块」而不是继承

家具 = **带 `placement` 这一块的物品**。不做类继承，理由是能力不排他：
一块蛋糕可以既能吃又能摆在桌上，继承表达不了。而且代码库对
食物、厨具、工具本来就是这么写的（`food?` / `cookware?` / `tool?`），
`placement?` 只是又一块，风格一致。

```ts
/** 能摆到屋里。带这一块的物品就是"家具" */
export type PlacementBlock = {
  surface: PlacementSurface;           // 地面 / 墙面
  footprint: GridFootprint;
  footprintMask?: ReadonlyArray<readonly [number, number]>;
  floorLayer?: FloorLayer;
  blocksMovement: boolean;
  coversOpenings?: boolean;            // 窗帘能盖住窗洞
  capabilities: FurnitureCapability[]; // 做饭 / 存储 / 睡觉 / 氛围…
  interactHint?: InteractHint;
  slots?: FurnitureSlot[];             // 灶眼、砧板
  anchors?: FurnitureAnchor[];         // 能坐能躺的落脚点
};

/** 声音。全是 ref，指向 Core/Data/audio 里的 profileId */
export type AudioBlock = {
  ambient?: AudioProfileId;  // 摆在屋里一直响：壁炉噼啪、挂钟滴答
  active?: AudioProfileId;   // 正在工作时响：灶眼加热
  use?: AudioProfileId;      // 用一下的那一声：开箱、开柜
};

/** 长什么样。**必填** */
export type VisualBlock = {
  id: VisualId;
  scale?: number;            // 不填 = 1
  preppedId?: VisualId;      // 下锅形态；不填 = 从主色自动生成切块
};

export type ItemDefinition = {
  id: ItemId;
  localizationKey: LocalizationKey;
  category: ItemCategory;
  rarity: Rarity;
  stackLimit: number;
  origin?: ItemOrigin;

  visual: VisualBlock;       // ← 必填
  audio?: AudioBlock;

  placement?: PlacementBlock;
  food?: FoodBlock;
  cookware?: CookwareBlock;
  servingWare?: ServingWareBlock;
  ingredient?: IngredientBlock;
  tool?: ToolBlock;
};
```

**`visual` 必填是刻意的**：这样"加了一件物品但没人知道它长什么样"
在编译期就过不去。现在那种"静默不画、分不清没做还是坏了"从类型上就消失了。
扔在地上、拿在手上、下锅，用的都是这一份。

### 一个注册表

```ts
export const itemDefinitions = [ ... ] satisfies ItemDefinition[];

export function findItemDefinition(id: ItemId): ItemDefinition | undefined;

/** 带 placement 的才算家具，取代 findFurnitureDefinition */
export type PlaceableItem = ItemDefinition & { placement: PlacementBlock };
export function isPlaceable(item: ItemDefinition): item is PlaceableItem;
export function findPlaceableItem(id: ItemId): PlaceableItem | undefined;
```

### 视觉：一张表管到底

```
ItemDefinition.visual.id  →  VisualRegistry  →  低多边形图元拼出来的模型
```

三个消费方共用：**手上**（原大）、**锅里**（缩小 + 形态）、**以后掉落物**。

**形态只有两种，第二种不用建模：**

- **整**（authored）——写在视觉配方里
- **切块**（**自动生成**）——从「整」形态取主色，吐几块小楔形

「熟」不需要第三种形态：起锅后锅里装的是**成品物品**，它自己有 `visual`。
所以加一道菜 = 加一个成品物品 = 一个模型，线性增长，不存在
recipe × ingredient 的组合爆炸。

> 依据是 `Core/logic/cookingRules.ts` 的 `take_out_dish`：它把锅里的东西
> 整个换成 `[{ itemId: recipe.output }]`。锅里任何时刻装的都是"物品"。

**主色从模型里取**（体积最大那块 mesh 的材质色，建一次缓存），
`INGREDIENT_COLOR` 删掉——颜色和模型永远不会对不上，因为它就是模型的颜色。

### 会消失的东西

| 现在 | 之后 |
|---|---|
| `FurnitureDefinition` 类型 | `PlacementBlock` |
| `furnitureDefinitions` 注册表 | 并进 `itemDefinitions` |
| `placeableFurnitureId` / `findItemByFurnitureId` | 不需要，id 就是同一个 |
| `findFurnitureDefinition` | `findPlaceableItem` |
| i18n 两条名字 | 一条 |
| `INGREDIENT_SHAPE` / `INGREDIENT_COLOR` | 并进视觉注册表 |

## 三、迁移方案

### id 定案：留**物品**那一侧

落地灯合并后的 id 是 **`furniture_floor_lamp`**，不是 `floor_lamp`。

代价说清楚：存档里 `placedFurniture[].furnitureId` 记的是**家具**那一侧的 id
（`floor_lamp`），所以要改名的是**世界数据**。而 `restoreWorld` 会
**丢弃引用了未知家具的记录**——不迁移的话，老存档里摆着的家具会静默消失。
这是本次迁移最要紧的一条。

### 要改的只有一处

存档里引用 id 的地方全盘过一遍：

| 位置 | 存的是哪种 id | 要不要改 |
|---|---|---|
| `character.inventory[].itemId` | 物品 id | **不改**（留的就是物品 id） |
| `placedFurniture[].furnitureId` | 家具 id | **要改名** |
| `placedFurniture[].state.slotContents[].itemId` | 物品 id | 不改 |
| `placedFurniture[].state.lootTableId` | 战利品表 id | 不改 |
| `character.heldItem` | 物品 id | 不改（已废弃恒为 null） |
| `discoveredRecipeIds` | 配方 id | 不改 |
| `actionEntries[].actionId` | 行动 id | 不改 |

**结论：迁移 = 一张「家具 id → 物品 id」的改名表，作用在 `placedFurniture` 上。**

### 迁移条目（v9）

```ts
{
  to: 9,
  migrate: (save) => {
    for (const placed of save.ownWorld.placedFurniture ?? []) {
      placed.furnitureId =
        LEGACY_FURNITURE_ID[placed.furnitureId] ?? placed.furnitureId;
    }
    return save;
  },
}
```

`LEGACY_FURNITURE_ID` 是一张**写死的** 30 条对照表，就放在
`Data/Save/migrations.ts` 里，**不从注册表推导**——迁移表必须
冻结在写它的那一刻。从当前注册表推导的话，将来谁再改一次 id，
这条旧迁移的行为会跟着变，那是迁移最忌讳的事。

### 迁移的验收

1. 用改动**之前**的构建存一份档（屋里摆满家具、锅里煮着东西、背包有东西）
2. 切到改动**之后**的构建读它
3. 逐条核对：家具一件不少、锅里的内容还在、背包数量对得上
4. 再存一次、再读一次，确认不会二次迁移

### 顺带要改的代码（不是存档，但引用了旧 id）

- `seedInitialFurniture`（`cardboard_box` / `cardboard_stack`）
- `testRoom`（遍历 `furnitureDefinitions`）
- 已有迁移 v6/v7/v8 里写死的 `"stove"` 等字面量 —— **不要动**，
  那是历史，改了会让旧存档走错分支

## 四、分阶段计划

每阶段独立可验证、可单独回退。**每阶段做完先在浏览器里验一遍再进下一阶段。**

### 阶段 1 · Core 类型与注册表合并

- `ItemDefinition` 加 `visual` / `audio` / `placement` 三块
- `furnitureDefinitions` 的 30 条并进 `itemDefinitions`，
  家具 id 换成物品 id，`visualId` 挪进 `visual.id`
- `audioProfileId` 按语义拆进 `audio.ambient` / `audio.active`
- 加 `isPlaceable` / `findPlaceableItem`，旧函数名先保留做薄转发（本阶段不删）
- i18n 合并成一条

**验收**：`tsc` 双绿；游戏能起来；家具能摆能交互。

### 阶段 2 · 存档迁移

- 写 v9 迁移 + `LEGACY_FURNITURE_ID` 冻结表
- `SAVE_SCHEMA_VERSION` → 9

**验收**：老档读进来家具一件不少（照上面四步走一遍）。

### 阶段 3 · 拆掉旧路径

- 删 `placeableFurnitureId` / `findItemByFurnitureId` / `findFurnitureDefinition`
- 调用方改查 `placement`

**验收**：全仓库 grep 不到旧函数名；`tsc` 双绿。

### 阶段 4 · 视觉三表合一

- `INGREDIENT_SHAPE` 的 9 条改写成正式视觉配方
- 主色改成从模型取，删 `INGREDIENT_COLOR`
- `buildItemVisual(itemId)` 统一入口，手上 / 锅里都用它
- 家具物品自然就有模型了（`visual.id` 指的就是原来的家具模型）

**验收**：手上拿番茄看得见番茄（现在看不见）；锅里的鸡蛋和现在一样。

### 阶段 5 · 切块形态 + 兜底出声

- 通用切块生成器（主色 → 几块小楔形）
- 生食材下锅用切块，成品菜用整形态
- 查不到视觉配方 → 中性色块 + **控制台点名一次**（同一个 id 不刷屏）

**验收**：番茄下锅是切块；控制台能列出还缺哪些模型。

### 阶段 6 · 补模型

按缺失清单补 C 类那 24 件。**不一次补完**：先食物（13 件，要下锅要拿手上），
材料（11 件）排后面。

## 六、不做的事

- **不做类继承**——用能力块，理由见第二节
- **不给每道菜建模**——成品菜就是一个物品
- **不做「生/切/熟」三态全 authored**——切块自动生成，熟态由成品物品承担
- **不做贴图 / PBR**——整套画风是低多边形 + 平面着色
- **不一次补齐 24 件模型**——结构先对，缺的在控制台点名

## 七、边界

| 关注点 | 位置 | 加内容时改什么 |
|---|---|---|
| **有哪些东西** | `Core/src/Data/items` | 加一条定义 |
| **长什么样** | `Game3D/Visual/VisualRegistry` | 加一条配方 |
| **发什么声** | `Core/src/Data/audio` + 物品上的 `audio` ref | 加一条定义 + 填一个字段 |
| **什么时候显示 / 什么时候响** | `HeldItemView` / `CookwareView` / `Soundscape` | 通常不用改 |

**加一件能拿、能摆、能下锅、会响的东西 = 数据一条 + 视觉配方一条，代码零改动。**

反面教材：不要再为「某个场合要显示某个东西」新开一张表——
这份文档要还的债，就是上一次这么干欠下的。

## 八、后续定案：厨具也是家具（2026-07-31 追加）

> 阶段 3 做完之后定的，**排在阶段 4/5 之后做**。

**决定**：厨具与盛器（锅、高锅、盘）也带 `placement`，可以摆在屋里任何地方，
**只有摆在带 Cooking 能力的地方才加热**。

### 岔路在哪

现在"世界里的一口锅"只有一种存法：灶眼的 `slotContents[slotId]`，
锅里的菜和火候挂在 `state.container` 上。直接给厨具加 `placement` 的话，
地上那口锅会变成 `placedFurniture[]` 里的记录——**同一口锅有了两种表示**，
正是这份文档在还的那笔债（落地灯存两遍）。

### 定的是哪条

锅永远是放置物，**"在灶眼上"只是一种位置**：

- `FurniturePlacement` 加第三种 kind：`{ kind: "slot", hostInstanceId, slotId }`
- 锅的内容统一进 `PlacedFurnitureState.container`，`slotContents` 删掉
- 加不加热不用新写规则——`slotHeatsCookware` 现在就是"看所在家具有没有
  Cooking 能力"，只是输入换个来源
- 存档 v10：把 `slotContents` 里的容器搬成独立的 `placedFurniture` 记录

依据是市面通行做法都是这个形状：Overcooked 的锅在台面和在灶眼是同一个物件、
只有灶眼加热（`FurnitureSlot` 的注释本来就写着"对应 Overcooked 式流程"）；
Stardew 的桶和炉子是放置物自带 `heldObject`；Minecraft 熔炉是方块 + 物品栏。
**没有一个把"在机器上"和"在地上"分成两套数据。**

顺带解决：以后的砧板、盘架、面包机不用各写一套；锅摆桌上当摆设自然成立。

### 不选另一条的理由

"只有空厨具能放地上"能一天做完、零存档风险，但端着一锅汤放不到桌上，
玩家会当成 bug 而不是规矩；而且两种表示仍然并存，只是被规则挡住看不见。

### 顺带定的小事

锅碗的 `placement`：占地 1×1、`blocksMovement: false`、`floorLayer: Object`。
不挡路——一口锅绊不住人，做成挡路的话地上随手一放就把过道堵死。
