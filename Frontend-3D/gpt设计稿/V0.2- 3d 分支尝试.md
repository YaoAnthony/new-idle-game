# V0.2 — 3D 分支尝试

> 状态：**讨论中的草案**，不是已实现的代码。
> 本文件随讨论持续修改，`待定事项` 一节记录还没拍板的问题。

## 这个分支是什么

`Frontend-3D/` 是 `Frontend/` 的完整拷贝，用来验证一个问题：

**把 V0.2 的游戏架构用 Three.js 做成 3D，是否比 top-down 2D 更合适。**

`Frontend/`（2D + Phaser）保持冻结不动，作为回退方案。两边同时存在，直到 3D 验证结论明确。

## 项目定位（影响后面所有取舍）

**这是一个专注陪伴工具，包着奇幻生活游戏的外壳。**

游戏里的"行动"就是玩家**现实中真的要做的事**——任务表单里的例子是"写完 assignment2"，
时长由玩家自己设定。你设定两小时写作业，屋里的角色也坐下来写，白噪音响起，
然后你真的去写。

文档里的这几条线索都指向同一个方向：

- 关键词包含"听音乐、正常白噪音、睡觉白噪音"
- 行动分类是运动 / 工作学习 / 创作 / 休息——现实生活的四类活动
- "做任务可以获得一些现实的物品"，第一份奖励是奶酪和铁块，
  而吱吱从没见过奶酪：**"现实行动获得的奖励，可能是这个世界没有的东西"**

### 由此决定的优先级

| 高优先级 | 低优先级 |
|---|---|
| 专注模式的画面质感与安静感 | 家具种类的数量 |
| 白噪音 / 环境音的层次 | 战斗、数值成长深度 |
| 房间的"待着舒服" | 复杂玩法系统 |

奇幻屋子、宠物、家具是**情感奖励层**——它们的作用是让人愿意回来，
而不是让人沉迷于优化数值。3D 的价值也应该按这个标准衡量：
它让"待在这个房间里"更舒服了吗？

### 任务可离线，但陪着有奖励

任务用绝对 UTC 推进（`ActionProcessSave.startedAtUtc` + `durationMinutes`），
**关掉游戏也会照常完成**——不惩罚忘记关标签页的人。

但**陪着有额外奖励**，用奖励而不是锁定来引导真正的专注。

判定口径**刻意做得很松**：

- 只要游戏没关掉就算陪着，不检查标签页是否在前台
  （现实场景本来就是"一边写作业一边把游戏开在旁边屏幕"）
- 中途离开去上厕所、回消息，都不算破功
- 不做"功亏一篑"的阈值判定，不制造焦虑

奖励是**情感回报**而不是数值：宠物走过来陪着、事后好感度提升。
这正好对上 `整体架构.md` 里既有的措辞：

> 好感度只会在经历一些宠物事件以及**陪伴事件**后发生变化。

#### 这个宽松口径顺带消掉了一个类型缺口

原本以为要给 `ActionProcessSave` 加"累计前台时长"字段。
但既然不追踪时长、只看"任务完成的那一刻游戏还开着吗"，
那它就是一个**运行时事件**，不需要持久化任何东西：

- 游戏开着 → 任务完成瞬间触发陪伴事件，宠物有反应
- 游戏关着 → 重新打开时任务已按 UTC 正常完成，只是没有那次情感互动

`ActionProcessSave` 不用改。

## 为什么现在切成本最低

当前 2D 实现的实际进度：

- `src/Game/Features/Scene/GameScene.ts` — 空文件
- `src/Game/Features/Scene/world/initialhouse.ts` — 只有一个空注释块
- `Core/src/Data/furniture`、`Core/src/Data/items` — 空数组
- 唯一跑起来的是 `GameStart.ts`（标题背景图 + 萤火虫粒子）

也就是说 **gameplay 一行都还没写**。现在切换渲染器几乎零成本，往后每写一周 2D 玩法代码，成本就涨一截。

## 3D 对本作的具体好处

V0.2 文档里自己标出的最难的问题，在 3D 里是免费的：

> 墙饰要特别小心：top-down 2D 里"墙"不是普通地板格。……否则以后会很难处理遮挡、深度排序和点击选择。

| V0.2 的需求 | 2D 的做法 | 3D 的做法 |
|---|---|---|
| 墙饰与地饰分层 | 手写独立放置层，自己管遮挡 | 墙是真几何体，z-buffer 免费处理 |
| 深度排序 | 按 y 手动排序，多格家具和高家具容易出错 | 深度缓冲免费 |
| 点击选择家具 | 手写命中测试 | raycast 免费 |
| 音效墙体遮挡 + 距离衰减 | 全部手写 | `PositionalAudio` 原生衰减 + raycast 检测遮挡 |
| 1楼/2楼 | 独立场景或独立 tilemap | 就是 Y 轴 |
| 换墙纸 | 换图集 | 换材质 |
| 拍照功能 | 需要专门做截图合成 | 第二个相机 + renderTarget |

## 已确定的方向

### 画风

低多边形 + 平面着色 + 白色描边，参考图是户外低多边形场景（灯塔 / 帐篷 / 篝火 / 低面数树）。

拆解：

| 元素 | 做法 |
|---|---|
| 几何体 | Three.js 内置图元组合：`IcosahedronGeometry`(低细分)、`CylinderGeometry`、`ConeGeometry`、`BoxGeometry` |
| 着色 | `flatShading: true` + `MeshLambertMaterial`，不用 PBR、不用贴图 |
| 描边 | **浅色描边**（同参考图）。做法：inverted hull——复制网格放大、翻转法线、浅色 `BackSide`。注意这会让渲染量翻倍，需做成可开关 |
| 天空/远景 | 渐变色 + fog |
| 雨/风 | 粒子系统 |

**这个画风最大的优势：几乎不需要 3D 建模软件。**桌子 = 板子 + 四条腿，工作台 = 箱体 + 台面 + 架子，树 = 低面数球 + 圆柱。全部能用代码描述（见下方"程序化家具配方"）。

### 相机与墙（2026-07-29 第三次修订：镜头锁定屋内 + 真实屋顶）

> **推翻"漂浮展示盒"。**确定改为：**镜头严格锁在屋内，永不穿墙；
> 房间有真实天花板（含横梁）；真室内光——窗户是主光源。**
> 理由：镜头被关在屋里，"待在这个房间里"的包裹感强得多，
> 和"专注陪伴工具"的定位更贴。

实现要点：

- **经典肩后视角**：镜头方位角自动回到 `角色朝向 + 180°`，走路时永远看着背影，
  并有 0.5 的横向肩后偏移（角色偏在画面一侧而不是正中）
- ⚠️ **回中必须按"前进程度"加权，否则会自激**：WASD 是相机相对的，
  如果按住 A 时相机也跟着角色左转，"左"就一直在变，人会原地画圈。
  `forwardness`（纯 W=1／横走=0／后退=0）当权重后：往前走镜头跟到背后，
  横走和倒退镜头钉死。实测长按 W 到 1.5s 和 3.0s 数值完全一致，收敛无残留漂移
- Q/E 手动转镜后有 2.5s 冷却不自动回中；对话/专注/过场（`mode !== "follow"`）
  完全不回中，免得把推近的构图搅乱
- **相机约束：水平和垂直分开处理**，这是肩后视角能用的关键。
  角色贴墙站时"背后"就在墙里，若只会沿视线整体回缩，镜头会一路贴到后脑勺上
  （实测就是这样）。改为**撞墙只压水平距离、把省下的量还给高度**——
  镜头从上方越过肩膀往下看，构图还在。天花板同理只夹高度，
  夹了之后俯角自然变平（16×12 房间中央实测有效俯角 32°→23°，反而更像肩后视角），
  缩放行程也不会被卡死
- 出生点从贴着西门（x=-6.6）挪进屋里（x=-4.5）：贴墙时镜头被迫抬高俯拍，
  开局第一帧会变成头顶特写
- **墙高 4 格**（原 3 格）：给室内相机留头顶空间。存档迁移 v2 同步旧档
- **窗洞 2×2**（原 2×1）：窗户成为主光源后进光面要够大；窗帘（2×2）正好整扇盖住
- **天花板**：逐格 quad 只渲染朝下的面，每 4 格一条深色横梁；`castShadow: true`
- **真室内光**：墙和天花板真的挡光（单面墙靠 three 默认 shadowSide 规则投影），
  太阳全天在北侧（窗户侧，方位角 140°~222°）、仰角压低（11°~36°），
  光柱从窗洞探进屋里；半球光/环境光降为室内基底；
  灯具配方内嵌 `lamp-light` 点光，黄昏半亮、入夜全亮（动森式自动灯）
- **删掉的东西**：`FurnitureView.updateWallVisibility`（墙饰跟随剔除）、
  `applyWallVisibility`、`WALL_HEIGHT` 常量——相机永远在屋内，这些全成了死代码
- **已知代价**："缩放最远一眼看全屋"没有了（室内视角物理上看不全 16×12）。
  布置模式维持锁屋内（用户拍板），摆大房间靠走动查看

下面保留前两版方案的记录，作为决策历史：

### ~~相机与墙（M2 后修订：第三人称自由视角）~~（已被上方修订取代）

> **2026-07-28 实机后推翻了动森式方案。**M2 玩起来之后确定改为：
> **四面墙全保留 + 第三人称跟随相机 + FOV 50 + 自由移动。**

实现要点：

- 相机跟在角色身后（俯角 32°，距离 3~16 可缩放），Q/E 环绕 45° 步进
- **墙只渲染朝屋内的面**（背面剔除）：相机拉到墙外时，那面墙自动"透明"看进屋。
  四面墙都真实存在，却永远不挡视线——不需要墙体隐藏、不需要淡出、不需要相机碰撞
- 窗外天空板同样只朝屋内渲染，从墙外看不到穿帮
- 原动森式的"档位对照表隐藏两面墙"逻辑整体删除

### ~~相机与墙：动森式~~（已被上方修订取代）

**透视投影 + 窄 FOV（约 30°）**，固定斜角俯视，**永远只渲染背对相机的两面墙**。

选透视而非正交，是为了贴近参考图的观感。窄 FOV 能把透视变形压得很小，
接近正交的稳定感，同时保留一点纵深——摆家具时的对齐判断不会受太大影响。
动森室内用的也正是这个组合。

#### 这个选择消掉了整个"墙淡出"子系统

原本考虑的是"可旋转相机 + 靠近镜头的墙自动淡出"（模拟人生式）。
改成动森式之后，**相机永远待在房间外侧的一个角上方，不会转到墙背后**，
所以不存在"墙挡住视线"的情况，也就不需要：

- 逐面墙的透明度插值
- 半透明材质（在低多边形平面着色下本来就容易显脏）
- 墙饰跟随淡出的协调逻辑

省掉一整个 `WallVisibility` 系统。

#### 旋转做成 90° 档位

需要看别的墙时，相机按 90° 档位跳转（带一个短转场），
切换后换成另外两面墙可见。实现上就是：

1. 每面墙是一个 `Object3D` 组，**墙上的装饰挂在这个组底下**作为子节点
2. 当前相机档位 → 决定哪两面墙 `visible = true`
3. 墙饰是子节点，自动跟着显示/隐藏，不用单独处理

这正是 `WallFurniturePlacement.wallId` 这个字段设计得好的地方。

#### 取景：相机跟随角色 + 可缩放平移

动森房间约 8×8，正因为小，固定相机才能一屏看全。16×12 一屏看全的话家具会太小，
所以**房间比屏幕大，镜头跟着角色走**，并支持缩放和平移。

关键：**相机只平移，朝向永远不变**（除了 90° 档位切换）。
所以"哪两面墙背对相机"这件事不会因为角色走到哪里而改变，
`WallVisibility` 依然是一张静态的档位对照表，不需要任何动态判断。

即使角色走到房间最南端、相机跟到屋子外面去了，也没关系——
南边那两面墙本来就不渲染，相机"穿过"它们不会看到穿帮。

设计上的小补偿：把**缩放的最远档设成刚好框住整个房间**。
这样"一眼纵览自己的家"这个装饰游戏的核心爽点没有丢，只是变成了一个主动操作。

### 房间与网格尺寸

| 项目 | 取值 |
|---|---|
| 1 网格 | 1 世界单位（约等于现实 1 米，一把椅子占 1×1） |
| 初始房间 | **16 × 12 格**，一整块矩形，不做建筑隔断 |
| 墙高 | 3 格 |
| 角色身高 | 约 1.7 格 |

选大房间（16×12）和 `整体架构.md` 的**分区设计**是对上的：

> 化肥箱可以允许你把过期食物放进去……但是化肥箱很臭。**如果你只有一个区域，就不能制造化肥箱**，因为太臭了，玩家没办法住。

厨房区也是被当作独立区域描述的。所以 16×12 不是"一个空旷的大矩形"，
而是**一块可以被玩家自己划分成多个功能区的场地**（起居 / 厨房 / 工作 / 睡眠）。

分区靠家具和地毯自然形成，不做建筑上的隔断——`RoomSave` 保持单一 room，
放置逻辑最简单，玩家自由度也最高。

> 注：文档里"区域"（比如化肥箱要求的独立区域）之后可以做成**逻辑分区**——
> 玩家在地上圈定的功能区，而不是物理墙体隔开的房间。这样不牵动几何和寻路。

### 3D 场景怎么生成

Core 的 `generateRoom` 只产出**数据**（地板尺寸、四面墙、门窗开口的位置与尺寸）。
从数据变成网格体是 `Game3D/World/RoomBuilder` 的活，具体做法：

| 部位 | 做法 |
|---|---|
| 墙 | **薄片，无厚度**——一张立起来的面，渲染最省。窗洞后面直接就是景深盒 |
| 屋顶 | **不做**。动森式俯视直接看进屋里，房子感靠墙和家具建立 |
| 窗洞 | **用几块矩形拼出带洞的墙**，不引 CSG 布尔运算库——所有洞都是矩形且对齐网格，拼接足够 |
| 地板 | **分块**：逐格生成，每块颜色在基色附近轻微抖动，形成木板拼缝感 |
| 墙面 | 同样分块，制造深浅差 |
| 房间外围 | 纯背景色，随昼夜变化 |

分块是低多边形风格的标志，而且**纯代码生成、不需要任何贴图**。
16×12 的地板如果是一整块纯色会显得很空。

### 宠物占位造型

现阶段用 **5-8 个图元**拼极简团子：大头小身 + 耳朵 + 黑点眼 + 尾巴。
低多边形的"可爱"主要来自比例（头大、眼睛低而大），不是细节量。

#### 以后换精模的路径已经通了

`visualId` 间接层就是为这件事存在的：

```
今天： "chinchilla_baby" → { kind: "procedural", recipe: 团子配方 }
以后： "chinchilla_baby" → { kind: "gltf", url: "/models/chinchilla.glb" }
```

换模型只改 VisualRegistry 一行，Core、存档、寻路、好感度逻辑全都不动。

两个要提前知道的坎：

- **动画比模型更难**。带骨骼动画的 GLTF 可以用 `AnimationMixer` 直接播；
  但如果买到的模型不带动画，绑骨骼和做动画是专业活
- **风格会打架**。ACNH 是圆润造型 + 柔和着色，本作定的是硬边多面 + 平面着色 + 描边。
  真要换 ACNH 风格的宠物，房间也得跟着变圆润——那是另一套画风。
  已确认：**房间继续按参考图做硬边低多边形**

### 房间边界与窗户

**房间是一个封闭的盒子，玩家和视野都限制在屋内。不做室外场景。**

相机虽然物理上位于房间外侧上方（动森式斜角），但它只用来看进屋里；
房间之外没有可探索的世界，整体是一个"漂浮的展示盒"。

**窗户是唯一的对外通道**——天气、昼夜、外面世界的存在感，全部只能靠窗户传达。

这条设定把窗户的分量抬得很高。参考现有的像素标题背景图：
那个大圆窗外的森林和暮色，几乎是整张图的情绪来源。所以窗外不能只是一块死色板，
需要能随**天气**（雨 / 风 / 晴 / 阴）和**昼夜阶段**变化。

#### 房间外围：纯背景色

相机能看到的房间之外，就是一整块干净的背景色，**不做室外几何、不做地面**。
房间像一个漂浮的展示盒（动森室内的做法）。背景色本身随昼夜阶段变化。

#### 窗外：景深盒

每扇窗后面放一个浅浅的"盒子"，由几个面片组成：

1. **天空底**——纯色面片，颜色由昼夜阶段 + 天气决定
2. **远景剪影**——低多边形的树 / 山轮廓，比天空底更靠近窗户，制造纵深
3. **雨 / 风粒子**——只在对应天气时启用，发射器放在盒子里

成本很低（就几个面片 + 一个粒子发射器），但因为有前后层次，
镜头移动时会产生轻微视差，比贴一张平面图有"外面真的有个世界"的感觉。

窗户在 3D 里是真实几何体，所以"离窗户多近"可以直接用世界坐标距离算——
V0.2 音效系统要求的"越靠近窗户环境音越清晰"是免费的：

> 环境音应当检查存档的天气和房子的 type 播放，并且会找寻窗户和门的位置，
> 越靠近这两个地方，玩家应该能听到更清晰的环境音，如雨声等

### 光照与昼夜

**变暗但有下限，点灯能改善。**

夜里屋内偏蓝变暗，但保底亮度不会低到看不清家具——毕竟现实里的深夜正是这个游戏
最可能被打开的时段。点亮灯具后局部明显回暖，`FurnitureCategory.Lighting`
因此是有真实功能的家具，不只是摆设。

实现（受"手机能跑"预算约束）：

| 光源 | 作用 | 阴影 |
|---|---|---|
| 方向光 × 1 | 模拟从窗户进来的天光，颜色/强度/角度由 `dayPhase` 驱动 | 投阴影 |
| 环境光 | 保底亮度，夜间降到下限并偏冷 | — |
| 点光源（灯具） | 每件 Lighting 家具一盏暖色点光 | 不投阴影 |

### 天气对屋内的影响

天气不只是窗外的画面，要真的渗进屋里——雨天是最治愈的天气，
而"待在这个房间里舒服"是本作的高优先级目标。

| 层面 | 表现 |
|---|---|
| 光线 | 雨天 / 阴天时方向光减弱、环境光偏冷；晴天明亮偏暖 |
| 声音 | 环境音随天气切换，音量随**距窗户和门的距离**变化（V0.2 已有此要求） |
| 窗玻璃 | 雨天窗上有水痕缓慢流下（玻璃面片上做 UV 滚动，成本很低） |

家具级的天气反应（雨后植物滴水、刮风天风铃响）文档里也写过，
但那要逐件家具配反应表，放到家具内容填充阶段再做。

#### ⚠️ 顺带发现：灯具的开关状态没地方存

如果灯要能手动开关，`PlacedFurnitureState` 里没有合适的字段
（现有的是 `durability` / `storageInventoryId` / `activeProcessId` / `customVisualId`）。

**第一版建议：灯具入夜自动亮、天亮自动灭**（动森就是这样），
不需要改 Core 类型。之后确实需要手动开关时，再加一个状态字段。

这同时也呼应 V0.2 音效系统的要求：

> 环境音应当检查存档的天气和房子的 type 播放，并且会找寻窗户和门的位置，
> 越靠近这两个地方，玩家应该能听到更清晰的环境音，如雨声等

窗户在 3D 里是真实几何体，"离窗户多近"可以直接用世界坐标距离算，
环境音的空间感是免费的。

### 角色与宠物

**全部 3D 建模**（不用 2D 立绘面片）。

⚠️ 这是整个方案最大的成本中心，见"风险与成本"一节。

#### 主角：捏人系统（发型 / 衣服 / 配色自由搭）

配合拍照和联机确实值得——照片里那个人得是"你"。

**由此产生的架构硬约束（现在就要遵守）**：

`CharacterView` 必须**从零件拼装**，不能是一个整体模型：

```
角色 = 身体(可染色) + 发型(可替换) + 上衣(可替换,可染色) + 下装 + 鞋
```

每个部位是独立 `Object3D`，材质颜色由配置驱动。
如果第一版图省事做成单个整体模型，之后加捏人等于全部重做。

#### 角色动画：程序化 + 预设姿势

不做骨骼动画（换装零件全要绑到同一套骨骼上，而且这超出我能交付的范围）。

| 类型 | 做法 |
|---|---|
| 持续动作（走路、待机） | 代码直接驱动部件：腿前后摆、身体上下颠、手臂反向摆、呼吸起伏 |
| 姿态动作（坐、睡、学习、举家具） | 每个姿势是一组部件 transform 的快照，切换时插值过去 |

关键好处：动画操作的是**"左腿"这个槽位**而不是某个具体模型，
所以捏人换了发型换了衣服，动画自动适配，不用重做。

姿势数据是配置不是硬编码（`AGENTS.md` 要求内容不得写死在 gameplay 脚本里）。

#### ⚠️ Core 类型缺口 3：`avatar: string` 装不下捏人配置

```ts
PlayerSave = {
  name: string;
  avatar: string;   // ← 一个字符串放不下"发型3+上衣5+主色#c86"
  ...
}
```

两种改法，实现时定：

- `avatar` 改成结构化对象 `AvatarConfig { hairId, topId, colors: {...} }`
- 或 `avatar` 保持字符串当索引，配置另存一处

这是第三个由 3D 逼出来的类型缺口（前两个：锅放灶台上、灯具开关状态）。

### 装修系统：换整套房间几何

> 房子装修可以切换森林 / 海洋 / 石砖风格

三种风格是**三套不同的房间几何**（海洋系可能是圆拱顶、森林系是圆木梁），
不只是换配色。视觉冲击最强。

架构要求：`RoomBuilder` 必须由**风格配方**驱动，不能把某一种房间的几何写死。
风格配方描述：墙体剖面、屋顶形状、窗框样式、地板拼法、配色。

氪金的"换墙纸"是这套系统的轻量版——只替换配色部分，不动几何。

#### 换风格后的家具处理：能留的留，冲突的退回背包

换风格时跑一遍全量重校验：

1. 用新风格的网格和墙位，逐件校验 `placedFurniture`
2. 仍然合法的**原位保留**（地面家具大多数属于这类）
3. 悬空、压进墙里、或落在新风格没有的格子上的，**退回背包并明确告诉玩家**

校验函数放 `Core/src/logic/placement.ts`，和放置系统共用同一套规则——
Backend 校验联机存档时也是同一份代码。

#### 三种风格同时也是新建世界的随机结果

> 每个玩家会以"租到房子"的名义来到一间房子里。玩家会被**随机分配到初期可选的 3 个地区之一**，
> 并随机进入某一种屋子开始生活。
> 比如，如果是**森林系的屋子**，你可能会发现一只龙猫正躺在角落里呼呼大睡。

`seed` 随机决定三件事：**地区 → 屋子风格 → 初始宠物物种**。
森林系屋子配龙猫，海洋系配水生宠物——这解释了文档里那句"森林屋里躺着龙猫"。

好处是**装修系统和开局随机共用同一套数据**：三种风格的房间几何配方只做一份，
既用于新建世界时按 seed 选一个，也用于之后解锁装修后切换。

注意 `整体架构.md` 说装修要先解锁：

> 初期，房子的布局一直不变。但未来会认识一个生物，它可以帮助你装修房子。

所以开局风格是随机且锁定的，解锁装修后才能换。

#### ⚠️ Core 类型缺口 4：`HouseSave` 没有风格字段

```ts
type HouseSave = {
  houseId: HouseId;
  regionId?: string;
  // 缺 styleId
};
```

### 事件镜头：完整过场系统

> 制作好之后，突然出现突发事件，**镜头开始移动**，然后你会发现一个可爱的小动物

镜头完全接管，玩家暂时失去控制，直到事件结束。

架构要求：`CameraRig` 需要**模式系统**，而不是只有一个跟随逻辑：

| 模式 | 行为 |
|---|---|
| `follow` | 常态，跟随角色，玩家可缩放/旋转 |
| `cutscene` | 事件接管，沿脚本路径运镜，玩家输入被屏蔽 |
| `decorate` | 布置模式，自由平移 |

过场内容必须**数据驱动**（镜头路径、时长、缓动曲线、期间锁哪些输入），
不能写死在 gameplay 脚本里——这是 `AGENTS.md` 的硬性要求：

> 不得在 gameplay scripts 中 hardcode 内容、物理按键、用户可见文本……

### 多楼层：现在留维度，只渲染一层

> 一个游戏的存档地图应该是可以储存多个页面的，比如屋子出现1楼2楼等，我们初期留接口就可以

3D 里楼层就是 Y 轴。现在把维度留出来几乎免费，以后再加则要动 `RoomSave`、相机、
墙可见性、寻路四处，很烦。

第一版：数据结构带 floor 维度，相机 / 墙可见性 / 寻路的函数签名都预留 floor 参数，
但**实际只构建和渲染一层**。

### 做任务：镜头推近，进入专注模式

角色开始做任务时（学习 / 运动 / 创作 / 休息），镜头推近到角色和它使用的家具，
画面安静下来，配合白噪音。

复用 `CameraRig` 的模式系统（和事件过场、对话推近同一套机制）。

### 音乐与白噪音：屏幕 UI 播放器

游戏关键词里的"听音乐、正常白噪音、睡觉白噪音"做成**屏幕上的播放器面板**，
随时可调出来切曲、调音量，不需要走到某件家具旁边。

注意这与 V0.2 音效系统里的**家具环境音**是两套东西，不要混：

| | 播放器音乐 / 白噪音 | 家具环境音 |
|---|---|---|
| 空间化 | 否，全局播放 | 是，距离衰减 + 墙体遮挡 |
| 控制方式 | 屏幕 UI | 走近家具自然听到 |
| 例子 | 背景音乐、雨声白噪音 | 壁炉噼啪、鱼缸气泡、风铃 |

### 宠物移动：格子 A* 寻路

好感度的表现几乎全靠宠物的空间行为：

> 开始睡在玩家附近 / 玩家做任务时在旁边陪着 / 朋友来访时不再躲起来

这些都要求宠物能**真的走到某个位置**，所以用 A* 寻路，不是随机游荡。

好处是**零额外数据**：房间本来就是 16×12 网格，家具占格本来就要算（放置系统在用），
宠物寻路直接复用同一张占用图。

两个实现细节：

- A* 输出的是格子路径，渲染时在格子中心之间做平滑插值，宠物不会一格一格地跳
- 占用图要区分**完全阻挡**（柜子）和**可落脚目标**（椅子有 `Sitting` capability，
  提供可坐坐标；床可以睡上去）。否则宠物永远走不到椅子上

### 宠物派遣：走到门口，开门出去

不做室外，但派遣要有仪式感：宠物 A* 寻路走到门口 → 门打开 → 宠物走出去 → 门关上。

**门外就是未知**——这恰好和"不做室外场景"的设定自洽，
不是妥协，而是让门成为一个有分量的边界。回来时反向播放。

要求：门是房间里真实的几何体（有开合动画），并且是寻路的合法目标点。

### 对话：底部对话框 + 镜头拉近

镜头轻微推近到宠物，屏幕底部出对话框（动森做法）。
长对话好读，"了解它的性格"这个核心体验也需要看清表情。

镜头推近复用 `CameraRig` 的模式系统（和事件过场同一套机制），不另起炉灶。

### 世界内 UI：浮在 3D 容器上方

进度条、按 F 提示、饭熟了的图标——都浮在对应家具的上方，
而不是集中到屏幕边缘的面板里。一眼就知道是哪个东西在动。

实现是一个 world-to-screen 投影组件：

```ts
useWorldAnchor(object3D) → { x, y, visible }
```

把 3D 坐标投影成屏幕坐标，React 组件跟着定位。注意两点：

- 用 CSS `transform` 更新位置，不要改 `top/left`（避免触发重排）
- 被墙或家具挡住时要能隐藏，靠深度测试或 raycast 判断

全局信息（饥饿 / 疲劳 / 时间）仍然固定在屏幕角落，不浮空。

### 拍照功能

**分两种，来源不同：**

| 场景 | 做法 |
|---|---|
| 在家拍照 / 和朋友合影 | **游戏内真实渲染截图**——拍的是玩家自己布置的家，有感情，风格也天然统一 |
| 宠物带相机出门带回的照片 | **LLM 生成**——那些地方我们根本没建模，只能生成（暂不做） |

3D 让前者变成免费的：第二个相机 + `renderTarget` 就是一次拍照。

### UI

**像素风 UI（标题页、按钮、面板）暂时不动**，先把 3D 场景做出来，等看到实际画面再决定 UI 风格是否要统一。

UI 是 React DOM 覆盖层，与渲染器无关，不会因为换 Three.js 而失效。

### 标题页

**移除 Phaser**，标题背景改成 3D 实时房间（缓慢环绕的镜头）。

好处是一个渲染器跑到底，不用在项目里同时维护两套引擎；
而且标题页本身就成了画风的展示位，做完立刻能判断方向对不对。

### 目标平台

**桌面优先，手机能跑就行。**

由此推出的技术约束：

- 实时阴影只用一盏方向光，不做多光源阴影
- 描边优先用 inverted hull（不依赖后处理管线，移动端更稳），
  后处理 Sobel 作为备选方案，两者可切换
- 重复家具用 `InstancedMesh`
- `devicePixelRatio` 上限锁 2
- 不叠加大型后处理栈（bloom / SSAO 一类先不上）

## 与 Core / V0.2 数据契约的关系

### 结论：Core 一行都不用改，存档零迁移

V0.2 的数据契约描述的是**一个网格世界**，不是像素画面：

```ts
GridPosition { x, y }
GridFootprint { width, height }
Facing
PlacementSurface.Floor | PlacementSurface.Wall
```

"3 号格子上有一张朝北的桌子"——这句话在 2D 和 3D 里含义完全相同。2D 渲染成精灵图，3D 渲染成网格体，**`PlacedFurniture` 存的字节完全一致**。

唯一变化的是 `visualId` 怎么被解释，而那是 Frontend 的事。

### Core 类型影响汇总

讨论过程中一共摸出 5 个缺口。**它们都不是 3D 引入的**——2D 同样存在，
只是 2D 可以靠"画在上面""反正看不出来"糊弄过去，3D 逼着它们显形。

| # | 缺口 | 状态 |
|---|---|---|
| 1 | 锅放灶台上、盘子放桌上 | ⚠️ **需要改**（订正）：走槽位方案后不必动 `PlacementSurface`，但槽位内容仍需一个字段 `PlacedFurnitureState.slots` |
| 2 | 灯具的开关状态没字段可存 | ✅ **已消解**：入夜自动亮，不需要持久化 |
| 3 | `PlayerSave.avatar: string` 装不下捏人配置 | ⚠️ **需要改**：改结构化对象，或字符串当索引另存配置 |
| 4 | `HouseSave` 没有 `styleId` | ⚠️ **需要改**：加一个字段 |
| 5 | `ActionProcessSave` 没地方记录陪伴时长 | ✅ **已消解**：判定口径放松后变成运行时事件 |
| 6 | **`WallSave` 没有门窗** | ⚠️ **需要改**：加 `openings: WallOpening[]`，见"房间信息怎么存" |
| 7 | **`WeatherSave` 严重滞后于 V0.5 设计** | ⚠️ **需要重写**：见下 |
| 8 | 没有 `WeatherDefinition` 类型 | ⚠️ **需要新增**：V0.5 已给出完整定义 |

#### 缺口 7 详情：天气存了不该存的东西

```ts
// Core 现在
type WeatherSave = { currentWeatherId: WeatherId };
```

但 `V0.5 - 天气系统.md` 明确写着：

> 这里最重要的是：**天气不应该一直保存"现在是什么天气"**。
> 当前天气应该由 Clock → 世界时区 → `WorldDayId` + 天气 seed → override 推导

和时钟是同一个哲学（不存当前时刻，只存推导依据），但 Core 存的恰恰是当前天气。
V0.5 给的正确结构是：

```ts
type WeatherSave = {
  seed: number;
  lastResolvedWorldDayId: WorldDayId;
  schedule: WeatherScheduleEntry[];      // 当天的天气安排
  overrides: WeatherOverrideSave[];      // 事件/天气瓶/家具的临时覆盖
};
```

这是唯一一个**需要改结构而非加字段**的缺口，但因为还没有任何存档，现在改零成本。

#### 天气对 3D 表现层的额外要求

V0.5 里这几条是 3D 要做的活：

- **刮风天**要让风铃响、窗帘动、树叶动 → 家具需要"天气反应"数据
- **天气瓶**支持 `scope: "room"` → 房间级天气覆盖，只改这个房间的窗外景深盒和光照
- 暴雨是 `救助大河` 事件的触发条件之一 → 天气要能被事件系统读取

需要真的动 Core 的是 1、3、4、6，**全部是加可选字段，没有改结构、没有破坏性迁移**，
老存档给默认值即可（`slots: {}`、`openings: []`）。

其中 6 是最重要的一个：门窗不只是装饰——窗户是唯一对外通道、要挂景深盒、
环境音按距窗距离衰减；门是宠物派遣的寻路目标。**没有它整个房间是个密封盒子。**

### Core 需要新增的部分

不是改，是补。目前 `Core/src/` 只有类型和空注册表，建议补上**纯网格数学**：

```
Core/src/logic/
  occupancy.ts    footprint + facing → 占用哪些格子
  placement.ts    这个位置能不能放？（纯函数，不依赖任何渲染器）
```

放 Core 的理由：`AGENTS.md` 写了"Backend 不得复制一份独立的内容规则"。联机时房主世界的放置必须由服务端校验，两边必须跑同一份代码。而且纯函数可以脱离浏览器做测试。

## 工程结构

三层分离，**关键约束：只有最内层能 import three**。

### 四层，每层有明确的禁止事项

| 层 | 职责 | 禁止 |
|---|---|---|
| `Core/` | 共享类型、内容注册表、纯规则 | 任何渲染器、DOM、浏览器 API |
| `Data/` | 持久化：存档读写、迁移、设置 | 游戏逻辑、three |
| `Game/` | 游戏逻辑：状态、系统、事件 | **three**、DOM |
| `Game3D/` | 渲染：场景图、相机、材质、交互 | 直接改存档（只能发事件） |
| `Components/` | React UI | three（除了容器挂载） |

"Game 层禁止 import three"这条要**用 ESLint 强制**，不能靠自觉：

```js
// eslint.config.js
{
  files: ["src/Game/**"],
  rules: { "no-restricted-imports": ["error", { patterns: ["three", "three/*"] }] }
}
```

### 数据流向是单向的

```
用户输入 → Game3D/Interaction → EventBus → Game/Systems
                                              ↓
                                    Core/logic 校验
                                              ↓
                                    Game/State 更新
                                              ↓

                            ↓                                ↓
              Game3D/World 同步场景图              Data/Save 防抖落盘
```

`Game3D` **不能直接改存档**，只能发事件。这样所有状态变更都有单一入口，
联机时把同一批事件发给 Backend 校验也是顺理成章的。

## 存档设计

### 存什么、存哪

沿用现有的 `gameSaves` object store，**整份 `GameSave` 作为一条记录**，不拆表。

理由：这个游戏的存档规模很小（一个房间、几十件家具、几只宠物，
估计几十 KB），拆表带来的复杂度远大于收益。IndexedDB 的事务是原子的，
写到一半崩溃会自动回滚，比文件写入更安全。

**只有一个世界，不做多存档槽位。**符合"租到房子安顿下来"的叙事，
也和动森一致。初期不做云端，但键名结构对齐 `V0.8 - 存档云端同步.md`，
以后接云同步不用重构。

```
gameSaves/
  "world"             → GameSave（主存档）
  "world.backup"      → 上一份成功存档（双份轮写）
  "world.conflict"    → 云端冲突时保留的本地副本（V0.8 要求，接云端时启用）
settings/
  "device"            → 音量、键位、画质（跨存档共享，不进 GameSave）
```

### 双份轮写 + 自动回退

治愈游戏丢存档是灾难性的，所以不只依赖 IndexedDB 的事务原子性：

1. 写入前，把当前主存档整体复制到 `world.backup`
2. 再写 `world`
3. 加载时若 `world` 读不出来或校验失败，**自动回退到 `world.backup`** 并告知玩家

成本极低（多一次写），能挡住绝大多数灾难。

### 与 V0.8 云端同步的对齐

初期只做 `local_only`，但要预留 `V0.8 - 存档云端同步.md` 定义的三种模式：

| 模式 | 说明 |
|---|---|
| `local_only` | 没登录 / token 无效 / 云服务不可用，只用本地存档 |
| `cloud_sync` | 已登录未联机，本地正常存，每 30 分钟同步云端 |
| `multiplayer_session` | 联机中，停止普通云同步，状态以 server session 为准 |

现在要做的只有一件事：**存档模块的接口按"模式"设计**，
而不是写死成"直接读写 IndexedDB"。这样接云端时只是多一个实现。

### 自动存档时机

V0.2 已经定了原则——**不要每帧或每分钟写**：

> `WorldClockSave` 只在正常存档、退出、进入后台、跨越 `WorldDayId`
> 或产生重要耐久时间状态时更新

具体触发点：

| 触发 | 说明 |
|---|---|
| 耐久操作后（防抖 2–3 秒） | 放置/移除家具、制作、烹饪、送礼 |
| 行动开始 / 完成 | `ActionProcessSave` 变更 |
| 跨越 `WorldDayId` | 每日系统的边界 |
| 页面进入后台 / 关闭 | `visibilitychange` + `pagehide` |
| 手动存档 | 如果做 |

**不触发**：角色移动、相机旋转、镜头缩放、UI 开关——这些是瞬时状态，不入档。

### 迁移

`GameSaveMeta.saveSchemaVersion` 已经在类型里。迁移做成有序链：

```ts
migrations: [
  { to: 2, migrate: (save) => ... },
  { to: 3, migrate: (save) => ... },
]
```

加载时从存档的版本一路升到当前版本。**每次改 Core 类型都要问：需要迁移吗？**
（`AGENTS.md` 的硬性要求）

## 房间信息怎么存

### 存几何结果，不存"配方引用"

这是个真正的岔路口：

| | 存几何结果 | 只存 styleId + seed，加载时生成 |
|---|---|---|
| 存档体积 | 略大（但房间就几面墙，可忽略） | 极小 |
| 内容更新后 | 老存档保持原样，房间不会突变 | 配方一改，**所有人的房间形状会变** |
| 家具合法性 | 稳定 | 配方微调就可能让家具悬空 |
| 联机 | 访客直接用房主存档的几何，**必定一致** | 双方内容版本不同 → **生成出不同的房间** |

**选存几何结果。**决定性理由是联机：V0.2 规定联机时上传房主存档、大家一起进这个存档，
如果房间是"加载时按配方生成"，客户端版本一有差异就会各自生成不同的房间。

`styleId` 仍然要存，但只作为**来源标记**（用于装修 UI 显示当前风格、
以及未来重新生成时的默认值），不作为渲染依据。

### 门窗必须进 WallSave

现在的定义没有门窗：

```ts
type WallSave = { wallId, facing, grid, origin };
```

但我们已经确定：窗户要做景深盒、环境音按距窗距离衰减；
门是宠物派遣的寻路目标、有开合动画。**这两样现在无处安放。**

门窗是**结构性的**（属于屋子风格，不是玩家随手摆的家具），所以应该属于墙：

```ts
type WallOpening = {
  openingId: string;
  kind: "door" | "window";
  gridPosition: GridPosition;   // 在这面墙上的位置
  size: GridFootprint;          // 洞口尺寸
  visualId: VisualId;           // 窗框/门的外观
};

type WallSave = {
  wallId; facing; grid; origin;
  openings: WallOpening[];      // 【新增】
};
```

这样：`RoomBuilder` 按 openings 在墙上挖洞并放窗框；
`WindowView` 在每个 window 后面挂景深盒；
`DoorView` 让 door 可开合并注册成寻路目标；
音效系统遍历 openings 算距离。

### 房间必须支持"长大"

`V0.10 - 多地区设计.md`：

> 添加全新 NPC——工程师……支付一定的金额，可以扩建我们的建筑，
> 让同居的小动物们有更好的居住地

所以 **16×12 是初始尺寸，不是固定尺寸**。`RoomSave.floorGrid` 本来就是数据，
扩建就是改这个值 + 重新生成墙。因为选了"存几何结果"，扩建时显式重写几何、
重新校验家具（和换装修风格同一套流程）。

扩建只增不减，所以家具基本不会失效——比换风格安全。

### 别把"以后有室外"这条路堵死

`V0.10` 还写了：

> 在解锁大河后，理论上还能去一些户外进行探索

所以"不做室外"是 **V1 的范围决定，不是永久架构约束**。
好在 `MapSave` 本来就是 `Record<mapId, MapSave>` 的多地图结构，
只要 `RoomBuilder` / 相机 / 寻路不假设"世界只有一个房间"，这条路就留着。

### 占用图不存，加载时重建

占用图（哪些格子被占）是**派生数据**，从 `placedFurniture` 算出来，不进存档。
放置校验和宠物 A* 寻路共用这一张运行时的图。

## 视觉资源策略：visualId 间接层

Core 里 `FurnitureDefinition.visualId` 只是个字符串。Frontend 有一张表决定它怎么变成几何体：

```ts
// Game3D/Visual/VisualRegistry.ts
"ordinary_workbench_default" → { kind: "procedural", recipe: workbenchRecipe }
"chinchilla_baby"            → { kind: "gltf", url: "/models/chinchilla.glb" }
```

好处：

- **先用程序化配方跑通全部系统**，之后哪个家具想换成精修模型，只改这一张表
- Core 和存档完全不动，无痛替换
- 宠物同理：先程序化团子，后精模

### 程序化家具配方

配方本身就是数据，形如：

```ts
type VisualRecipe = {
  parts: Array<{
    shape: "box" | "cylinder" | "cone" | "sphere";
    size: [number, number, number];
    position: [number, number, number];
    rotation?: [number, number, number];
    color: PaletteKey;
  }>;
};
```

这直接满足 V0.2 的"家具应该是随时添加注册的"：
**加一个新家具 = Core 加一条定义 + Registry 加一条配方，不需要美术出图、不需要资源管线。**

## 风险与成本

### 最大成本：3D 宠物

已确定宠物全部建模。诚实评估这是复利成本：设计里宠物会像宝可梦一样进化，
一个物种 = 多个形态 × 每形态若干动画（待机 / 走 / 睡 / 吃）。

**建议的顺序策略**：宠物放到最后做。先把房间、家具、放置、相机、光照跑通，
宠物先用程序化团子占位。等看到实际画面手感，再决定宠物投多少美术资源。
有 visualId 间接层，这个决定可以无限期推迟而不阻塞任何事。

### 建模能力边界（诚实说明）

本机没有装 Blender。可用手段是"用代码拼图元"。

- **家具 / 建筑 / 植物道具**：把握大，这类"方块和圆柱组成"的东西代码写得又快又准
- **低多边形小动物**：能拼出形状，也能写程序化动画（呼吸起伏、耳朵抖、走路颠簸，这个画风不需要骨骼绑定）。
  但**"可爱"是美术判断不是几何问题**，只能靠"渲染 → 截图 → 看 → 调参"逼近，比人手捏慢很多
- **精细角色 / 有机造型 / 高质量骨骼动画**：做不了。后备方案是 text-to-3D 服务（Meshy / Tripo 一类）出 GLTF，靠 visualId 间接层接进来

## 台面放置：走槽位系统

`整体架构.md` 的第一天流程里明确有这些操作：

> 系统提示用户可以将背包里的**锅拿出来，放到灶台上**，然后把米放进去开始煮饭
> 再从背包里**拿一个盘子**，就可以盛出番茄和炒饭

但 V0.2 只定义了两种放置面（`Floor` / `Wall`），
**"物件放在另一件家具的台面上"两种都盖不住**。

这不是 3D 带来的新问题——2D 也存在，只是 2D 可以靠"画在上面"糊弄过去。
3D 里台面有真实高度，躲不掉。

**决定：走槽位系统，不扩展 `PlacementSurface`。**

灶台有固定的"锅位"、展板有"切菜位"、工作台有"产出位"。
这正是 Overcooked 的做法，而文档里写的就是"类 overcook"。

好处：

- `PlacementSurface` 保持 `Floor | Wall` 两种，放置系统不用处理嵌套坐标
- 槽位是家具自己的状态，挂在 `PlacedFurnitureState` 下，存档结构简单
- 烹饪本来就不需要"自由摆放"——锅就该在灶眼上，不是随便放在台面某个格子

代价：桌上自由摆花瓶、相框这类**纯装饰性台面摆放暂时做不了**。
如果之后确实需要，再单独加 `PlacementSurface.Surface`，
届时槽位系统和自由台面可以共存（功能走槽位、装饰走台面）。

## 通读全部版本文档后的交叉发现

把 `版本期望/` 下 15 份文档全部读完之后的补充。

### V0.9 联机验证了"命令模式"这个设计

> 玩家移动只同步运行时位置，**不修改 WorldSave**。
> 家具摆放、制作、天气变化等**耐久操作发送给 Server**。Server 验证成功后更新
> 房间中的 WorldSave，增加 revision，再向所有参与者广播。
> 房客**不能直接上传修改后的完整 WorldSave** 覆盖房主世界。

这正好对上前面"`Game3D` 不能直接改存档，只能发事件"的约束。
更进一步：**耐球操作应该做成显式的 Command 对象**，而不是直接调 store 的方法。

```
本地：Command → Core 校验 → 应用到本地 State
联机：Command → 发给 Server → Server 用同一份 Core 校验 → 广播 → 各端应用
```

同一个 Command 两条路径，校验逻辑只写一份（在 `Core/logic`）。
如果现在直接改 store，以后接联机要把所有状态变更点重写一遍。

V0.5 里天气瓶的例子也是这个形状：

```ts
type UseWeatherItemCommand = {
  itemStackId: string;
  weatherId: WeatherId;
  scope: { mapId?: string; roomId?: string };
};
```

### 唯一真相：一份存档，WebSocket 只托管它

设计目标：**所有耐久状态都真正落在存档里，不存在游离于存档之外的耐久数据。**
这样联机时 Server 只需要托管一份 `WorldSave`，不需要维护第二套状态。

Command 是通道，存档是真相：

```
本地：Command → Core 校验 → 改 WorldSave → 防抖落盘
联机：Command → Server → 同一份 Core 校验 → 改房主 WorldSave → revision++ → 广播
```

#### ⚠️ 缺口 9：Core 里有三处重复定义

按"唯一真相"这个标准去查，发现同一份数据在两个地方都有：

| 数据 | 位置 A | 位置 B |
|---|---|---|
| 玩家背包 | `PlayerSave.character.inventory` | `WorldSave.playerCharacter.inventoryId` → `inventories` |
| 饥饿 / 疲劳 | `PlayerSave.character.needs` | `WorldSave.playerCharacter.needs` |
| 已学配方 | `PlayerSave.discoveredRecipeIds` | `WorldSave.progression.discoveredRecipeIds` |

联机场景直接给出了正确切法——V0.9 说房客可以在房主世界里丢弃、捡起物品，
说明**玩家带着自己的东西进别人的世界**：

| 归属 | 内容 |
|---|---|
| `PlayerSave`（跟着玩家走） | 背包、饥饿疲劳、已学配方、捏人配置 |
| `WorldSave`（属于世界） | 家具、宠物、储物箱、天气、事件进度、房间几何 |

所以 `WorldSave.playerCharacter` 和 `WorldSave.progression.discoveredRecipeIds`

### 8. 放置分层与通行

**地毯和家具分属不同层**：地毯铺在下面，桌椅放在地毯上。
既然选了"靠家具和地毯自然分区"，地毯就必须能被踩在下面。

**是否挡路由家具自己声明**，不由层决定：

```ts
// FurnitureDefinition 新增
blocksMovement: boolean;    // 柜子/桌子 true，地毯/小摆件 false
```

由此得出一个重要结论：**同一批家具数据要生成三张互相独立的图**：

| 图 | 用途 | 来源 |
|---|---|---|
| 放置占用图（分层） | 这个格子能不能放东西 | 地毯层 / 家具层各一张 |
| 通行图 | 人和宠物能不能走过去 | 只算 `blocksMovement` 为真的 |
| 落脚目标 | 宠物能坐/睡在哪 | `Sitting` / `Sleep` capability |

地毯占格但不挡路；椅子占格、挡路、同时又是宠物的目标——三件事完全独立，
不能用一张图糊弄过去。

### 9. 对话只发事件，不写效果

对话节点不直接改好感度或解锁功能，只**发出一个事件 id**，
后果交给事件系统处理：

```ts
type DialogueNode = {
  ...
  emitEventId?: EventId;      // 取代原计划的 effects 列表
};
```

好处：好感度变化、功能解锁、宠物记忆这些逻辑只在事件系统里存在一份，
对话不重复造一套效果系统。前面标记的那个"待补的口子"由此关闭。

## 验收标准与里程碑

### 验收标准：完整跑通第一天流程

不是"做个好看的房间"，而是从搬进屋一路走到妈妈打电话。

拆开看，第一天流程需要这些系统：

> 背包 · 快捷栏 · 家具放置 · 工作台 · 配方 · 制作 · 对话 · 宠物 · 好感度 ·
> 事件 · 过场镜头 · 行动系统 · 专注模式 · 槽位 · 烹饪 · 睡眠 · 功能解锁 · 手机电话

**这基本上等于整个 V1。**

### 排序原则：让画风最早暴露

最大的风险不是某个系统难写，而是**画风做出来不对**——那样前面所有工作都要重来。
所以里程碑按"最早能判断画风"来排，而不是按系统依赖顺序。

| 里程碑 | 内容 | 能验证什么 |
|---|---|---|
| **M1 能看** | 房间几何（16×12 + 墙 + 门窗洞）、动森式相机（档位/跟随/缩放）、浅色描边、平面着色、昼夜光照、窗外景深盒、预置灶台和纸箱、`/time` `/weather` 调试命令 | **画风对不对**（关键判断点） |
| **M2 能动能摆** | 捏人角色 + 程序化动画、WASD + 碰撞、三张占用图、放置系统（虚影/合法性/旋转/多格）、背包快捷栏 | 摆家具的手感 |
| **M3 能做东西** | 工作台交互 + 配方 + 制作、槽位系统、灶台烹饪 | 制作循环 |
| **M4 有故事** | 对话系统、宠物（A* / 好感度）、事件系统 + 过场镜头、行动系统 + 专注模式 | 情感体验 |
| **M5 第一天闭环** | 睡眠、妈妈电话、教程引导串联 | 完整验收 |

**M1 结束时就要停下来看画风。**如果那时候觉得不对，改的只是 M1 的量；
如果拖到 M5 才发现，就是全盘重来。

### 存档模块的边界（新增，实现时定的）

| 入档 | 不入档 |
|---|---|
| 房间几何（含门窗）、已放置家具、背包槽位、饥饿疲劳、宠物（位置+好感）、事件进度、解锁功能、**已触发的剧情规则**、进行中的行动 | 相机、角色位置、占用图（派生）、对话状态、在制烹饪、教程步数（由信号重放推导） |

两个非显然的点：

1. **`firedStoryRuleIds` 必须入档**（为此给 `WorldSave.progression` 加了这个可选字段）。
   不存的话读档后 `StoryRule.once` 重新成立，开场提示和灰灰登场会再演一遍
2. **行动按绝对 UTC 恢复**：存的是 `startedAtUtc` + `durationMinutes` 而不是剩余秒数。
   读档时已过完成时刻的**立刻结算发奖**，没过的按剩余时间重新挂定时器——
   对齐"关掉游戏也会照常完成，不惩罚忘记开着标签页的人"

### 工具：画布像素回传

文档里计划的"页面把 WebGL 画布 POST 回磁盘"这轮真的用上了，做法很轻：
一个 Node HTTP 接收端 + 页面里 `renderer.render()` 后 `toDataURL()` 再 `fetch` 出去。
浏览器面板没显示时 rAF 会停，但**手动调一次 render 再读像素仍然有效**，
这是无人值守验证 3D 画面的可行路径（本轮的悬空墙饰 bug 就是这么看出来的）。
