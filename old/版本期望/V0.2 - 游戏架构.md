## 时间系统

游戏世界采用现实时间，一天对应现实中的 24 小时。世界不会在存档中不断写入“当前几点几分”，也不会通过做任务或睡觉推进时钟。当前昼夜由一个 Clock Source 提供的 UTC 时间，转换到这个世界固定保存的 IANA 时区后推导。

时间相关概念必须分开：

- `UTC 时间`：用于跨设备、云存档、联机和绝对到期时间。
- `世界本地时间`：UTC 转换到世界时区后的日期与钟点，用于昼夜、音乐、天气表现和 NPC 作息。
- `WorldDayId`：按照世界时区和每日换日时间计算出的逻辑日期，用于每日任务、每日奖励和“现实中的下一天”条件。
- `事件进度`：剧情真正的推进状态。现实时间只能成为事件的触发条件之一，不能代替事件状态。
- `累计时长`：只用于不需要跨存档的动画、进度条等短时过程；不能用于食物过期、每日刷新或剧情日期。

### 时间策略

时间规则采用注册表定义，避免把换日时间、昼夜阶段和异常处理写死在 gameplay script 中：

```ts
type TimePolicyId = string;

type TimePolicyDefinition = {
    id: TimePolicyId;
    mode: "real_time";

    // 每日系统的换日点，由内容配置决定，例如凌晨某个时间
    dayRolloverLocalTime: string;

    // 昼夜阶段的开始时间，由 Presentation、音乐、天气和 NPC 作息共同读取
    dayPhases: Array<{
        phaseId: "dawn" | "day" | "dusk" | "night";
        startsAtLocalTime: string;
    }>;

};

type WorldClockSave = {
    // 创建世界时确定，之后不会因为设备或玩家所在地改变而自动变化
    timeZoneId: IanaTimeZoneId;
    timePolicyId: TimePolicyId;

    // 最近一次持久化检查点观察到的 UTC，不是持续保存的当前时间
    lastObservedUtc: UtcTimestamp;
    lastObservedSource: "device" | "server";
    lastObservedWorldDayId: WorldDayId;

    // 仅在检测到设备时间回拨或其他异常时记录，方便恢复和诊断
    anomaly?: {
        kind: "clock_rollback" | "large_forward_jump";
        detectedAtUtc: UtcTimestamp;
        reportedDeviceUtc: UtcTimestamp;
    };
};
```

`WorldClockSave` 只在正常存档、退出、进入后台、跨越 `WorldDayId` 或产生重要耐久时间状态时更新，不需要每帧或每分钟写入。`lastObservedUtc` 是检测本地时间回拨的水位线，不是保存世界当前钟点。

### 当前时间来源

所有系统通过统一 Clock Interface 获取时间，不能直接读取设备 API：

```ts
type ClockSample = {
    nowUtc: UtcTimestamp;
    source: "device" | "server";
    trusted: boolean;
};
```

时间来源按运行模式处理：

- `local_only`：使用设备提供的 UTC，再转换到 `WorldClockSave.timeZoneId`。设备时区只用于首次创建世界时提供默认值，之后不会自动改写世界时区。
- `cloud_sync`：在线时优先使用 Server UTC；离线时仍可使用设备 UTC，保证核心玩法不依赖网络。
- `multiplayer_session`：只使用 Server UTC，并统一转换到房主世界的 `timeZoneId`。访客的设备时间、设备时区和自己世界的时区都不能影响房主世界。

当前昼夜、音乐时段和 NPC 作息每次都从有效 UTC 推导，不写入 Save。夏令时变化由 IANA 时区规则自然处理，因此某些现实日期可以是 23 或 25 小时，但 `WorldDayId` 仍按照世界当地换日点计算。

### 剧情与睡觉

剧情推进由 `WorldSave.progression.events` 中的事件状态决定。事件可以声明以下条件：

- 已完成的前置事件。
- 已解锁的功能。
- 已完成的任务或交互。
- 最早可触发的 `WorldDayId`。
- 当前天气、地图或 NPC 状态。

现实日期只负责让事件变成“可以触发”。只有玩家实际进入并完成事件后，才写入新的事件阶段。错过若干现实日期时，不应一次性自动播放或完成多段剧情。

睡觉只处理休息动画、疲劳恢复和睡眠音景，不修改 UTC、不跳到下一天，也不直接完成任何剧情。文案中的“睡醒后”如果实际上要求现实中的下一天，应表达为“到达后续 `WorldDayId` 且玩家再次进入世界后”；如果不要求等待现实中的下一天，则应由事件前置条件触发。

每日任务和每日奖励必须记录已经处理或领取过的 `WorldDayId`，确保同一个世界日内重复登录、切换设备或重新连接都不会重复结算。向前跨过多个日期时，默认只开放当前世界日，不自动补发所有错过日期的奖励。

### 时间存档冲突

设备时间、存档修改时间和游戏世界时间不能互相替代。`GameSave.meta.updatedAtUtc` 只用于显示和诊断，不能用于判断哪份世界进度更新。

云存档遵循以下规则：

1. 云端使用递增的 `cloudRevision` 作为存档顺序，Server 接收写入时添加可信 UTC。
2. Client 只能基于自己最后确认的 `cloudRevision` 条件写入。Revision 不匹配时，不得直接覆盖云端。
3. 已登录的 `cloud_sync` 模式以 Server 确认的完整存档为权威，不对两个 `WorldSave` 做字段级自动合并。
4. 冲突时保留本地副本作为 conflict backup，加载云端权威版本，并明确提示后续恢复入口；不得通过比较设备 `updatedAtUtc` 或 `lastObservedUtc` 静默选取存档。
5. 云端不存在存档时，允许上传本地存档并由 Server 创建初始 `cloudRevision`。
6. 加载云存档后，当前昼夜重新由最新 Server UTC 和该存档的世界时区推导。已经写入的事件进度、每日领取记录和物品状态不因时钟重新计算而倒退。

### 本地时间回拨与跨设备

在 `local_only` 或离线状态下，如果设备报告的 UTC 早于 `lastObservedUtc`：

- 当前有效时间暂时钳制在 `lastObservedUtc`，时间不能倒流。
- 已完成事件、每日领取和已经过期的食物不会恢复。
- 依赖未来时间完成的等待、食物保质期和下一日刷新暂停推进，直到设备时间追上，或者获得可信 Server UTC。
- 游戏核心的移动、装饰、背包和不依赖时间的任务仍然可以正常进行。
- `WorldClockSave.anomaly` 记录异常，但不把它当作作弊处罚依据。

重新获得可信 Server UTC 后，以 Server UTC 重新建立时间锚点；已经产生的耐久进度不回滚，但后续时间条件从新的可信时间继续计算。

跨设备或玩家现实旅行时，世界继续使用创建时保存的 `timeZoneId`，不会跟随新设备时区。未来如果允许玩家主动迁移世界时区，应作为独立功能处理，并保证迁移不会重复生成每日任务、每日奖励或剧情事件。

设备时间大幅向前跳跃时可以记录 `large_forward_jump`，但世界仍按新的日期显示。所有每日奖励依靠 `WorldDayId` 幂等记录防止重复领取，剧情也只能从当前事件状态继续，不会因为跨过很多天而自动完成。

### 食物过期

所有会过期的食物统一按绝对 UTC 处理：

1. `ItemDefinition.food.shelfLifeSeconds` 定义保质时长；未设置表示不会过期。
2. 食物生成或烹饪完成时，使用当时的有效 UTC 计算 `expiresAtUtc = nowUtc + shelfLifeSeconds`。
3. 判断是否过期只比较有效 UTC 与 `ItemStackState.expiresAtUtc`。
4. 食物离线时继续过期，跨时区后到期点不变，联机时由 Server UTC 判断。
5. 世界日期只用于每日系统，不用于食物过期；累计在线时长也不用于食物过期。
6. 一旦食物已被耐久状态标记为过期，后续时钟回拨不能让它恢复新鲜。

未来冰箱、冷冻或保鲜效果应修改明确的 `expiresAtUtc` 或在存取时按独立保鲜规则重新计算，不能偷偷切换为另一套计时单位。

## 声效系统

分成音乐，声效，Player 是 listener，即听觉位置，下面是具体规则

### 规则
音效应当遵循以下规则
- 距离衰减
- 最大听距
- 墙体遮挡检测
- 被遮挡时降低音量或加 low-pass
- 某些墙/门/窗可通过定义改变遮挡强度

音乐则不受上述规则影响


### 音乐

我们会储存一系列无版权音乐，后期可以像动森一样分早中晚的时间播放不同时间段的音乐，现在共享一个大音乐库

可以随机播放，顺序播放，单曲循环，可以选择音乐播放（为未来音乐播放器做准备）

特殊剧情会柔性中断当前播放音乐，插播符合剧情的音乐


### 声效

Player 是 listener，即听觉位置，以下所有的音效都会根据距离调整，声音应该受障碍物影响，如墙的另一头应该听不到，家具，小动物声音 等
下面是三种类型：
- 环境音： 环境音应当检查存档的天气和房子的type播放，并且会找寻窗户和门的位置，越靠近这两个地方，玩家应该能听到更清晰的环境音，如雨声等
- 家具音：家具有不同的音效
- 小动物声音： 小动物做的事情发出不同的声音

## 网格装饰

装饰是本作品一大核心，我们会有分为墙饰（wall_grid）和地面装饰（floor_grid）

墙饰只能放在墙上的网格，地面装饰（家具）只能放在地面，

每个可放置物都有自己的 footprint，例如 1x1、1x2、2x2，以适应不同的尺寸的图片

目前墙饰有：
- 画、挂钟、窗帘、壁灯、风铃

目前地饰有：
- 桌子、床、工作台、地毯、椅子

墙饰要特别小心：top-down 2D 里“墙”不是普通地板格。最好把墙面放置点做成独立的 wall placement layer，不要让它混进地面家具系统，否则以后会很难处理遮挡、深度排序和点击选择。

## 家具注册

家具应该是随时添加注册的
下面是对应的数据机构

```ts

type VisualId = string;
type AudioProfileId = string; // 未来再进行复杂变化，或者不改

// 用于告诉商店分类等
enum FurnitureCategory {
    Station = "station",
    Storage = "storage",
    Bed = "bed",
    Seating = "seating",
    Table = "table",
    Lighting = "lighting",
    Decoration = "decoration",
}

// 墙壁装饰物还是地面装饰物
enum PlacementSurface {
    Floor = "floor",
    Wall = "wall",
}

// 对应功能，将抽象给不同的家具
enum FurnitureCapability {
    Crafting = "crafting",
    Cooking = "cooking",
    Storage = "storage",
    Sleep = "sleep",
    Sitting = "sitting",
    Ambience = "ambience",
}

type FurnitureDefinition = {
    id: string, // 用于确定家具的注册id
    visualId: VisualId; // 视觉资源 ID，例如 "ordinary_workbench_default"，方便出皮肤
    footprint: GridFootprint // 网格占地，保证不同图片都按规则限制长宽

    placementSurface: PlacementSurface; // floor or wall

    localizationKey: string, // 其实就是名字，只是方便未来翻译

```

理论上当一个家具被造出来，他的type应该如下所示：

```ts

    
    type PlacedFurniture = {
        instanceId: PlacedFurnitureInstanceId; // 世界中这个具体家具的唯一 ID

        furnitureId: FurnitureId; // 指向 FurnitureDefinition.id，例如 "ordinary_workbench"

        //储存放置信息
        type FurniturePlacement =
            | 
                {
                    kind: PlacementSurface.Floor;
                    roomId: RoomId;
                    gridPosition: GridPosition;
                }
            | 
                {
                    kind: PlacementSurface.Wall;
                    roomId: RoomId;
                    gridPosition: GridPosition;


                    wallId: WallId; // 墙有好几面
                };

        state: PlacedFurnitureState; // 针对不同的家具的不同变化，应该有更细微的思考
    };

    type PlacedFurnitureState = {
        durability?: number;

        // 如果这个家具有 Storage capability，可以指向它拥有的库存
        storageInventoryId?: string;

        // 如果这个家具有 Cooking/Crafting 等过程，可以记录正在进行的流程
        activeProcessId?: string;

        // 如果单个实例换了皮肤，比如同一张床被玩家换成春季外观
        customVisualId?: VisualId;
    };
```

以下特别的家具设计解释：
    Crafting ： 点击打开工作台UI
    Cooking : 打开厨房界面（直到工作台完成才会出现）
    Storage = 储存系统，点击根据ID打开对应储存UI（冰箱和箱子应当都是不同的）
    Sleep = 睡觉会播放睡觉动画，但是不会跳过当天，会有呼吸声，播放专属轻柔音乐
    Sitting = 椅子，提供坐的xy坐标，引导角色坐下
    Ambience = 白噪音家具，如风铃等，这些会发出一些特别的，温柔的声音

## Event Bus

我们不能直接沟通所有的系统，这样会有很大的负担，所以应该设计一套event bus，方便未来指令，事件系统调试，以及添加内容
