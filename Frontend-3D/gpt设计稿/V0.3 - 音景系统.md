> 2026-07-31。起因是「调成雨天没声音」，查下来雨声其实是响的，
> 但过程中挖出三个真缺陷，顺带发现 `Oldfrontend` 有一套更成熟的音频架构值得搬。
> 这份文档是**定位结论 + 完整设计**，供后续实现照做。

## 一、诊断结论（已查证，不是猜测）

### 雨声其实是响的

用真实鼠标点击解锁后实测：

```
contextState: "running"
loopGains: [
  { id: "ambience_forest",    gain: 0.45 },
  { id: "weather_audio_rain", gain: 0.9  }
]
```

规则层、播放层都正确。听不到的最可能原因是**素材太大导致首次出声延迟**：

| 素材 | 体积 |
|---|---|
| `system/environment/forest.mp3` | 6.8 MB |
| `system/weather/rain_light.wav` | 5.4 MB |
| `system/environment/sea.wav` | 5.4 MB |
| `furniture/fire_crackling.wav` | 5.4 MB |
| `action/cooking.wav` | 5.4 MB |

5.4 MB 的 30 秒立体声 WAV，fetch + `decodeAudioData` 要好几秒。
切完天气盯着看，前几秒确实是静的。

### 缺陷 A：假解锁（**已修**）

`unlockAudio()` 原本只等 `ctx.resume()` 的 Promise 就把 `unlocked` 置 true。
但**没有可信用户手势时 `resume()` 也会 resolve**，context 仍停在 `suspended`——
于是出现「诊断显示已解锁、实际一声不响」，而且 `pendingLoops` 被清空后再没人补播。

修法：`resume()` 之后检查 `ctx.state !== "running"` 就直接返回，不置 unlocked。

### 缺陷 B：诊断指令报的是假状态（**已修**）

`sound` 指令原本只报内部标志 `unlocked`。现在补了两项真值：

- `contextState` —— AudioContext 的真实状态，`running` 之外都是「其实没声音」
- `loopGains` —— 每条循环的实际增益，用来区分「没在播」和「在播但音量是 0」

后来又补了两项（2026-07-31）：`loopGains` 里带上 `tag`（两个壁炉是两条
独立循环，只看 profileId 分不出来）、以及 `loading`（正在 fetch/decode 的
路径，用来区分「没在播」和「还没加载完」）、`zone`（玩家所在分区）。

### 缺陷 C：五个素材没接进注册表

`cooking` / `pen` / `fire_crackling` / `open_box` / `wooden_chest_open` 都已放进
`public/audio/`，但 `Core/src/Data/audio` 里没有条目，所以永远不会响。

## 二、从 Oldfrontend 学到的四件事

旧版 `Oldfrontend/src/.../SystemIdleGame/audio/` 有 5237 行的完整音频架构
（AudioSystem 725 / AudioRegistry 205 / AudioEventMapper 109 /
EnvironmentalAudioDirector 304 / EntityActionSoundCatalog 54 / MusicDirector 386）。
架构方向和我们一致（「有哪些声音」和「什么时候响」分离），但有四个设计我们缺：

### 1. 距离衰减是数据，不是 3D 引擎 ⭐

旧版给每条音效一个 `audibleRadius`，手算音量：

```ts
const falloff = 1 - clamp(distance / radius, 0, 1);
const volume = clamp(max(minVolume, baseVolume * falloff * falloff), 0, 1);
if (distance > radius) return;   // 超出半径直接不播
```

**这比 `PannerNode` 更适合本作**：治愈系游戏不需要方位感（左耳右耳），
只需要「走近了听得见」。手算音量不用维护 listener 朝向、不用管声道旋转，
四行代码，而且音量曲线完全可控。

> 原计划上 PannerNode，看完旧版后改了主意。

### 2. tag 化播放

旧版播放时打 tag（`entity:苔苔:sound:eat`），之后能按 tag 单独调音量/停止。

我们现在按 `profileId` 索引循环（`loops: Map<profileId, LoopHandle>`），
**这意味着屋里放两个壁炉会冲突**——第二个被当成同一条声音。
要做「每件家具一条独立循环」，tag 化绕不过去。

### 3. 分区声音档案 ⭐

旧版同一场雨在户外 0.5、温室 0.18、屋里另有一条闷响素材，
用「档案」表达而不是散落的 if：

```ts
ENVIRONMENTAL_AUDIO_PROFILES = {
  outdoor:    { rain: { rainVolume: 0.5,  stormVolume: 0.62 }, ... },
  greenhouse: { rain: { rainVolume: 0.18, stormVolume: 0.24 }, ... },
  house:      { ... },
}
```

**这对我们比对旧版更重要**：本作全程在屋里，隔着墙听雨本来就该比外面闷。
而且能直接接上已经做好的 `zoneAt(room, cell)`——玄关、浴室、卧室各一份档案。

### 4. 起落不对称 + 最小可闻回收

- 淡入 2200ms / 淡出 3400ms —— 声音来得快去得慢，符合听感
- 音量低于 `MIN_AUDIBLE_VOLUME = 0.015` 就真的 stop 并释放，
  不留一堆听不见却在跑的循环

我们现在淡入淡出同速，且从不因为音量低而回收。

### 不搬的部分

- Phaser 依赖（`Phaser.Math.Distance` / `FloatBetween`）—— 我们是 three.js，自己写
- `generatedMusicRegistry.ts` 3116 行的生成音乐库 —— 本作暂时不做音乐
- `AudioSystem` 725 行的规模 —— 我们的引擎够用，只补 tag 和距离
- 硬编码在前端的 `ENTITY_ACTION_SOUND_REGISTRY` —— 那张表该放 Core，
  和家具/物品注册表一致

## 四、已完成的改动（本次）

### 变体随机 + 音高抖动（**已实现并验证**）

`AudioProfileDefinition.resourcePath` 现在接受 `string | string[]`，
给数组就是变体，每次播放**随机挑一条**：

```ts
{
  id: "sfx_unpack",
  busId: AudioBusId.Effects,
  resourcePath: [
    "/audio/action/open_box.wav",
    "/audio/action/chest_open.wav",
  ],
  loop: false,
  pitchVariance: 0.06,   // ±6% 音高抖动
}
```

两个关键点：

1. **缓存按具体文件路径，不按 profileId**——按 id 缓存的话变体永远只播第一条
   （第二次就命中缓存了）。这是最容易写错的地方。
2. **音高抖动和变体是同一个目的**：只有两条素材时，配上 ±6% 音高
   就能听出四五种差别，比再找素材便宜得多。

实测 100 次随机：`open_box 48 / chest_open 52`，分布均匀。

循环音不吃变体（一直在响，换不换无所谓），只对一次性音有意义。

### 类型上新增的字段

```ts
resourcePath: string | string[];   // 数组 = 变体
pitchVariance?: number;            // 音高随机范围
audibleRadius?: number;            // 有位置的声音；不填 = 全局音
```

## 五、六个步骤（2026-07-31 全部落地）

> 下面保留原始设计，实现时有三处按市面通行做法调整了，记在第八节。

### 步骤 1 · 接现有素材（不需要新代码）

| 素材 | 接到 | profileId | 循环 |
|---|---|---|---|
| `fire_crackling.wav` | 壁炉 | `furniture_fireplace` | 是 | ✅ |
| `cooking.wav` | 灶眼加热中 | `furniture_cooking` | 是 | ✅ |
| `pen.wav` | 行动进行中（写字/学习） | `sfx_action_writing` | 串接 | ✅ |
| `open_box` + `chest_open` | 拆纸箱 | `sfx_unpack` | 否 | ✅ |
| `wooden_chest_open.wav` | 开储物箱 / 衣柜 | `sfx_storage_open` | 否 | ✅ |
| `Wall_clock.wav` | 挂钟 | `furniture_clock` | 是 | ✅ 后补的素材 |

家具侧只需填 `audioProfileId`。现在填了四件：fireplace / stove /
kitchen_counter_l / wall_clock，其余仍是 `null`。

行动侧同理：`ActionDefinition` 新增了 `audioProfileId` 字段，
`work_study` 和 `creation` 填 `sfx_action_writing`。

### 步骤 2 · tag 化播放

`loops` 的键从 `profileId` 改成 `tag`：

```ts
playLoop(profileId, { tag: `furniture:${instanceId}`, volume })
stopLoop(tag)
setTaggedVolume(tag, volume)
```

不传 tag 时默认用 profileId（兼容现有的底噪/天气层）。

### 步骤 3 · 距离衰减

```ts
// Soundscape 每 ~120ms 跑一次
for (const placed of placedFurniture) {
  const profile = definitionOf(placed).audioProfileId;
  if (!profile) continue;
  const def = findAudioProfileDefinition(profile);
  if (!def?.audibleRadius) continue;

  const d = distance(playerPos, furnitureCenter(placed));
  const falloff = 1 - clamp(d / def.audibleRadius, 0, 1);
  setTaggedVolume(`furniture:${placed.instanceId}`, falloff * falloff);
}
```

超出半径 → 音量 0 → 低于 `MIN_AUDIBLE` 自动停并释放。

### 步骤 4 · 分区声音档案

```ts
// Core/src/Data/audio
export const zoneAudioProfiles: Record<HouseZoneKind, {
  weatherVolumeScale: number;   // 屋里听雨该闷一些
  ambienceVolumeScale: number;
}> = { ... };
```

消费方查 `zoneAt(room, playerCell)`，拿到档案后缩放各层音量。

> 实测：站在玄关时雨声 0.9 × 1.05 = **0.945**、底噪 0.45 × 1.05 = **0.472**，
> 走进 LDK 各自回到 0.9 / 0.45。分区档案生效。

### 步骤 5 · 开机预载（因为定案不压缩，延迟只能靠这条解决）

保持 WAV 就得接受单个素材 5 MB，所以**不能等要播了才去加载**。
在标题页就把底噪和天气层预热进缓存：

```ts
// AudioEngine 暴露一个预载入口
export function preloadProfiles(ids: string[]): Promise<void>
```

要点：
- `buffers` 已经按路径缓存，预载就是提前调一次 `loadBuffer`
- **不要 await 全部**——一条卡住不该拖住整局，用 `allSettled`
- 预载在标题页跑（玩家停留那几秒正好够），不阻塞进游戏
- 只预热"一定会用到的"：当前地区底噪 + 雨声。
  家具音按需加载即可（玩家不一定摆壁炉）
- **在途请求也要按路径去重**：素材要几秒才解码完，这期间的第二次请求
  会 miss 缓存，同一个 5 MB 文件下两遍。只缓存结果不够，要缓存 Promise

> 实测：标题页就发出了 `forest.mp3` 和 `rain_light.wav` 的请求，
> 进屋时 `sound` 的 `loading` 是空的——首次出声不再等。

### 步骤 6 · 脚步声

分地材：`zoneAt` 已能查出踩在木地板 / 玄关土间 / 浴室瓷砖上。
每种材质一条 profile（配 3~4 个变体 + 音高抖动），按移动速度定间隔。

## 六、素材规格与欠账

### 规格

- 放 `Frontend-3D/public/audio/` 下，WAV 或 MP3 均可
- **循环音必须无缝**（首尾能接上，否则每 30 秒一次咔哒）
- 一次性音尽量短（< 1.5 秒），单声道即可

### 体积：保持 WAV（2026-07-31 定案，不要再问）

五个 5 MB 级素材是首次出声延迟的直接原因，转 MP3 能降到约 400 KB。
**但定案是保持 WAV 不压缩**，理由是将来可能迁到 Godot——
Godot 对短音效推荐 WAV（导入时不用解码，触发延迟更低），
MP3 只适合长背景音乐。现在一刀切压掉原始文件，等于把选择权提前丢掉。

所以延迟问题**不靠压缩解决**，靠这两条：

1. **预载**：进游戏时把底噪和天气层先 fetch + decode 进缓存
   （`buffers` 已经按路径缓存，只差一个开机预热）。
   玩家在标题页停留的那几秒正好够用。
2. **首次出声给反馈**：素材还在加载时不要一片死寂——
   要么先播一条极短的占位，要么在 `sound` 诊断里能看出「正在加载」。

将来真要迁 Godot 时再按素材类型分别决定：
短音效留 WAV，长循环（底噪/天气）可以考虑 OGG Vorbis
（Godot 原生支持且能无缝循环，比 MP3 更适合）。

## 七、不硬编码的三条边界

这是整套设计的核心约束，实现时不能破：

| 关注点 | 位置 | 加内容时改什么 |
|---|---|---|
| **有哪些声音** | `Core/src/Data/audio` 注册表 | 加一条定义 |
| **谁会发声** | 家具 / 行动 / 地材上的 `audioProfileId` 字段 | 填一个字段 |
| **什么时候响** | `Frontend-3D/.../Soundscape` 订阅既有事件 | 通常不用改 |

**加一件会响的家具 = 填一行数据；换素材 = 改一行路径；加变体 = 数组里多一行。
代码零改动。**

反面教材：不要在 `kitchen.ts`、`unpack.ts` 这些玩法系统里直接调 `playOneShot`——
那样「什么时候响」就散落到各处了。统一由 Soundscape 订阅事件。

## 八、实现时改掉的三处（2026-07-31）

原设计有三处按 Wwise / FMOD 的通行做法调整了，理由记在这里，别改回去。

### 1. 触发条件是数据，不是从 capability 反推

原打算用「有 `Ambience` 能力就常响、有 `Cooking` 能力就加热时响」推导。
改成在音频定义上写一个显式的 `trigger: AudioTriggerKind`。

理由：中间件里 emitter（挂在哪件东西上）和 State（什么条件下播）本来就是
两张表。`FurnitureCapability` 是**玩法能力**不是发声条件——将来出现
带 `Cooking` 却该静音的电磁炉、或带 `Ambience` 却只在夜里响的东西，
反推就套不上了。现在家具那边照样只填一个 `audioProfileId`，
条件写在声音自己身上。

### 2. 写字声是「串接」，不是循环也不是定时穿插

文档步骤 1 把 `pen.wav` 标成 `loop: 否`，一度打算做成每隔 4~9 秒穿插一声。
改成**播完立刻接下一条**（`chained: true`，间隔 150~400ms 随机 + 音高抖动）。

理由：持续性动作音（写字、锯木、脚步）在商业游戏里是 looping emitter，
定时 one-shot 是给偶发点缀（鸟叫、雷声）用的——每隔几秒响一下会像
「写一笔停一会儿」。但真循环要求素材首尾无缝（见第六节），`pen.wav` 做不到。
串接是 Wwise "Continuous Random Container" 的解法：听感连续，
又不要求任何一条素材本身能无缝循环。

实测：8 次连播间隔 6.4~7.1 秒（素材 6.48 秒 ÷ 各自的音高），
空隙全部落在 150~400ms 区间内，音高在 0.957~1.042 之间逐条变化。

### 3. 不做并发数上限

Wwise 那套 "limit instances to N, discard furthest" 没有实现。
距离衰减配上 `MIN_AUDIBLE_VOLUME` 回收本身就是等价机制——半径 7 格的壁炉，
玩家不可能同时站在很多个的 7 格内，多摆的那些自然会被压到听不见然后释放。
多一套限流只是多一处要维护的规则。
