《Overcooked》的厨房玩法并不是真正模拟做饭，而是把做饭拆成一系列可以被分工、传递、阻塞和打断的任务节点：

接订单 → 取食材 → 暂存/传递 → 加工 → 烹饪 → 装盘 → 上菜 → 回收脏盘 → 清洗 → 再利用

玩家需要在限时内完成尽可能多的订单。厨房布局会刻意分离食材箱、砧板、炉灶、盘子、洗碗池和出餐口，让移动路线和团队配合成为主要难点。

对于你的 Phaser 小屋游戏，最值得借鉴的不是“厨房很混乱”，而是下面三个设计：

台面是共享存储空间，锅是带状态的加工容器，盘子是订单提交载体。

二、厨房空间怎么划分

建议厨房全部建立在你之前说的网格系统上。

每一个厨房设施占据一个或多个格子，玩家站在相邻格子并朝向设施时进行交互。

设施	主要功能	是否能放东西
食材箱	无限或限量生成某种食材	否
普通台面	暂存、传递食材和器皿	是，1个
砧板	放置并切割食材	是，1个
炉灶	给锅、平底锅加热	只能放锅具
烤箱	烘烤完整菜品	只能放烤盘或对应菜品
洗碗池	清洗脏盘子	可容纳多个脏盘
盘子架	提供干净盘子	可叠放
出餐口	验证并提交成品	只能放装盘菜品
垃圾桶	删除错误食材或失败菜品	放入即销毁
关键原则

普通台面建议默认只有一个表面槽位。

玩家不能把三个西红柿互相叠在同一个台面格子上，但可以：

把三个西红柿装进一口锅；
把多个成分装进一个盘子；
把多个空盘叠放在盘子架；
把多个脏盘放入洗碗池队列。

这样能保持画面清晰，也能让“台面不够用”自然成为玩法压力。

三、食物应该怎么放置
1. 物品只有四种存在位置

每一份食材只能存在于以下位置之一：

玩家手中
设施表面
锅、碗或盘子内部
被销毁或已提交

不要让食材同时既显示在锅里，又保留在台面数据中。

例如：

西红柿
holderType: cookware
holderId: pot_01

而不是分别记录“西红柿坐标”和“锅坐标”，否则后面移动锅时很容易出现食材留在原地的 Bug。

2. 食物需要状态机

一份食材不是简单的图片，而是一个会变化的实体。

生西红柿
    ↓ 切割
切碎西红柿
    ↓ 放入锅中
烹饪中的西红柿
    ↓ 完成
番茄汤
    ↓ 长时间未处理
烧焦的番茄汤

建议初期使用这些状态：

type FoodState =
    | "raw"
    | "chopped"
    | "mixed"
    | "cooking"
    | "cooked"
    | "burnt";

砧板需要玩家持续执行操作才能完成切割；锅具放在炉灶上会自动增加烹饪进度，完成后继续加热则会逐渐烧焦。这也是《Overcooked》中最主要的操作压力之一。

3. 放置规则表

当玩家拿着物品面对设施时，不要直接写大量 if else，而是根据规则表判断。

手持物	目标位置	结果
生食材	空台面	放下
生食材	空砧板	放到砧板
可烹饪食材	对应锅具	加入锅具
错误食材	不兼容锅具	拒绝并提示
锅具	空台面	暂时放下
锅具	对应炉灶	开始或继续加热
成品锅具	空盘子	将成品转移到盘子
成分	未完成的盘子	加入盘子
完整盘子	出餐口	验证订单
脏盘子	洗碗池	加入清洗队列
任意食物	垃圾桶	销毁

错误放置最好不要自动删除。

例如玩家拿着生肉点击盘子时，应该：

盘子轻微晃动；
出现红色禁止图标；
播放很短的错误音效；
保持玩家仍然拿着生肉。

否则玩家会觉得系统吞掉了自己的东西。

四、锅、碗、盘应该怎么设计
1. 锅和平底锅

锅具应当是可移动容器，而不是固定在炉灶上的动画。

玩家可以：

从台面拿起空锅；
把锅放到炉灶上；
往锅里添加食材；
烹饪完成后把锅端走；
放到普通台面暂存；
将成品倒入盘子；
再把空锅放回炉灶。

《Overcooked》中，锅用于煮制，平底锅用于煎制；锅具需要放在对应热源上，完成后继续留在热源上会烧焦。

建议锅具包含这些数据：

type Cookware = {
    id: string;
    cookwareType: "pot" | "pan" | "steamer" | "mixing_bowl";
    capacity: number;
    ingredients: FoodItem[];
    recipeId?: string;
    cookProgress: number;
    burnProgress: number;
    state: "empty" | "preparing" | "cooking" | "cooked" | "burnt";
};
容量设计

第一版建议：

汤锅：最多3份食材；
平底锅：一次1份肉类；
蒸笼：一次1个蒸制组合；
搅拌碗：最多2—3份食材。

容量最好是固定的，不要一开始做真实体积计算。

2. 盘子

盘子不是普通容器，而是菜品组装和订单提交的最终单位。

例如汉堡：

空盘子
  + 面包
  + 熟肉饼
  + 生菜
  + 番茄
= 完整汉堡

寿司：

空盘子
  + 海苔
  + 熟米饭
  + 切好的鱼
= 鱼肉寿司

汤类则是：

空盘子
  + 一整锅完成的汤
= 一盘汤

盘子只在出餐时进行最终订单判断。成功出餐后，盘子暂时离开厨房，随后作为脏盘从回收口返回；有洗碗池的关卡中，脏盘需要清洗后才能再次使用。

3. 碗需要分成两类

不要把所有“碗”做成一种东西。

制作碗

用于加工，不能直接出餐：

搅拌碗；
面糊碗；
沙拉盆；
调味碗。

它的角色类似锅具，只是加工方式不同。

出餐碗

本质上等同于盘子：

汤碗；
拉面碗；
饭碗。

它是订单提交载体，出餐后会变成脏碗。

视觉上可以不同，但程序层面可以统一为：

type ServingWareType =
    | "plate"
    | "soup_bowl"
    | "rice_bowl"
    | "cup";
五、一份菜的完整流程

以番茄汤为例。

阶段一：订单生成

顶部出现订单：

番茄汤
需要：3份番茄
剩余时间：45秒

订单系统只描述最终菜品，不需要要求玩家按照固定顺序完成。

阶段二：取得食材

玩家接近番茄箱并按交互键：

空手 → 手持生番茄

食材箱通常可以无限提供食材，但也可以在特殊关卡中加入补货时间。

阶段三：放到砧板
手持生番茄
→ 面对空砧板按交互
→ 番茄放在砧板上

玩家再次按住操作键：

切割进度：0% → 100%

完成后番茄状态变成 chopped。

阶段四：放入锅中

玩家拿起切好的番茄，放入汤锅。

汤锅：
番茄 1/3

重复三次后：

汤锅：
番茄 3/3
识别结果：番茄汤

如果放入两个番茄和一个蘑菇：

无法匹配配方

此时可以选择：

锅停止烹饪，要求玩家倒掉错误内容；
或者允许生成“失败料理”。

第一版建议采用第一种，更容易理解。

阶段五：烹饪

汤锅放在炉灶上后：

准备中 → 烹饪中 → 已完成 → 即将烧焦 → 已烧焦

玩家把锅从炉灶移到普通台面后，烹饪和烧焦进度暂停。

这让玩家可以通过“端锅离火”管理多个订单。

阶段六：装盘

玩家拿着空盘子接近完成的锅：

空盘子 + 完成的番茄汤
→ 一盘番茄汤

锅恢复为空锅。

也可以允许玩家拿着锅面对空盘子完成同样操作。两个方向都支持，操作会更自然。

阶段七：出餐

玩家把番茄汤放到出餐口。

系统进行验证：

订单队列中是否存在番茄汤？
菜品是否完整？
菜品是否烧焦？
是否使用正确餐具？

成功：

订单完成
获得基础分
根据剩余时间增加小费
盘子进入顾客区域

原作也是通过正确且快速完成订单获得分数和速度奖励。

阶段八：脏盘回收

等待一段时间后：

出餐盘
→ 脏盘回收口
→ 洗碗池
→ 清洗进度
→ 干净盘子
→ 重新投入使用

盘子数量要故意限制。

例如厨房只有三只盘子，玩家连续完成三份菜后，就必须处理脏盘，否则第四份菜即使做好也无法出餐。

这会形成第二条资源循环：

食材生产循环
+
餐具回收循环
六、推荐的统一交互方式

《Overcooked》的操作简单，是因为绝大部分行为可以归结为两种按钮。

交互键

用于瞬时行为：

拿起物品；
放下物品；
从食材箱取东西；
把东西放进锅；
从锅里装盘；
提交菜品。
操作键

用于需要持续时间的行为：

切菜；
洗盘；
搅拌；
灭火；
揉面。

系统根据玩家面前的设施和手持物自动判断行为。

判断优先级
1. 玩家手中有物品，并且目标能接收该物品
2. 玩家手中有物品，并且目标表面为空
3. 玩家空手，并且目标表面有物品
4. 玩家空手，并且目标可以生成物品
5. 无可用操作

这样可以减少“我想拿盘子，却误触炉灶”的情况。

七、系统结构建议

考虑到你之前希望使用注册表而不是硬编码，厨房系统可以拆成下面几个模块。

KitchenScene
├── GridManager
│   ├── 格子坐标
│   ├── 占用检测
│   └── 玩家朝向检测
│
├── ItemManager
│   ├── 食材
│   ├── 锅具
│   └── 餐具
│
├── StationManager
│   ├── 台面
│   ├── 砧板
│   ├── 炉灶
│   ├── 洗碗池
│   └── 出餐口
│
├── InteractionResolver
│   └── 判断玩家当前交互结果
│
├── RecipeManager
│   ├── 配方识别
│   ├── 加工要求
│   └── 成品验证
│
├── OrderManager
│   ├── 生成订单
│   ├── 订单倒计时
│   └── 计分
│
└── DishReturnManager
    └── 脏盘回收与重新生成

配方也建议完全数据驱动：

const tomatoSoup = {
    id: "tomato_soup",
    ingredients: [
        { item: "tomato", state: "chopped", amount: 3 }
    ],
    process: {
        station: "pot",
        method: "boil",
        duration: 8
    },
    servingWare: "soup_bowl"
};

未来增加蘑菇汤，只需要注册新配方，不需要修改锅、炉灶或者订单系统。
