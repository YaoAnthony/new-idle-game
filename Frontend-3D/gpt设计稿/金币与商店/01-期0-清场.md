## 0a-2 · 镜头按「这张图上的建筑列表」判定，拔掉"一图一主屋"公理

> **状态：✅ 已完成**（2026-08-22，提交 `2995aa0`）。下面的改法逐条落地，验收五组全部命中
> 预测值——**一个数都没改期望**。实测多出来的证据记在「验收」一节。
>
> **这条是期 2 的硬前置。** 房子和陆地小屋都是**同图走进去**（不换地图），领地上会同时站
> 两栋以上可进的建筑——镜头必须知道"人在哪一栋里"。
> 期 2 的 2A-0（一图多栋运行时）在此基础上继续，把门、走路、占用图也按房间分开。

### 为什么要做

用户定了：**院子里会盖小房子**（陆地小屋、以后的仓库工坊），而且**都是同图走进去的**。

0a 的 `houseRectWorld()` 只算**主房间一栋**的矩形。这和"房子中心 = 世界原点"是同一类隐含公理——
代码里没写"只有一栋"，但结构上只容得下一栋。第二栋盖起来的那天，人走进去镜头不切屋内盒，
从屋顶上方俯视穿进去看。到时候再改，就是把 0a 刚收口的三处判据再拆一遍。

### 改法（两个文件）

**`Frontend-3D/src/Game/State/world/maps.ts`** —— 加两个只读访问器

```ts
/** 当前图上的某个房间（含它自己的 RoomAnchor） */
export function getRoom(roomId: string): RoomSave | undefined {
  return worldState.rooms[roomId];
}
/** 当前图上的全部房间 */
export function getRooms(): Readonly<Record<string, RoomSave>> {
  return worldState.rooms;
}
```

理由：家具、门、掉落物都带 `roomId`，转世界坐标必须用**自己那个房间**的锚点；
今天到处用 `getWorld().room`（主房间）去转，是同一公理的另一份拷贝。

**`Frontend-3D/src/Game3D/World/RoomScene.ts`** —— 五处

| # | 位置 | 改前 | 改后 |
|---|---|---|---|
| 1 | 字段 | `private readonly built: BuiltHouse` 单数 | 保留 `built`（门、窗、陈设仍用它），**新增** `private readonly houses: Array<{ room: RoomSave; built: BuiltHouse }>`；构造函数 `buildHouse` 之后 `push` 一条。今天长度为 1 |
| 2 | 字段 | `private cameraOutdoors = false`（布尔） | `private cameraInsideRoomId: string \| null`——布尔说不了"在**哪一栋**里"，多栋时滞回没法按栋算 |
| 3 | 模块级 | 无 | `type HouseFootprint = { roomId; rect; floorY; wallHeight; ridgeHeight }` + 纯函数 `outsideDistance(rect, at)`（正=在外多远、负=在内多深，滞回要的连续量） |
| 4 | `houseRectWorld(): DeckRect \| null` | 单数、收起返回 null | 换成 `standingHouses(): HouseFootprint[]`——遍历 `houses`，跳过 `built.stowed` 的，每栋按**自己的** `anchorOf(room)` 算世界矩形、取自己的 `wallHeight / ridgeHeight / elevation` |
| 5 | `syncCameraBounds` | 对一个矩形算 `outside`，按布尔滞回 | 见下方伪代码；屋外禁入盒 = **所有**站着的房子各一个 + `outdoorBlockers`；屋内盒 = **当前所在那一栋**的矩形/墙高/地板标高 |
| 6 | `ceilingClearance()` | 读 `this.built.stowed / wallHeight` | `ceilingClearanceOf(house: HouseFootprint)`，按那一栋的墙高；收起的不在 `standing` 里，不再需要判 stowed |

### 底层现状：一个区域多栋小房子，真正卡在哪（2026-08-21 调查，供将来那一期用）

用户的要求是**一个区域可能有多个小房子**。调查结论：**这不是规则层的问题，是运行时状态层的问题。**

- **Core 的纯函数本来就是按房间算的**：`buildRoomOccupancy(room, …)`、`buildGroundMap(map, room)`、
  `checkPlacement`、`findPath` 全收单个 `room`。多栋 = 多调几次，规则一行不用改。
- **"只有一栋"只活在 Frontend 运行时**：`worldState` 持有**一个** `room`、**一个** `occupancy`、
  **一个** `groundMap`。21 个文件从它手里拿 `getWorld().room` / `worldState.room`（按引用数：
  walkable 11、RoomScene 8、FurnitureView 6、PlacementController 5、Soundscape 5、petAgent 5、doorsRuntime 5、
  obstacles 4、testRoom 3、house 3、maps 3、furniture 3、resting 2、petsRuntime 2、
  CookwareView / worldPreload / navigation / dropping / dailyTasks / placement / session 各 1）。
- **`MapDefinition.generateRooms` 已经返回 `Record<roomId, RoomSave>`**，数据层天然容得下多栋：
  第二栋 = 第二条 `RoomSave`，带自己的 `anchor`。base 今天只返回 `living` 一条。
- **路由器已经有了**：`groundMap` 的每块地板面带 `roomId`，`walkable.roomIdAt(x, z)` 今天就能回答
  "这个点属于哪个房间"。多栋的通行判定 = 先 `roomIdAt` 找到房间，再用**那个房间**的 occupancy 和锚点。

所以将来那一期的形状是：`worldState` 从"一个 room + 一个 occupancy"改成"按 roomId 各一张表"，
`groundMap` 收全部房间（每栋一块地板面），21 个消费方按"这个点 / 这件家具属于哪个 room"改写。
**本节（0a-2）只做其中镜头那一角**，它是这条路的第一步，不是全部。

**经营的那块地本身也是一个房间**（2026-08-21 用户问"能不能一起调用"，答：能）：

- `RoomSave` 对"房间"的唯一要求是有一张 `floorGrid`；墙、门都可选。**小镇广场就是先例**
  （`town/layout.ts`：`walls: {}`），广场上的家具/寻路/放置今天就走 `buildRoomOccupancy` 那套，零特判。
- 据点的院子照此声明成一个大网格、无墙、锚点原点的房间（`roomId = "yard"`）。院子里的长椅花坛 = `roomId` 为
  yard 的家具——这就是"院子 = 另一张放置面"那条决策的落地。1 格 = 1 世界单位，屋里院子同一把尺子，
  房子锚点吸附整数格，所以房子占地在院子网格上永远整格。
- **一栋房子 = 两个身份**：内部是它自己的 `RoomSave` + 自己的占用图；外壳是**院子占用图里的一块阻挡**
  （锚点 + floorGrid 推出的矩形盖住的格子）。"一起调用" = 对院子调一次、对每栋房子各调一次，再把每栋的脚印
  盖进院子那张图。规则函数不改；缺的小件是 `buildRoomOccupancy` 今天只认家具不认"房子脚印"——加一个参数或
  外面包一层，十几行。`housePlacementCheck` 的 `occupiedCells` 口就是给院子占用图准备的。
- **院子的地板就是地形，不用加标记**（用户问"高度变化了也能适应吗"，答：能，且比加标记更省）。
  `buildGroundMap` 今天给每个房间压一块平地板且排在地形前面（groundMap.ts 第 70–84 行）——院子成了房间，
  起伏地形会被压平，人直接走进河。但**兜底的地形面已经带着 `roomId = map.outdoorRoomId`**
  （第 124–129 行，今天就叫 `"yard"`）。所以规则是推出来的，不是标出来的：
  **`room.roomId === map.outdoorRoomId` 的房间，地板面就是地形面，不再另推一块平板**。
  高度全由高度场答（`surfaceElevationAt` 本来就按面分三档：高度场 > 单轴坡 > 常数），河岸岸壁照旧是陡坡。
  广场没踩到这个坑只因它本来是平的，它也不是任何图的 outdoorRoomId。
- **寻路按高度自适应，三处都从现有规则推**：
  1. 院子占用图里**陡得站不住的格标成阻挡**——阈值不是新数，就是 groundMap 的 `isStandable`（今天已在
     `isWalkable` 里拦"斜切岸壁溜进河"）。格子化一次，A* 就自动绕开岸壁和河。
  2. `findPath` 展开邻格时加一条**迈步校验**：`canStep(相邻两格的标高)`，用的是 groundMap 已有的
     `MAX_STEP_UP 0.55 / MAX_STEP_DOWN 1.0`（注释里写着"迈步规则只能有一份"，正好）。加一个可选的
     `elevationAt(cell)` 回调，不传 = 平地 = 今天的行为，屋里一行不变。
  3. 节点预算从**网格大小推**（`width × height × 1.5`）而不是写死 4096——4096 是按 24×20 定的，
     院子 80×60 = 4800 格一跨就碰顶，表现是"走到一半站住"。
- 这三条落地后，室外走路今天的两套（`outdoorPass` 院界+阻挡盒、地形陡度）和室内那套（占用图 A*）合成一套：
  **陡度归 groundMap，阻挡归占用图，步高归 canStep**，各管一样、各只有一份。

## 0b · 存档不再写入小镇/店铺几何

> **状态：✅ 已完成**（2026-08-22，提交 `f55513c`）。两处改动照做，四条新用例，
> 每条都验证过"改回去会红"。实测数字全部对上，另有两处文档草稿写错的地方记在验收里。

### 背景：什么该存、什么不该存

游戏里两种地方：

- **家**（`base`）：玩家能挪家具、收放房子，改动必须进存档
- **小镇 + 六家店**（`town`、`shop-*`）：布局固定，玩家动不了。`MapDefinition.volatileRooms: true` 标记它们
  「每次进图当场重新生成，存档里那份直接忽略」

这个标记**读档时是生效的**（`restoreWorld` / `switchMapState` 都看它），但**写档时没人看它**——
`snapshotWorld()` 把所有图的完整几何都写进去。结果是写进去了从没被读过。

实测（用下面「验收·字节」那段脚本量的）：

| | 字节 |
|---|---|
| 家 | 2 726 B |
| 小镇 + 六家店（写进去又丢弃） | 7 305 B |
| 废字节占比 | **72.8%** |
| 每多一座同规模小镇 | +7 305 B，随内容线性增长 |

### 为什么不是「改一行」——读档侧的两个暗礁

原计划写「serialize.ts 改一行跳过 volatile 图、连键都不留」。写细后发现**读档侧有两处逻辑依赖那些键存在**：

1. `loadWorldEntities`（`entities.ts`）：`activeKey = bundle.maps[当前图] ? 当前图 : 第一张图`。
   玩家**在店里存档**，存档里没有店的键 → `activeKey` 退回 `base` → 家里的家具被判成「当前图的」→
   **灌进店铺场景**。
2. `restoreWorld`（`maps.ts`）：`current = saved.maps[当前图] ?? 第一张` → 同样退回 `base` →
   `base` 被当成当前图不上架 → 回家时 `shelvedMaps.base` 不存在 → **家的几何按定义重新生成，锚点和收放状态丢失**。
3. `roomToMapIndex`（`entities.ts`）：实体归属靠「存档几何里的 roomId → mapId」索引；volatile 图没几何就没索引。
   定义兜底只补了 `outdoorRoomId` 和 `extraRoomIds`，**漏了 `primaryRoomId`**（店的主房间、广场）。

所以做法改成**键留着、几何清空**：volatile 图写成 `{ mapId, rooms: {} }`。
两处兜底照常命中键；`rooms: {}` 被读档侧本来就忽略；每图约 30 字节。再补上第 3 条的一行。

> 被否：**连键一起去掉 + 改写两处兜底**。触及 3 个文件 4 处逻辑，而且那两处兜底还服务于
> 「老存档的键不一定叫 base」的兼容路径，改它们要回归更多老档用例。留键是零风险的那条路。

## 0d · 在院子里开始行动，人原地不动

> **状态：✅ 已完成**（2026-08-22，提交 `b440aec`）。改法照做，四条验收全过。
> 根因实测坐实：院子三个起点的房本地格分别是 (−8,2)、(32,24)、(10,26)，**全在 24×20 的网格外**，
> `findPath` 一律返回 null；同样三个起点 `findRoute` 都找得到路（6–7 个路点）。

### 根因

`RoomScene.beginFocusSequence()`（约第 955 行）负责"行动开始 → 走到支撑家具旁 → 进入专注"。它找路用的是
**屋内 A\***：

```ts
const start = worldToRoomCell(room, this.controller.x, this.controller.z);   // 人在院子 → 格子在房子网格之外
…
const path = findPath(room.floorGrid, occupancy, start, cell, { allowBlockedGoal: false });  // 只认 24×20 那张格
if (!path) continue;                                                          // 起点越界 → 每个候选格都 null
…
// 找不到路就原地进入专注（至少不阻塞行动）
this.enterFocusPose(centerX, centerZ);                                       // ← 用户看到的"原地不动"
```

那句兜底在屋里是对的（桌子被围死了就原地做）；在院子里就成了 bug。

**不是寻路不支持院子。** `Game/Systems/navigation.ts` 的导航网格覆盖整个可走范围（注释原话："室内房间
本来就在它里面"），采样时当没锁的门都开着，`findRoute(from, to)` 收世界坐标、吐世界坐标路点，`/goto town`
从客厅走到镇上靠的就是它。`beginFocusSequence` 是更老的代码（房间还是整个世界的年代），`navigation.ts`
是后来为 `/goto` 做的，行动走位从没迁过去。

### 改法（一个文件）

`Frontend-3D/src/Game3D/World/RoomScene.ts` · `beginFocusSequence()`，候选格循环那一段：

**改前**

```ts
    const start = worldToRoomCell(room, this.controller.x, this.controller.z);

    this.controller.enabled = false;

    for (const cell of candidates) {
      if (occupancy.blocked.has(`${cell.x},${cell.y}`)) continue;
      const path = findPath(room.floorGrid, occupancy, start, cell, {
        allowBlockedGoal: false,
      });
      if (!path) continue;

      const points = path.map((p): [number, number] => {
        const world = roomCellToWorld(room, p.x, p.y);
        return [world.x, world.z];
      });
      this.controller.walkAlong(points, () => {
        this.enterFocusPose(centerX, centerZ);
      });
      return;
    }
```

**改后**

```ts
    /*
     * 走统一的室内外导航（Systems/navigation 的 findRoute），不走屋内 A*。
     * 屋内 A* 只认房子那张格：人在院子里起点就越界，每个候选格都 null，
     * 最后掉进"找不到路就原地进入专注"的兜底——那句在屋里是对的（桌子
     * 被围死了就原地做），在院子里就是用户报的"原地不动"。
     * findRoute 的网格本来就盖着屋内（采样时门当开着），从哪儿出发都能到。
     */
    const from = { x: this.controller.x, z: this.controller.z };

    this.controller.enabled = false;

    for (const cell of candidates) {
      if (occupancy.blocked.has(`${cell.x},${cell.y}`)) continue;
      const goal = roomCellToWorld(room, cell.x, cell.y);
      const points = findRoute(from, goal);
      if (!points) continue;

      this.controller.walkAlong(points, () => {
        this.enterFocusPose(centerX, centerZ);
      });
      return;
    }
```

文件头 import 加 `findRoute`（来自 `../../Game/Systems/navigation`）；`findPath` / `worldToRoomCell` 若此后无人用，
从 `core` 的 import 里删掉（tsc 会报 unused）。

**为什么不顺手把兜底也改掉**：屋里桌子被围死时"原地进入专注"仍是想要的行为；改法只换找路的那套，兜底语义不动。

**`findRoute` 出来的路点已经拉直**（视线测试去掉锯齿），`walkAlong` 照走；候选格顺序不变，仍是"家具四周第一个有路的邻格"。
