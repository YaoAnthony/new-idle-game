## 一句话

给 148 件物品各写一个价，把散落各期的金额收进**一张收支并排的表**，
再配一条不变量测试钉住「4~5 个任务永远能 cover 当前开销」。

玩家这一期仍然看不到新东西（可以顺手在物品详情露一行价格）。它是期 3 卖货、
期 5 小店、期 8 餐厅共同的地基——三期都要问同一个问题："这东西值多少"。

## 四件事

### 1-1 · `value` 字段 + 一条体检用例

#### 类型

`Core/src/types/items.ts`，`ItemDefinition` 里 `rarity` 后面：

```ts
  stackLimit: number;
  rarity: Rarity;
  /** 不填按 Otherworld 处理——这个世界的东西是默认，现实物品才是特例 */
  origin?: ItemOrigin;
```

改成：

```ts
  stackLimit: number;
  rarity: Rarity;
  /** 不填按 Otherworld 处理——这个世界的东西是默认，现实物品才是特例 */
  origin?: ItemOrigin;

  /**
   * **这东西值多少金币。**
   *
   * 一个数管两头：卖给小动物按它算，从商人手里买也按它算。**不设
   * 买卖价差**——因为收和卖的集合不重叠（他只收家具、只卖食材，
   * 决策 12），套利在结构上就不成立，再引入一个折扣系数只是多一个
   * 要解释的数字。哪天真出现"同一件东西他既收又卖"，那时候再加价差，
   * 而且那时候才有真实的场景能说清折扣该是多少。
   *
   * **逐件手写，不从 rarity 推公式**（用户 2026-08-24 定）。理由是
   * "这东西值多少"是内容不是推论：同样是"优良"的一张沙发和一块门垫，
   * 玩家心里的价钱差得很远，公式抹平的正是这个差别。稀有度只在**起草**
   * 时当基准用（见下面的定价方法），落进注册表的是显式数字。
   *
   * 不填 = 不可交易。场景道具（灶台、纸箱）、任务物品、图纸都不填——
   * 图纸不填是刻意的：它是商店发出来的凭证，能倒卖的话就成了套现口子。
   */
  value?: number;
```

#### 体检用例

`Core/tests/content.test.ts` 末尾加一条：

```ts
/**
 * 可交易的东西必须有价。
 *
 * 漏写的后果不是崩溃，是**它在商人那儿卖 0 金币**——玩家点了卖、
 * 东西没了、钱没多，看起来像 bug 而且没人报得清。这类"静默地不对"
 * 正是这份文件存在的理由。
 *
 * 豁免的是**结构上就不该交易**的三类，逐类点名而不是给个开关：
 * Quest（任务物品）、图纸（商店发的凭证，能倒卖就是套现口子）、
 * 场景道具（本来就进不了背包，`chestExcludedItemIds` 那张表点过名）。
 */
test("可交易的物品都有价——漏写的会静默地卖 0 金币", () => {
  const EXEMPT_CATEGORIES = new Set([ItemCategory.Quest]);

  for (const item of itemDefinitions) {
    if (EXEMPT_CATEGORIES.has(item.category)) continue;
    if (item.blueprint) continue;
    if (chestExcludedItemIds.has(item.id)) continue;

    assert.ok(
      typeof item.value === "number",
      `${item.id}（${item.category}）没写 value——它会在商人那儿卖 0 金币`,
    );
    assert.ok(item.value! > 0, `${item.id} 的 value 应该大于 0`);
  }
});
```

import 补 `ItemCategory` 和 `chestExcludedItemIds`。

#### 定价方法：稀有度给起草基准，落库是显式数字

148 件全靠拍脑袋会前后不一致（同一档的两件东西差三倍），所以**起草时**
用一张基准表，落进注册表的仍是逐件写死的数：

| 类别 | 普通 | 优良 | 稀有 | 判据 |
|---|---|---|---|---|
| 原料（木头、石墨） | 2 | — | — | 一次行动能拿好几个，单价必须低 |
| 加工件（板子、纸） | 4 | — | — | 比原料贵一档，做加工才有意义 |
| 食材（生的） | 6 | 10 | — | **玩家买**的主要开销 |
| 熟食 | 12 | 18 | 26 | 比食材之和贵——做饭要有溢价 |
| 家具 · Otherworld（工作台造的） | 8 | 16 | 30 | 本地木头敲的，商人见得多 |
| 家具 · Real（行动带回的） | 20 | 45 | 90 | **那边来的东西**，稀罕（决策 12） |

三条压着这张表的约束：

1. **一件普通 Real 家具（20）< 一天打满勾（5×4+12 = 32）**——用户定的
   "单笔：一个勾 > 一件普通家具"落到数字上就是它。而卖货靠**量**赢：
   水獭 2~3 天来一趟，一趟清十几件。
2. **一顿饭的食材 ≤ 一个勾**（决策 6 的"必需开销 1~2 个勾就够"）。
   基础食材 6，一道两材料的菜 12——两个勾多一点，边界上。真到期 3
   接食材货架时按实跑再调这一档。
3. **开一块地 50**（`territoryTuning.unlockCost`，已定）不动。它是这张表
   唯一的既有锚点，其余的数字围着它排。

> 起草脚本可以，**落库必须是字面量**：`value: 20` 而不是
> `value: priceOf(rarity, "furniture")`。公式留在代码里的话，改一件东西
> 的价会连带改一片，而"这件为什么比那件贵"就再也说不清了。

### 1-2 · `Core/src/Data/economy/index.ts`

新建。**全蓝图所有金额从此住这里**（总纲的第一条纪律）。

```ts
/**
 * 经济总表。**改平衡只动这一个文件。**
 *
 * ## 为什么收支要并排
 *
 * 「一天 4~5 个任务永远 cover 当前开销」（用户 2026-08-24）是一条
 * **不变量**，不是一个数。要守住它，"这个阶段进多少 / 出多少"必须
 * 一眼看得见——分散在 dailyTasks、商人货架、餐厅进货三个文件里的话，
 * 每次调平衡都要在三处之间心算，而心算错了没有任何东西会报。
 * 下面 `economyInvariant` 那条用例读的就是这张表。
 *
 * ## 阶段列是留着的，今天只有一个阶段
 *
 * 用户 2026-08-24：阶段刻度（挂在居民数还是地块数还是天数）等数值平衡
 * 时再定。所以这里**结构留全、数字全是占位**——照 `goldJarTuning` 的
 * 先例（l1 是定的、l2/l3 明写占位）。真平衡时是往下面加行、改数，
 * 不是改代码。
 */

export type EconomyStage = {
  stageId: string;
  /** 人读的名字，报错信息里用 */
  label: string;

  /** 进项 */
  income: {
    /** 每日任务打一个勾 */
    perTaskCheck: number;
    /** 四条全打完的满格奖 */
    boardComplete: number;
    /**
     * 卖货的**典型一天**估算。卖货是脉冲式的（水獭 2~3 天来一趟，
     * 一趟清一批），这里填的是摊平到每天的量，只给不变量测试当参考——
     * 它不是任何地方的实际发放数，实际发放按每件的 `value` 算。
     */
    typicalSellPerDay: number;
  };

  /** 出项，**分两层** */
  spending: {
    /**
     * **必需**：不花就过不下去的（吃饭）。
     * 这一项要低到 1~2 个勾就能覆盖——少做几天只该慢，不该倒退。
     */
    essentialPerDay: number;
    /**
     * **可选**：推进度用的（餐厅进货、旅行商人、盖楼摊平）。
     * 打满勾之后的余量就是它的预算。
     */
    optionalPerDay: number;
  };
};

/**
 * 阶段表。**今天只有一个阶段，数字全是占位。**
 *
 * `opening` 这一行反映的是**期 1 落地时的真实状态**：卖货（期 3）、
 * 食材开销（期 3）都还不存在，所以两项都是 0。期 3 上线时把它们填上，
 * 那一刻不变量测试才真正开始咬人。
 */
export const economyStages: EconomyStage[] = [
  {
    stageId: "opening",
    label: "开局（还没有商人和居民）",
    income: {
      // 这两个是**现行值**，不是占位：dailyTasks/index.ts 里已经在用
      perTaskCheck: 5,
      boardComplete: 12,
      typicalSellPerDay: 0, // 期 3 之前没有销路
    },
    spending: {
      essentialPerDay: 0, // 期 3 之前食材不要钱（行动会掉、农田会长）
      optionalPerDay: 0,
    },
  },
];

/** 一天打满那块板能拿多少（4 个勾 + 满格奖）。不变量测试和 UI 共用 */
export function fullBoardIncome(stage: EconomyStage, taskCount: number): number {
  return stage.income.perTaskCheck * taskCount + stage.income.boardComplete;
}

/**
 * 交易的调参（期 3 用）。
 *
 * 卖价就是 `value`、不打折——收和卖的集合不重叠，套利不成立
 * （见 `ItemDefinition.value` 那段）。这里只有"想要"的溢价。
 */
export const tradingTuning = {
  /** 水獭每次来，有几件"这回特别想要的" */
  wantedCount: 3,
  /** 想要的那几件加多少倍价。1.5 = 一件 20 的卖 30 */
  wantedMultiplier: 1.5,
  /** 他多久来一趟（世界日）。固定周期，玩家数得出来（用户 2026-08-24 定） */
  otterVisitEveryDays: 3,
  /** 旅行商人多久来一趟。拉开到 7 天以上，两个角色才不糊 */
  travelerVisitEveryDays: 8,
};

/**
 * 偷窃（期 3）。**第一次全额追回**，所以这个数不是净损失，
 * 是"看得见的一笔钱短暂地不见了"——数值要小到不吓人、大到看得见。
 */
export const theftTuning = {
  /** 小龙偷走多少。库里不够就偷到底为止（adjust_gold 的负数支） */
  amount: 8,
};

/** 居民买家具的日预算（期 5 小店的隔夜结算读它）。占位值 */
export const shopkeepingTuning = {
  budgetPerResidentPerDay: 15,
};
```

### 1-3 · 不变量测试

`Core/tests/economy.test.ts`（新）：

```ts
import assert from "node:assert/strict";
import { test } from "node:test";

import { dailyBoardDefinition } from "../src/Data/dailyTasks/index.js";
import { economyStages, fullBoardIncome } from "../src/Data/economy/index.js";

/**
 * 经济的**不变量**（用户 2026-08-24 定）：一天做 4~5 个任务永远能
 * cover 当前开销。
 *
 * 这不是一条"当前数值对不对"的断言，是一道**闸**：以后任何人调平衡，
 * 把某个阶段的必需开销调到打满勾都不够，这里当场红。没有它的话，
 * 那种破坏要等玩家在游戏里饿一天才发现，而且会被当成"这版怎么这么难"
 * 而不是"有人改错了一个数"。
 *
 * 分两条断言是因为"慢"和"倒退"是两回事（总纲：慢不是倒退）：
 * 必需开销要低到轻松覆盖，可选开销才允许吃掉余量。
 */

test("每个阶段：打满一块板的收入 ≥ 当天的必需开销", () => {
  assert.ok(economyStages.length > 0, "阶段表不能是空的");

  for (const stage of economyStages) {
    const income = fullBoardIncome(stage, dailyBoardDefinition.taskCount);
    assert.ok(
      income >= stage.spending.essentialPerDay,
      `阶段「${stage.label}」：打满一块板拿 ${income}，必需开销 ${stage.spending.essentialPerDay}——不够吃饭`,
    );
  }
});

test("每个阶段：必需开销不超过两个勾——少做几天只该慢，不该倒退", () => {
  for (const stage of economyStages) {
    const twoChecks = stage.income.perTaskCheck * 2;
    assert.ok(
      stage.spending.essentialPerDay <= twoChecks,
      `阶段「${stage.label}」：必需开销 ${stage.spending.essentialPerDay} 超过两个勾（${twoChecks}）——出差一周回来会被吃穿`,
    );
  }
});

test("每个阶段：打满板还剩得下推进度的钱（必需 + 可选 ≤ 满格收入 + 卖货）", () => {
  for (const stage of economyStages) {
    const income =
      fullBoardIncome(stage, dailyBoardDefinition.taskCount) +
      stage.income.typicalSellPerDay;
    const outgo = stage.spending.essentialPerDay + stage.spending.optionalPerDay;
    assert.ok(
      income >= outgo,
      `阶段「${stage.label}」：一天进 ${income}、出 ${outgo}——进度会停住`,
    );
  }
});

test("阶段 id 不重复", () => {
  const ids = new Set<string>();
  for (const stage of economyStages) {
    assert.ok(!ids.has(stage.stageId), `阶段 id 重复：${stage.stageId}`);
    ids.add(stage.stageId);
  }
});
```

## 最容易写错的三处

### 一 · 图纸不能有价

图纸是商店发出来的**凭证**。给它定价 = 玩家花 50 买张图纸、转手卖 50，
或者更糟：卖价高于买价时无限刷钱。体检用例里 `if (item.blueprint) continue;`
就是拦这个的，别"顺手"给它补一个价让用例过。

### 二 · 卖价和买价共用一个数，靠的是**集合不重叠**不是靠折扣

今天成立是因为决策 12（他只收家具、只卖食材）。**哪天有人让某个商人
既收又卖同一类东西，这个前提当场失效**，那时候要加的是价差，不是在
调用点补一个乘数。把这条写进 `value` 的注释里（上面已经写了），
下一个人改商人货架时才看得见。

### 三 · 占位值必须**注释明写**是占位

`goldJarTuning` 的先例：l1 写着"用户定的"，l2/l3 写着"占位值，等产出量
定下来再调"。这一期填进 economy 表的几乎全是占位——不写明的话，
三个月后没人分得清哪个数是拍过板的、哪个是随手填的，而"不敢动的数字"
比"错的数字"更耽误事。

### 顺手加的：`window.__run`

命令行的唯一入口是聊天面板，自动化验收要走"聚焦输入框 → 逐字打字 →
回车 → 从 DOM 捞回显"四步，每步都可能因为面板动画、输入法、滚动位置失手，
而那些失手看起来像"命令坏了"。照 `window.__scene` 的先例挂了个 DEV-only
的 `window.__run(input)`，直接调 `runCommand`。**玩家可达的入口没有新增。**
后面八期的浏览器验收都靠它。
